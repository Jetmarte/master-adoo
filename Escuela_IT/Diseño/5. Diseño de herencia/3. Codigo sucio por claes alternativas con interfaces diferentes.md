# 3. Código sucio por clases alternativas con interfaces diferentes

> [!info] Code smell · Alternative Classes with Different Interfaces
> *Refactoring* (Code Smells) — Martin Fowler.
> Relacionado con [[6. Patron metodo plantilla|Método Plantilla]], [[1. Principio de sustitucion de LISCOV|LSP]] y [[7. Principio No te repitas DRY|DRY]].
> Existe una versión ampliada en [[4. Codigo sucio por clases alternativas con interfaces diferentes|Diseño de métodos]].

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Alternative Classes with Different Interfaces** | *Refactoring* (Code Smells) — Martin Fowler |
| **Clases alternativas con interfaces diferentes** | Traducción al español |

---

## 📖 ¿Qué es?

Dos o más clases realizan **la misma función** (semánticamente equivalente), pero exponen **interfaces distintas**: nombres de método diferentes, parámetros distintos o responsabilidades repartidas de forma inconsistente.

> [!warning] Señal de alarma
> El cliente necesita **conocer cada clase concreta** y escribir `if/else` o `switch` para usar una u otra.

### 🧩 Ejemplo típico

```java
public class RepositorioClientesMySQL {
    public void guardarCliente(Cliente cliente) { /* ... */ }
    public Cliente buscarClientePorId(int id)   { /* ... */ }
}

public class RepositorioClientesMongo {
    public void insertar(Cliente cliente) { /* ... */ }
    public Cliente obtener(int id)        { /* ... */ }
}
```

```java
// ❌ El cliente conoce los detalles de cada implementación
if (configuracion.usaMySQL()) {
    repositorioMySQL.guardarCliente(cliente);
} else {
    repositorioMongo.insertar(cliente);
}
```

---

## ❓ Por qué es un problema

- **Complejidad innecesaria**: el cliente maneja varios nombres para la misma operación.
- **Código duplicado** en los clientes (mismos `if/else`, validaciones, bucles).
- **Impide el polimorfismo**: no se puede tratar a las clases de forma uniforme.
- **Difícil de sustituir**: cambiar de implementación obliga a tocar el cliente.
- **Mantenimiento frágil**: un cambio en una clase exige revisar todos sus usos.

> [!tip] Idea clave
> Si dos clases son **alternativas** (hacen lo mismo), deben ofrecer **la misma interfaz**. Así el cliente depende de la **abstracción**, no de la implementación.

---

## ✅ Solución

| Técnica | Cuándo usarla |
|---------|---------------|
| **Rename Method** | Hacen lo mismo pero se llaman distinto (`guardar` vs `insertar`) |
| **Move Method / Move Field** | Una responsabilidad está en la clase equivocada; se mueve hasta homogeneizar |
| **Extract Superclass** | Comparten comportamiento **e** interfaz |
| **Extract Interface** | Solo comparten la interfaz, no la implementación |
| **Método Plantilla** | El esqueleto del algoritmo es común y solo cambian algunos pasos |

> [!note] Pasos prácticos
> 1. **Renombrar** los métodos equivalentes para que tengan el mismo nombre y cabecera.
> 2. **Mover** responsabilidades hasta que las clases hagan lo mismo con los mismos nombres.
> 3. **Extraer** una superclase o una interfaz común y hacer que el cliente dependa de ella.

---

## 🔧 Ejemplo (después): interfaz común

```java
public interface RepositorioClientes {
    void guardar(Cliente cliente);
    Optional<Cliente> buscarPorId(int id);
}
```

```java
public class RepositorioClientesMySQL implements RepositorioClientes {
    @Override
    public void guardar(Cliente cliente) { /* ... */ }

    @Override
    public Optional<Cliente> buscarPorId(int id) { /* ... */ }
}

public class RepositorioClientesMongo implements RepositorioClientes {
    @Override
    public void guardar(Cliente cliente) { /* ... */ }

    @Override
    public Optional<Cliente> buscarPorId(int id) { /* ... */ }
}
```

```java
// ✅ El cliente ya no sabe qué implementación usa
public class ServicioClientes {
    private final RepositorioClientes repositorio;

    public ServicioClientes(RepositorioClientes repositorio) {
        this.repositorio = repositorio;
    }

    public void registrar(Cliente cliente) {
        repositorio.guardar(cliente);
    }
}
```

> [!success] Resultado
> Desaparece el `if/else`, el cliente depende de una **interfaz estable** y se pueden añadir implementaciones sin tocar el código cliente ([[6. Principio abierto - cerrado|Open/Closed]]).

## 🎮 Ejemplo del temario: `PutController` y `MoveController`

Ambos realizan **semánticamente la misma función de control**, pero exponen métodos distintos (`put` y `move`):

```java
// ❌ Interfaces diferentes para la misma responsabilidad
public class PutController {
    public void put(Coordinate coordinate) { /* colocar ficha */ }
}

public class MoveController {
    public void move(Coordinate origen, Coordinate destino) { /* mover ficha */ }
}
```

Solución del temario:

1. **Homogeneizar** los métodos (`colocate`).
2. Crear una jerarquía de herencia con la clase base `ColocateController`.
3. Aplicar **Método Plantilla**: la superclase define el esqueleto y las subclases implementan los pasos variables.

```java
// ✅ Interfaz homogénea con Método Plantilla (simplificado)
public abstract class ColocateController {
    public final void colocate(Coordinate origen, Coordinate destino) {
        validate(origen, destino);
        executeColocate(origen, destino);
        updateView();
    }

    protected abstract void executeColocate(Coordinate origen, Coordinate destino);
    protected abstract void updateView();

    private void validate(Coordinate origen, Coordinate destino) { /* común */ }
}

public class PutController extends ColocateController {
    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // colocar ficha en el destino
    }

    @Override
    protected void updateView() { /* ... */ }
}

public class MoveController extends ColocateController {
    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // mover ficha de origen a destino
    }

    @Override
    protected void updateView() { /* ... */ }
}
```

---

## 🔍 Cómo detectarlo

- Dos clases con **métodos equivalentes y nombres distintos**: `guardar` / `insertar` / `add` / `save`.
- Clientes con **`if/else` o `switch`** para elegir entre clases alternativas.
- **Parámetros en distinto orden** o con distinto tipo para la misma operación.
- Una clase tiene una responsabilidad que **debería estar** en la otra.
- Al cambiar una clase hay que cambiar **también** la otra para mantener la coherencia.

---

## 🎯 Conclusión para examen

1. **Clases alternativas con interfaces diferentes** = clases que hacen lo mismo pero el cliente las usa de forma distinta.
2. **Problema:** complejidad innecesaria, duplicación, falta de polimorfismo y mantenimiento frágil.
3. **Solución:** **renombrar** métodos equivalentes, **mover** responsabilidades para homogeneizar y **extraer** una superclase o interfaz común.
4. En el temario, `PutController` y `MoveController` se unifican con **herencia** y **Método Plantilla** sobre `ColocateController`.

> [!question] Pregunta típica
> *"¿Qué es el smell 'Alternative Classes with Different Interfaces' y cómo se corrige?"*
> **Respuesta:** son clases que realizan la misma función pero exponen interfaces distintas (`guardarCliente` vs `insertar`), lo que provoca `if/else` y duplicación en los clientes. Se corrige renombrando los métodos equivalentes, moviendo responsabilidades hasta homogeneizarlas y extrayendo una superclase o interfaz común; en el temario se aplica con `ColocateController` y Método Plantilla.
