# 4. Código sucio por herencia rechazada

> [!info] Code smell · Refused Bequest
> *Refactoring* (Code Smells) — Martin Fowler.
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]], [[2. Relacion de herencia vs composicion|Herencia vs composición]] y [[6. Patron metodo plantilla|Método Plantilla]].

---

| Término | Fuente |

---

## 📖 ¿Qué es?

Una subclase **hereda métodos y atributos del padre que no necesita**. La herencia se usa para reutilizar **parte** del comportamiento, pero la subclase se ve obligada a cargar con una interfaz que no le corresponde.

> [!warning] Señal de alarma
> Aparecen métodos **vacíos**, métodos que **lanzan `UnsupportedOperationException`** o atributos heredados que nunca se usan.

### 🧩 Ejemplo típico

```java
public class Ave {
    public void volar() { /* ... */ }
    public void comer() { /* ... */ }
}

// ❌ El pingüino no vuela, pero hereda volar()
public class Pinguino extends Ave {
    @Override
    public void volar() {
        throw new UnsupportedOperationException("Los pingüinos no vuelan");
    }
}
```

```java
// El cliente confía en el contrato de Ave... y falla
public void soltar(List<Ave> aves) {
    for (Ave ave : aves) {
        ave.volar(); // ❌ explota con Pinguino
    }
}
```

---

## ❓ Por qué es un problema

- La subclase **no es sustituible** por el padre → se viola [[1. Principio de sustitucion de LISCOV|LSP]].
- La **interfaz de la subclase queda contaminada** con operaciones que no debería ofrecer.
- El cliente escribe código defensivo (`instanceof`, `try/catch`) o **falla en tiempo de ejecución**.
- La jerarquía se vuelve **confusa**: no queda claro qué puede hacer realmente cada clase.

> [!tip] Idea clave
> Heredar **implementación** que no se usa es un olor **débil**; heredar y **rechazar la interfaz** (negar un método público) es un olor **fuerte** que exige rediseño.

---

## 🔍 Dos tipos de herencia rechazada

| Tipo | Qué ocurre | Gravedad | Solución |
|------|------------|----------|----------|
| **Rechazo de implementación** | La subclase no usa algún método/atributo heredado, pero no molesta | 🟡 Débil | A menudo **no merece la pena** limpiarlo |
| **Rechazo de interfaz** | La subclase **no puede** cumplir un método público y lo deja vacío o lanza excepción | 🔴 Fuerte | **Reemplazar herencia por delegación** o rediseñar la jerarquía |

> [!quote] Fowler (parafraseado)
> «No nos importa rechazar implementaciones, pero rechazar la interfaz ya es otra cosa.»

---

## 🛠️ Solución tradicional: reestructurar la jerarquía

1. Crear **clases intermedias** (habitualmente abstractas).
2. **Empujar métodos hacia abajo** (*Push Down Method*) y **campos hacia abajo** (*Push Down Field*).
3. **Subir** a la clase padre solo el **factor común** de todas las derivadas.

Así cada clase padre tiene **exactamente** lo que comparten sus hijas, ni más ni menos.

```java
// ✅ Jerarquía reestructurada
public abstract class Ave {
    public void comer() { /* común a todas */ }
}

public abstract class AveVoladora extends Ave {
    public abstract void volar();
}

public class Pinguino extends Ave {
    public void nadar() { /* ... */ }
}

public class Aguila extends AveVoladora {
    @Override
    public void volar() { /* ... */ }
}
```

> [!warning] Cuidado
> Reestructurar **complica** la jerarquía. Si el rechazo es solo de implementación y no causa problemas, a menudo **es mejor dejarlo** (el olor es demasiado débil para limpiarlo).

## 🎮 Ejemplo del temario: `prePut` en `ColocateController`

```java
// ❌ MoveController hereda prePut, pero no le atañe
public abstract class ColocateController {
    public void prePut() { /* preparar colocación */ }
    public abstract void colocate();
}

public class PutController extends ColocateController {
    @Override
    public void colocate() { /* poner ficha */ }
}

public class MoveController extends ColocateController {
    @Override
    public void prePut() {
        // implementación "vacía": no le corresponde
    }

    @Override
    public void colocate() { /* quitar y poner ficha */ }
}
```

`MoveController` **rechaza** `prePut`: hereda una operación que no necesita y se ve obligado a implementarla vacía.

### ✅ Solución del temario: Método Plantilla

Se reestructura la jerarquía para que el método abstracto común sea `colocate`, y cada derivada lo redefina según su responsabilidad:

```java
public abstract class ColocateController {
    public final void colocate(Coordinate origen, Coordinate destino) {
        validate(origen, destino);
        executeColocate(origen, destino);
        updateView();
    }

    protected abstract void executeColocate(Coordinate origen, Coordinate destino);
    protected abstract void updateView();

    private void validate(Coordinate origen, Coordinate destino) { /* común */ }
}

public class PutController extends ColocateController {
    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // poner ficha
    }

    @Override
    protected void updateView() { /* ... */ }
}

public class MoveController extends ColocateController {
    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // quitar ficha del origen y poner en el destino
    }

    @Override
    protected void updateView() { /* ... */ }
}
```

> [!success] Resultado
> Ninguna subclase hereda operaciones que no le corresponden; **no hay métodos vacíos** y se respeta el contrato de la clase base.

---

## 🔧 Solución definitiva: reemplazar herencia por delegación

Si la subclase **reutiliza comportamiento pero rechaza la interfaz**, no juegues con la jerarquía: **aplica Replace Inheritance with Delegation**.

```java
// ❌ Pila que hereda de List: hereda métodos que no debería exponer
public class Pila<T> extends ArrayList<T> {
    public void apilar(T elemento) { add(elemento); }
    public T desapilar()           { return remove(size() - 1); }
}
```

```java
// ✅ Composición + delegación: solo expone la interfaz de pila
public class Pila<T> {
    private final List<T> elementos = new ArrayList<>();

    public void apilar(T elemento) { elementos.add(elemento); }
    public T desapilar()           { return elementos.remove(elementos.size() - 1); }
    public boolean vacia()         { return elementos.isEmpty(); }
    public int tamano()            { return elementos.size(); }
}
```

> [!tip] Regla
> Si la subclase **no quiere apoyar la interfaz** de la superclase, la herencia es la herramienta equivocada: usa **composición y delegación** (ver [[2. Relacion de herencia vs composicion|Herencia vs composición]]).

---

## 🔍 Cómo detectarlo

- Métodos sobrescritos con **cuerpo vacío** o que solo lanzan una excepción.
- Subclases que usan **solo una parte** de los métodos heredados.
- Aparición de `instanceof` para evitar llamar a métodos “peligrosos”.
- Comentarios del tipo `// no soportado` o `// no aplica`.
- Atributos heredados que la subclase **nunca lee ni escribe**.

---

## 🎯 Conclusión para examen

1. **Herencia rechazada** = la subclase hereda métodos o atributos que **no necesita**.
2. **Olor débil**: rechazo de implementación → a menudo no merece limpieza.
3. **Olor fuerte**: rechazo de interfaz (métodos vacíos o que lanzan excepciones) → **rediseñar**.
4. **Solución tradicional**: clases intermedias, *push down* de métodos/campos y subir solo el factor común.
5. **Solución definitiva**: si se rechaza la interfaz, **reemplazar herencia por delegación**.
6. En el temario, `MoveController` rechaza `prePut`; se corrige con **Método Plantilla** y `colocate`.

> [!question] Pregunta típica
> *"¿Qué es la herencia rechazada y cómo se corrige?"*
> **Respuesta:** es un smell en el que una subclase hereda métodos o atributos que no necesita, a menudo dejándolos vacíos o lanzando excepciones. Si solo se rechaza la implementación puede ser tolerable; si se rechaza la interfaz, hay que rediseñar la jerarquía (clases intermedias, *push down*) o, mejor, **reemplazar la herencia por composición y delegación**. En el temario se corrige con el patrón Método Plantilla sobre `ColocateController`.
