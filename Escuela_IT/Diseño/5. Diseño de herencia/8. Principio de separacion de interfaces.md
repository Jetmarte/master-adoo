# 8. Principio de separación de interfaces (ISP)

> [!info] Principio SOLID · Interface Segregation Principle
> Formulado por **Robert C. Martin** como la **I** de SOLID.
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]], [[10. Principio de unica responsabilidad|SRP]] y [[8. Principio KISS|KISS]].

---

## 📖 ¿Qué dice el principio?

> [!quote] Robert C. Martin
> «Los clientes **no deberían verse forzados a depender** de interfaces que **no usan**.»

O dicho de otro modo:

> [!tip] Idea clave
> Es mejor **muchas interfaces pequeñas y específicas** que **una interfaz grande y genérica** («gorda»). Cada cliente debe conocer **solo lo que necesita**.

---

## ❓ Motivación

Cuando un cliente depende de una clase con una **interfaz que no usa** (pero otros clientes sí), ese cliente **se ve afectado** por los cambios que otros clientes fuercen sobre la clase.

En una jerarquía de herencia, a veces se añaden interfaces a la clase base **solo por el beneficio de una subclase**:

- La interfaz de la base se **contamina** y se vuelve «gorda».
- Cada nueva interfaz añadida a la base **obliga a implementarla** (o a permitirla por defecto) en **todas** las derivadas.
- Es habitual rellenarla con **métodos vacíos** en vez de abstractos → se viola [[1. Principio de sustitucion de LISCOV|LSP]].

> [!warning] Señal de alarma
> Clases con métodos que lanzan `UnsupportedOperationException`, métodos vacíos “porque toca”, o clientes que solo usan 2 de 15 métodos de una interfaz.

---

## ❌ Ejemplo: la interfaz «gorda»

```java
// ❌ Interfaz que mezcla responsabilidades de varios clientes
public interface Trabajador {
    void trabajar();
    void comer();
    void dormir();
    void cobrar();
}
```

```java
// ❌ El robot no come ni duerme: se ve obligado a implementar lo que no usa
public class Robot implements Trabajador {
    @Override
    public void trabajar() { /* ... */ }

    @Override
    public void comer()  { throw new UnsupportedOperationException(); }

    @Override
    public void dormir() { throw new UnsupportedOperationException(); }

    @Override
    public void cobrar() { throw new UnsupportedOperationException(); }
}
```

> [!danger] Problemas
> - `Robot` depende de métodos que **no necesita**.
> - Se viola **LSP**: un `Robot` no puede sustituir a un `Trabajador` genérico.
> - Un cambio en `comer()` (por ejemplo, para un `Humano`) obliga a recompilar/revisar `Robot`.

### ✅ Solución: segregar interfaces

```java
public interface Trabajador {
    void trabajar();
}

public interface SerHumano {
    void comer();
    void dormir();
}

public interface Asalariado {
    void cobrar();
}
```

```java
// ✅ Cada clase implementa solo lo que le corresponde
public class Robot implements Trabajador {
    @Override
    public void trabajar() { /* ... */ }
}

public class Empleado implements Trabajador, SerHumano, Asalariado {
    @Override public void trabajar() { /* ... */ }
    @Override public void comer()    { /* ... */ }
    @Override public void dormir()   { /* ... */ }
    @Override public void cobrar()   { /* ... */ }
}
```

> [!success] Resultado
> Cada cliente depende de **interfaces cohesivas**. `Robot` no arrastra métodos que no puede cumplir y se respeta [[1. Principio de sustitucion de LISCOV|LSP]].

## 🏛️ Ejemplo del temario: la secretaría de la universidad

Un mismo objeto (la **secretaría**) ofrece servicios **muy distintos** a clientes distintos, pero trabaja sobre los **mismos datos**:

| Cliente | Interfaz que usa | Operaciones |
|---------|------------------|-------------|
| **Alumnos** | `SecretariaAlumnos` | matricularse, consultar expediente… |
| **Profesores** | `SecretariaProfesores` | cerrar grupo, firmar actas… |
| **Dirección** | `SecretariaDireccion` | configurar planes de estudios… |
| **Rectorado** | `SecretariaRectorado` | … |

```java
public interface SecretariaAlumnos {
    void matricular(String alumno, String asignatura);
    Expediente consultarExpediente(String alumno);
}

public interface SecretariaProfesores {
    void cerrarGrupo(String asignatura);
    void firmarActas(String asignatura);
}

public interface SecretariaDireccion {
    void configurarPlanDeEstudios(String titulacion, Plan plan);
}
```

```java
// ✅ Un mismo objeto implementa varias interfaces cohesivas
public class Secretaria implements SecretariaAlumnos, SecretariaProfesores, SecretariaDireccion {
    // ... implementaciones que comparten los mismos datos
}
```

Cada cliente colabora con el **mismo objeto**, pero a través de una **interfaz completamente diferente**:

```java
public class Alumno {
    private final SecretariaAlumnos secretaria; // solo conoce lo suyo

    public Alumno(SecretariaAlumnos secretaria) {
        this.secretaria = secretaria;
    }

    public void matricularse(String asignatura) {
        secretaria.matricular("Ana", asignatura);
    }
}
```

> [!note] Clave
> Las interfaces se implementan en el **mismo objeto** porque manipulan los **mismos datos**; lo que cambia es **qué ve cada cliente**. Se puede acceder a ellas por **delegación** o mediante una **clase base**.

---

## 🎮 Ejemplo del temario: `BoardView` y `PresenterView`

**Problema:** `BoardView` tenía acceso a **más operaciones de las necesarias** de la vista.

**Solución:** definir una interfaz **mínima** `PresenterView` que determine el **único método** accesible desde `BoardView`.

```java
// ✅ Interfaz segregada: solo lo que BoardView necesita
public interface PresenterView {
    void showBoard(String tablero);
}

public class BoardView {
    private final PresenterView presenterView;

    public BoardView(PresenterView presenterView) {
        this.presenterView = presenterView;
    }

    public void render(String tablero) {
        presenterView.showBoard(tablero);
    }
}
```

Así `BoardView` **no puede** llamar a operaciones de la vista que no le corresponden.

## 🔧 Cómo aplicar ISP

| Técnica | Qué hace |
|---------|----------|
| **Extract Interface** | Extraer de una interfaz gorda el grupo de métodos que usa un cliente |
| **Split Interface** | Dividir una interfaz en varias cohesivas |
| **Delegación** | Un mismo objeto implementa varias interfaces y cada cliente usa la suya |
| **Clase base abstracta** | Los clientes conocen abstracciones con interfaces cohesivas |

> [!note] Pasos prácticos
> 1. Identificar los **grupos de clientes** y qué métodos usa cada uno.
> 2. **Agrupar** los métodos por cliente (interfaces cohesivas).
> 3. Hacer que el objeto implemente **todas** las interfaces necesarias.
> 4. Inyectar en cada cliente **solo** la interfaz que necesita.

---

## ⚖️ Compromiso: no abusar (YAGNI)

Como todos los principios SOLID, ISP **cuesta esfuerzo y tiempo** y **aumenta la complejidad**. Aplicarlo en exceso produce un código lleno de **interfaces con un solo método**.

> [!warning] Equilibrio
> Aplica ISP **según la experiencia y el sentido común**, identificando las áreas donde la **extensión futura es más probable**.
> **[[8. Principio KISS|KISS]]** y **[[6. Principio no vas ha necesitarlo YAGNI|YAGNI]]** también cuentan: no crees interfaces que hoy no necesitas.

---

## 🔍 Cómo detectar una violación

- Interfaces con **muchos métodos** que sirven a clientes muy distintos.
- Clases que implementan métodos **vacíos** o que lanzan excepciones.
- Clientes que usan **solo una parte** de la interfaz.
- Cambios en la interfaz que **obligan a tocar** clases que no usan ese método.
- Nombres de interfaz genéricos (`Manager`, `Service`, `Util`) con responsabilidades mezcladas.

---

## 🎯 Conclusión para examen

1. **ISP**: los clientes **no deben depender** de interfaces que **no usan**.
2. Prefiere **interfaces pequeñas y cohesivas** frente a una **interfaz gorda**.
3. Las interfaces gordas **contaminan** la clase base y fuerzan métodos vacíos → violan [[1. Principio de sustitucion de LISCOV|LSP]].
4. **Solución:** segregar en varias interfaces, implementarlas en el **mismo objeto** y que cada cliente use la suya (por delegación o clase base).
5. En el temario: `PresenterView` limita lo que `BoardView` puede usar; la secretaría universitaria ofrece una interfaz distinta a alumnos, profesores y dirección.
6. **No abusar**: demasiadas interfaces de un solo método también son un problema (**[[8. Principio KISS|KISS]]** / **[[6. Principio no vas ha necesitarlo YAGNI|YAGNI]]**).

> [!question] Pregunta típica
> *"¿Qué es el Principio de Segregación de Interfaces y pon un ejemplo?"*
> **Respuesta:** los clientes no deben verse obligados a depender de interfaces que no usan. Una interfaz «gorda» obliga a implementar métodos innecesarios (a menudo vacíos o con excepciones), contamina la clase base y viola LSP. Se corrige dividiéndola en interfaces cohesivas que el mismo objeto implementa y de las que cada cliente conoce solo la suya. Ejemplo: separar `Trabajador`, `SerHumano` y `Asalariado`; en el temario, `PresenterView` limita la interfaz que usa `BoardView`.
