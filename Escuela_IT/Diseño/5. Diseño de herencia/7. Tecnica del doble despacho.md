# 7. Técnica del doble despacho

> [!info] Técnica · Double Dispatch
> Base del patrón **Visitor** (GoF). Permite elegir el comportamiento según el **tipo del receptor** y el **tipo del argumento**.
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]] y [[6. Principio abierto - cerrado|Open/Closed]].

---

## 📖 ¿Qué es?

> [!tip] Idea clave
> El **doble despacho** envía un mensaje a un objeto polimórfico **pasándose a sí mismo** como parámetro, para que el receptor elija el método adecuado según la **clase concreta** del objeto. Así se evita preguntar por el tipo con `instanceof`.

**Un despacho simple**: `objeto.metodo()` → el método se elige según el **tipo del receptor**.
**Doble despacho**: `visitante.visit(objeto)` → el método se elige según el **tipo del receptor** (`visitante`) **y** el **tipo del argumento** (`objeto`).

---

## ❓ Motivación

Necesitamos dar un **tratamiento específico según la clase derivada concreta** de un objeto polimórfico. La solución “fácil” (y sucia) es preguntar por el tipo:

```java
// ❌ RTTI: viola LSP y Open/Closed
for (OperationController controller : controllers) {
    if (controller instanceof StartController) {
        view.showStart((StartController) controller);
    } else if (controller instanceof PutController) {
        view.showPut((PutController) controller);
    } else if (controller instanceof MoveController) {
        view.showMove((MoveController) controller);
    }
}
```

Cada nueva subclase obliga a **modificar** este `if/else` → [[7. Codigo sucio por cirugia a escopetazos|Cirugía a escopetazos]] y violación de [[1. Principio de sustitucion de LISCOV|LSP]].

---

## 🛠️ Solución: `accept` + `visit`

### Paso 1 — En el objeto polimórfico: `accept`

Cada clase de la jerarquía implementa `accept`, que se **auto-pasa** (`this`) al visitante:

```java
public abstract class OperationController {
    public abstract void accept(OperationControllerVisitor visitor);
}
```

```java
public class StartController extends OperationController {
    @Override
    public void accept(OperationControllerVisitor visitor) {
        visitor.visit(this); // 'this' ya es de tipo StartController
    }
}
```

### Paso 2 — En el visitante: un `visit` por cada derivada

```java
public interface OperationControllerVisitor {
    void visit(StartController controller);
    void visit(PutController controller);
    void visit(MoveController controller);
}
```

```java
public class TicTacToeView implements OperationControllerVisitor {
    @Override
    public void visit(StartController controller) {
        // mostrar pantalla de inicio
    }

    @Override
    public void visit(PutController controller) {
        // mostrar tablero para poner ficha
    }

    @Override
    public void visit(MoveController controller) {
        // mostrar tablero para mover ficha
    }
}
```

### Paso 3 — El cliente ya no pregunta por el tipo

```java
// ✅ Sin instanceof: el doble despacho elige el método correcto
for (OperationController controller : controllers) {
    controller.accept(view);
}
```

---

## 🧠 ¿Por qué es “doble”?

| Despacho | Quién elige | Qué método se ejecuta |
|----------|-------------|-----------------------|
| **1.º** | El objeto concreto (`StartController`) | `accept(...)` de su clase |
| **2.º** | El visitante (`TicTacToeView`) según el **tipo estático** de `this` | `visit(StartController)` |

El truco está en que `visitor.visit(this)` se resuelve en **tiempo de compilación** por la **sobrecarga** (`visit(StartController)` vs `visit(PutController)`), y `accept` se resuelve en **tiempo de ejecución** por el **polimorfismo**.

> [!note] Sin `accept`, no hay doble despacho
> Java **no** tiene doble despacho nativo: si llamas `visitor.visit(controller)` con una variable de tipo `OperationController`, siempre entra por `visit(OperationController)`. Por eso hace falta el `accept` que fije el tipo concreto con `this`.

---

## 🎮 Ejemplo del temario: `TicTacToeView`

**Problema:** `TicTacToeView` preguntaba por la clase del objeto polimórfico (`OperationController` y sus derivadas) → violación de LSP.

**Solución:** aplicar doble despacho haciendo que `TicTacToeView` sea el **visitador** de la jerarquía `OperationController`.

```java
public interface OperationControllerVisitor {
    void visit(StartController controller);
    void visit(PutController controller);
    void visit(MoveController controller);
}
```

```java
public abstract class OperationController {
    public abstract void accept(OperationControllerVisitor visitor);
}
```

```java
public class TicTacToeView implements OperationControllerVisitor {
    // Implementa un visit por cada controlador
}
```

También se aplica en el temario a `GameView` como visitador de `CoordinateController`, incorporando la interfaz `CoordinateControllerVisitor` (relacionado con [[5. Principio de inversion de dependencias|Inversión de dependencias]]).

---

## 🔄 Relación con el patrón Visitor

El **doble despacho** es el **mecanismo**; el **Visitor** es el **patrón** que lo estructura:

```
Elemento (accept)  ──>  Visitor (visit)
   ▲                        ▲
   │                        │
ConcreteElementA       ConcreteVisitor
ConcreteElementB
```

| Ventaja | Inconveniente |
|---------|---------------|
| Añadir **nuevas operaciones** (visitantes) sin tocar los elementos | Añadir **nuevos elementos** obliga a cambiar **todos** los visitantes |
| Elimina `instanceof` y respeta [[6. Principio abierto - cerrado|Open/Closed]] para operaciones | Puede romper la encapsulación si el visitante necesita datos privados |
| Centraliza en un visitante la lógica de un recorrido | Más clases y más indirección |

> [!warning] Compromiso
> El doble despacho **abre** la jerarquía a nuevas **operaciones** pero la **cierra** a nuevos **tipos** (habría que añadir un `visit` en la interfaz del visitante). Úsalo cuando los tipos son estables y las operaciones cambian.

---

## 🔍 Cuándo usarlo

- Necesitas un comportamiento que depende de **dos tipos** a la vez.
- Tienes una jerarquía **estable** de elementos y **muchas operaciones** distintas sobre ellos.
- Quieres **eliminar `instanceof`/`switch`** sobre subtipos.
- El tratamiento por tipo está **disperso** en varios clientes.

---

## 🎯 Conclusión para examen

1. **Doble despacho** = enviar `accept` al objeto polimórfico **pasándose a sí mismo** (`this`) para que el visitante elija el `visit` adecuado.
2. **Mecánica:**
   - En cada derivada: `void accept(X x) { x.visit(this); }`
   - En el visitante: un `void visit(Derivada d)` por cada derivada.
3. Evita `instanceof`/RTTI y respeta [[1. Principio de sustitucion de LISCOV|LSP]].
4. Es la base del patrón **Visitor**.
5. En el temario: `TicTacToeView` visita `OperationController` y `GameView` visita `CoordinateController`.

> [!question] Pregunta típica
> *"¿Qué es el doble despacho y qué problema resuelve?"*
> **Respuesta:** es una técnica que permite ejecutar un comportamiento según el tipo concreto de un objeto polimórfico sin usar `instanceof`. El objeto recibe `accept(visitante)` y se pasa a sí mismo con `this`; el visitante tiene un `visit` sobrecargado por cada derivada. Así el primer despacho lo resuelve el polimorfismo (`accept`) y el segundo la sobrecarga (`visit`). Es la base del patrón Visitor; en el temario se usa en `TicTacToeView` sobre `OperationController`.
