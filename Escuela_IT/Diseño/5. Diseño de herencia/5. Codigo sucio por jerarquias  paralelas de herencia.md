# 5. Código sucio por jerarquías paralelas de herencia

> [!info] Code smell · Parallel Inheritance Hierarchies
> *Refactoring* (Code Smells) — Martin Fowler.
> Es un **caso especial** de [[7. Codigo sucio por cirugia a escopetazos|Cirugía a escopetazos]].
> Relacionado con [[6. Patron metodo plantilla|Método Plantilla]] y [[2. Relacion de herencia vs composicion|Herencia vs composición]].

---

## 📖 ¿Qué es?

Ocurre cuando **cada vez que creas una subclase de una jerarquía, te ves obligado a crear también una subclase en otra jerarquía**. Las dos jerarquías crecen **en paralelo** y con los mismos prefijos.

> [!warning] Señal de alarma
> Los nombres de las clases de una jerarquía **empiezan igual** que los de la otra. Si añadir `X` a una familia obliga a añadir `X` a la otra, tienes jerarquías paralelas.

### 🧩 Ejemplo clásico del temario

```
Paciente
├── Paciente de Seguridad Pública
│   ├── Paciente de Seguridad Pública de Traumatología
│   ├── Paciente de Seguridad Pública de Cardiología
│   └── ...
└── Paciente de Seguridad Privada
    ├── Paciente de Seguridad Privada de Traumatología
    ├── Paciente de Seguridad Privada de Cardiología
    └── ...
```

Cada **tipo de seguro** (público/privado) se combina con cada **especialidad** (traumatología/cardiología), generando una **explosión combinatoria** de clases.

---

## ❓ Por qué es un problema

- **Explosión de clases**: `n` tipos × `m` especialidades = `n × m` subclases.
- **Duplicación**: la lógica de una jerarquía se repite en la otra.
- **Acoplamiento oculto**: cambiar una jerarquía obliga a cambiar la otra.
- **Mantenimiento costoso**: añadir una especialidad exige tocar **todas** las ramas.
- Dificulta cumplir [[7. Principio No te repitas DRY|DRY]] y [[1. Principio de sustitucion de LISCOV|LSP]].

> [!tip] Idea clave
> El problema no es que existan dos jerarquías, sino que estén **acopladas**: cada subclase de una **exige** una subclase correspondiente en la otra.

---

## 🛠️ Solución: reestructurar la jerarquía

| Técnica | Qué hace |
|---------|----------|
| **Reubicar responsabilidades** | Mover el comportamiento común a la clase correcta |
| **Aplicar [[6. Patron metodo plantilla|Método Plantilla]]** | La clase base define el esqueleto; las derivadas implementan los pasos |
| **Composición con roles polimórficos** | Una clase contiene **tantos roles** como jerarquías paralelas y **delega** en ellos |

En lugar de heredar de dos ejes a la vez, la clase principal **tiene** un objeto de cada eje y **combina** su comportamiento.

### ✅ Rediseño del ejemplo

```
Paciente
├── tiene un Enfermo   (especialidad)
└── tiene un Seguro    (cobertura)

Enfermo
├── Enfermo de Traumatología
└── Enfermo de Cardiología

Seguro
├── Seguro Público
└── Seguro Privado
```

```java
public interface Enfermo {
    String getEspecialidad();
}

public class EnfermoTraumatologia implements Enfermo {
    @Override
    public String getEspecialidad() { return "Traumatología"; }
}

public class EnfermoCardiologia implements Enfermo {
    @Override
    public String getEspecialidad() { return "Cardiología"; }
}

public interface Seguro {
    double getCobertura();
}

public class SeguroPublico implements Seguro {
    @Override
    public double getCobertura() { return 1.0; }
}

public class SeguroPrivado implements Seguro {
    @Override
    public double getCobertura() { return 0.8; }
}

// ✅ Paciente combina los dos roles por composición
public class Paciente {
    private final Enfermo enfermo;
    private final Seguro seguro;

    public Paciente(Enfermo enfermo, Seguro seguro) {
        this.enfermo = enfermo;
        this.seguro = seguro;
    }

    public String descripcion() {
        return enfermo.getEspecialidad() + " con " + seguro.getCobertura();
    }
}
```

> [!success] Ventajas
> Añadir una especialidad nueva **no obliga** a crear clases para cada seguro. Se elimina la explosión combinatoria y el acoplamiento entre jerarquías.

## 🎮 Ejemplo del temario: controladores `Manual` / `Random`

La jerarquía original crece en paralelo:

```
ColocateController
├── ManualPutController
├── ManualMoveController
├── RandomPutController
└── RandomMoveController
```

Problemas detectados:

- **Jerarquías paralelas**: `Manual…` y `Random…` se replican para `Put` y `Move`.
- **[[7. Principio No te repitas DRY|DRY]]**: `selectOrigin` se repite en `ManualPutController` y `ManualMoveController`, y también en `RandomPutController` y `RandomMoveController`.
- **[[4. Codigo sucio por herencia rechazada|Herencia rechazada]]**: no se puede subir `selectOrigin` a un ancestro común sin que una rama rechace métodos.

### ✅ Solución: separar la responsabilidad de selección

Se extrae una jerarquía **independiente** para seleccionar coordenadas y se **inyecta** en los controladores:

```
CoordinateController
├── ManualCoordinateController
└── RandomCoordinateController

PutController  ──tiene──> CoordinateController
MoveController ──tiene──> CoordinateController
```

```java
public interface CoordinateController {
    Coordinate selectOrigin();
    Coordinate selectTarget();
}

public class ManualCoordinateController implements CoordinateController {
    @Override
    public Coordinate selectOrigin() { /* pide al usuario */ return null; }

    @Override
    public Coordinate selectTarget() { /* pide al usuario */ return null; }
}

public class RandomCoordinateController implements CoordinateController {
    @Override
    public Coordinate selectOrigin() { /* aleatorio */ return null; }

    @Override
    public Coordinate selectTarget() { /* aleatorio */ return null; }
}
```

```java
public abstract class ColocateController {
    protected final CoordinateController coordinateController;

    protected ColocateController(CoordinateController coordinateController) {
        this.coordinateController = coordinateController;
    }

    public abstract void colocate();
}

public class PutController extends ColocateController {
    public PutController(CoordinateController coordinateController) {
        super(coordinateController);
    }

    @Override
    public void colocate() {
        Coordinate destino = coordinateController.selectTarget();
        // poner ficha
    }
}

public class MoveController extends ColocateController {
    public MoveController(CoordinateController coordinateController) {
        super(coordinateController);
    }

    @Override
    public void colocate() {
        Coordinate origen  = coordinateController.selectOrigin();
        Coordinate destino = coordinateController.selectTarget();
        // mover ficha
    }
}
```

> [!note] Relación con otros conceptos
> La solución usa **[[3. Inversion de control|Inversión de control]]** e **[[4. Inyeccion de dependencias|Inyección de dependencias]]**: en el arranque (`StartController`) se decide qué `CoordinateController` se inyecta en `PutController` y `MoveController` según el número de jugadores.

---

## 🔍 Cómo detectarlo

- Al crear una subclase de una jerarquía, **sientes la obligación** de crear otra en una jerarquía distinta.
- Los **prefijos** de los nombres coinciden entre jerarquías (`Manual…`, `Random…`; `Seguro…`, `Paciente…`).
- **Explosión combinatoria** de clases: `n × m` subclases.
- Cambios que se repiten **en paralelo** en dos familias de clases.
- Métodos idénticos en ramas hermanas que no se pueden subir sin rechazar herencia.

---

## 🎯 Conclusión para examen

1. **Jerarquías paralelas de herencia** = dos jerarquías que crecen **acopladas**: cada subclase de una exige una subclase en la otra.
2. Es un caso especial de **[[7. Codigo sucio por cirugia a escopetazos|Cirugía a escopetazos]]** y provoca **explosión combinatoria** de clases.
3. **Solución:** reubicar responsabilidades, aplicar **[[6. Patron metodo plantilla|Método Plantilla]]** y usar **composición con roles polimórficos** (una clase contiene y delega en cada eje).
4. En el temario, se extrae `CoordinateController` (`Manual`/`Random`) y se **inyecta** en `PutController` y `MoveController`, rompiendo el paralelismo.

> [!question] Pregunta típica
> *"¿Qué son las jerarquías paralelas de herencia y cómo se eliminan?"*
> **Respuesta:** son dos jerarquías que crecen a la vez, de forma que crear una subclase en una obliga a crear otra en la segunda (p. ej. `ManualPut`/`ManualMove` y `RandomPut`/`RandomMove`). Se detectan por la explosión combinatoria y los prefijos comunes. Se eliminan reubicando responsabilidades y sustituyendo la herencia por **composición con roles polimórficos**, a menudo con **Método Plantilla** e **inyección de dependencias**.
