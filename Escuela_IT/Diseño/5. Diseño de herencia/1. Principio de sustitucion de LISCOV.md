# 1. Principio de sustitución de Liskov (LSP)

> [!info] Principio SOLID · Liskov Substitution Principle
> Formulado por **Barbara Liskov** (1987) y popularizado por **Robert C. Martin** como la **L** de SOLID.
> Relacionado con [[2. Relacion de herencia vs composicion|Herencia vs composición]], [[8. Diseño por contrato|Diseño por contrato]] y [[6. Patron metodo plantilla|Método Plantilla]].

---

## 📖 ¿Qué dice el principio?

> [!quote] Barbara Liskov (1987)
> «Si para cada objeto `o1` de un tipo `S` existe un objeto `o2` de tipo `T` tal que para todo programa `P` definido en términos de `T`, el comportamiento de `P` no cambia cuando `o1` sustituye a `o2`, entonces `S` es un subtipo de `T`.»

En palabras simples:

> [!tip] Idea clave
> **Un subtipo debe poder usarse en cualquier lugar donde se espera el tipo base, sin que el programa note la diferencia.**
> Las funciones que usan referencias a la clase base deben poder usar objetos de las clases derivadas **sin conocerlas**.

La herencia no es solo reutilizar código: es un **contrato de comportamiento**. Lo que importa no es el comportamiento privado interno, sino el **comportamiento público extrínseco** del que dependen los clientes.

---

## 🧠 Sustituibilidad: el ejemplo del pato de goma

Si una función recibe un `Ave` y espera que pueda `volar()`, entonces un `Pinguino` **no puede** ser un `Ave` si al volar lanza una excepción.

```java
public class Ave {
    public void volar() { /* ... */ }
}

public class Pinguino extends Ave {
    @Override
    public void volar() {
        throw new UnsupportedOperationException("Un pingüino no vuela");
    }
}
```

```java
// ❌ El cliente confía en el contrato de Ave y el programa falla
public void soltarTodas(List<Ave> aves) {
    for (Ave ave : aves) {
        ave.volar(); // ¡explota con un Pinguino!
    }
}
```

> [!warning] Conclusión
> Si una subclase **no puede cumplir** todo lo que promete la clase base, **no debe heredar de ella**. Esa jerarquía está mal diseñada.

---

## 📐 Reglas de contrato: precondiciones y postcondiciones

Una redefinición correcta en la clase derivada debe cumplir:

| Elemento | Regla | Efecto |
|----------|-------|--------|
| **Precondición** | Se **debilita** (o se mantiene) | El subtipo acepta **al menos** los mismos casos que el padre |
| **Postcondición** | Se **refuerza** (o se mantiene) | El subtipo garantiza **al menos** lo mismo que el padre |

Formalmente:

- La precondición del subtipo se combina con la del padre usando **OR** → menos restrictiva.
- La postcondición del subtipo se combina con la del padre usando **AND** → más restrictiva.

```java
public class Cuenta {
    protected double saldo;

    // pre:  cantidad > 0
    // post: saldo == old(saldo) - cantidad
    public void retirar(double cantidad) {
        saldo -= cantidad;
    }
}
```

```java
// ❌ Viola LSP: refuerza la precondición (exige más que el padre)
public class CuentaPremium extends Cuenta {
    @Override
    public void retirar(double cantidad) {
        if (cantidad < 100) {
            throw new IllegalArgumentException("Mínimo 100");
        }
        saldo -= cantidad;
    }
}
```

```java
// ✅ Cumple LSP: debilita la precondición (acepta más casos)
public class CuentaJoven extends Cuenta {
    @Override
    public void retirar(double cantidad) {
        if (cantidad <= 0) {
            throw new IllegalArgumentException("Cantidad positiva");
        }
        saldo -= cantidad;
    }
}
```

> [!note] Regla mental
> El subtipo puede **pedir menos** y **prometer más**. Nunca al revés.

## ❌ Violación clásica: `Cuadrado extends Rectangulo`

```java
public class Rectangulo {
    protected int ancho;
    protected int alto;

    public void setAncho(int ancho) { this.ancho = ancho; }
    public void setAlto(int alto)   { this.alto = alto; }
    public int area()               { return ancho * alto; }
}

public class Cuadrado extends Rectangulo {
    @Override
    public void setAncho(int ancho) {
        this.ancho = ancho;
        this.alto = ancho; // mantiene la invariante del cuadrado
    }

    @Override
    public void setAlto(int alto) {
        this.ancho = alto;
        this.alto = alto;
    }
}
```

El cliente de `Rectangulo` asume que **ancho y alto son independientes**:

```java
public void comprobar(Rectangulo r) {
    r.setAncho(5);
    r.setAlto(4);
    assert r.area() == 20; // ✅ con Rectangulo, ❌ con Cuadrado (area == 16)
}
```

> [!danger] Por qué falla
> `Cuadrado` cambia el comportamiento esperado: modificar el ancho **repercute en el alto**. Incumple la asunción razonable del cliente, aunque matemáticamente “un cuadrado sea un rectángulo”.

### ✅ Soluciones

| Solución | Idea |
|----------|------|
| **Jerarquías separadas** | `Rectangulo` y `Cuadrado` no heredan entre sí; ambas implementan una interfaz `Figura` con `area()` |
| **Objetos inmutables** | Sin `setAncho`/`setAlto` no hay forma de romper la invariante |
| **Composición** | `Cuadrado` **tiene** un `Rectangulo` (o un `Lado`) y delega |

```java
public interface Figura {
    int area();
}

public class Rectangulo implements Figura {
    private final int ancho;
    private final int alto;

    public Rectangulo(int ancho, int alto) {
        this.ancho = ancho;
        this.alto = alto;
    }

    @Override
    public int area() { return ancho * alto; }
}

public class Cuadrado implements Figura {
    private final int lado;

    public Cuadrado(int lado) { this.lado = lado; }

    @Override
    public int area() { return lado * lado; }
}
```

## 🚫 Otra violación: usar RTTI (`instanceof`)

Preguntar por el **tipo en tiempo de ejecución** para decidir qué hacer es una señal de que la abstracción no está bien hecha.

```java
// ❌ El cliente conoce las clases derivadas y las trata distinto
public void mover(Ave ave) {
    if (ave instanceof Pinguino) {
        ((Pinguino) ave).nadar();
    } else if (ave instanceof Aguila) {
        ((Aguila) ave).volar();
    } else {
        ave.volar();
    }
}
```

> [!danger] Por qué es grave
> Cada nueva subclase obliga a **modificar todos los `instanceof`** del sistema. Se rompe [[6. Principio abierto - cerrado|Open/Closed]] y aparece el smell [[7. Codigo sucio por cirugia a escopetazos|Cirugía a escopetazos]].
> Solución: **polimorfismo** (método `moverse()` redefinido en cada subclase) o [[7. Tecnica del doble despacho|doble despacho]] cuando el comportamiento depende de dos tipos.

## 🎮 Ejemplo del temario: `TicTacToeCoordinate`

En el Tres en Raya, `Coordinate` representa una coordenada del **tablero infinito** (valores `[0, ∞)`). La tentación es hacer:

```java
// ❌ Refuerza la precondición: solo admite [0, 2]
public class TicTacToeCoordinate extends Coordinate {
    public TicTacToeCoordinate(int fila, int columna) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
            throw new IllegalArgumentException("Fuera del tablero 3x3");
        }
        super(fila, columna);
    }
}
```

Un cliente que use `Coordinate` con `fila = 5` funciona; con `TicTacToeCoordinate` **falla**. Se ha reforzado la precondición → **violación de LSP**.

> [!success] Solución del temario
> **Relación de composición + delegación**: `TicTacToeCoordinate` **tiene** una `Coordinate` y delega en ella, en lugar de heredar. Ver [[2. Relacion de herencia vs composicion|Herencia vs composición]].

## ✅ Checklist para cumplir LSP

- [ ] ¿La subclase acepta **todos** los valores que acepta el padre? (precondición no reforzada)
- [ ] ¿La subclase garantiza **todo** lo que garantiza el padre? (postcondición no debilitada)
- [ ] ¿Respeta las **invariantes** y el significado de los métodos heredados?
- [ ] ¿Evita lanzar excepciones nuevas o no documentadas en métodos heredados?
- [ ] ¿Evita los `instanceof` / RTTI para distinguir subtipos?
- [ ] ¿Un cliente escrito solo con la clase base sigue funcionando con cualquier derivada?

> [!tip] Prueba de fuego
> Escribe el cliente **usando solo el tipo base**. Si al pasarle una derivada el resultado cambia o falla, no se cumple LSP.

---

## 🎯 Conclusión para examen

1. **LSP** = los objetos de una subclase deben poder **sustituir** a los de la superclase **sin alterar el comportamiento** del programa.
2. La herencia es un **contrato de comportamiento público**, no solo reutilización de código.
3. Regla de contrato: **precondiciones más débiles** (OR) y **postcondiciones más fuertes** (AND).
4. Violaciones típicas: **`Cuadrado extends Rectangulo`**, usar **`instanceof`/RTTI** y **reforzar precondiciones** en la derivada (ej. `TicTacToeCoordinate`).
5. Si no se puede cumplir el contrato: **no heredes**; usa **composición**, **delegación** o **interfaces**.

> [!question] Pregunta típica
> *"¿Qué es el Principio de Sustitución de Liskov y pon un ejemplo de violación?"*
> **Respuesta:** un subtipo debe poder sustituir a su tipo base sin que el cliente note diferencias. Se viola, por ejemplo, con `Cuadrado extends Rectangulo`: el cliente espera que ancho y alto sean independientes y el cuadrado los acopla. También se viola usando `instanceof` para tratar distinto a cada subtipo o reforzando precondiciones en la clase derivada. La solución es rediseñar con composición, delegación o interfaces comunes.
