# 6. Patrón Método Plantilla

> [!info] Patrón de diseño · Template Method
> *Design Patterns* — Gamma, Helm, Johnson y Vlissides (GoF). Patrón de **comportamiento**.
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]], [[6. Principio abierto - cerrado|Open/Closed]] y [[4. Codigo sucio por herencia rechazada|Herencia rechazada]].

## 📖 ¿Qué es?

> [!quote] GoF
> «Define el esqueleto de un algoritmo en una operación, difiriendo algunos pasos a las subclases. Permite que las subclases redefinan ciertos pasos de un algoritmo **sin cambiar su estructura**.»

Es decir: la **clase base** controla el **orden** de los pasos y las **subclases** implementan los detalles variables.

> [!tip] Idea clave
> **Estructura fija en el padre, detalles variables en las hijas.**
> El padre manda (*«no nos llames, ya te llamaremos»*), las hijas solo rellenan los huecos.

---

## 🧩 Estructura

```java
public abstract class Plantilla {

    // El "método plantilla": final para que nadie cambie el orden
    public final void algoritmo() {
        pasoComun();
        pasoAbstracto1();
        pasoAbstracto2();
        pasoOpcional();   // hook: las subclases pueden redefinirlo
    }

    // Paso común: lo implementa el padre
    private void pasoComun() { /* ... */ }

    // Pasos variables: obligatorios para las subclases
    protected abstract void pasoAbstracto1();
    protected abstract void pasoAbstracto2();

    // Hook: implementación por defecto vacía, la subclase decide
    protected void pasoOpcional() { /* por defecto no hace nada */ }
}
```

| Elemento | Papel |
|----------|-------|
| **Método plantilla** | Define el esqueleto y el **orden**; suele ser `final` |
| **Métodos abstractos** | Pasos **obligatorios** que implementan las subclases |
| **Métodos concretos** | Pasos **comunes** que ya implementa el padre |
| **Hooks** | Pasos **opcionales** con implementación por defecto vacía |

## 🍵 Ejemplo: preparar una bebida

```java
public abstract class Bebida {

    // ✅ Algoritmo común e invariable
    public final void preparar() {
        hervirAgua();
        prepararBebida();
        verterEnTaza();
        if (clienteQuiereCondimento()) {
            agregarCondimento();
        }
    }

    private void hervirAgua()    { System.out.println("Hirviendo agua"); }
    private void verterEnTaza()  { System.out.println("Vertiendo en la taza"); }

    // Pasos variables
    protected abstract void prepararBebida();
    protected abstract void agregarCondimento();

    // Hook: la subclase puede cambiar la condición
    protected boolean clienteQuiereCondimento() { return true; }
}

public class Cafe extends Bebida {
    @Override
    protected void prepararBebida()     { System.out.println("Colando café"); }

    @Override
    protected void agregarCondimento()  { System.out.println("Añadiendo azúcar y leche"); }
}

public class Te extends Bebida {
    @Override
    protected void prepararBebida()     { System.out.println("Infusionando té"); }

    @Override
    protected void agregarCondimento()  { System.out.println("Añadiendo limón"); }

    @Override
    protected boolean clienteQuiereCondimento() { return false; }
}
```

```java
Bebida bebida = new Cafe();
bebida.preparar(); // El orden lo decide Bebida; los detalles, Cafe
```

> [!success] Resultado
> El **esqueleto** (`preparar`) está en un único sitio y **no se duplica**; cada bebida solo aporta sus pasos específicos.

## 🎮 Ejemplo del temario: `ColocateController`

`PutController` y `MoveController` comparten el **mismo esquema** de colocación, pero cambian los pasos concretos:

```java
public abstract class ColocateController {
    protected final CoordinateController coordinateController;

    protected ColocateController(CoordinateController coordinateController) {
        this.coordinateController = coordinateController;
    }

    // ✅ Método plantilla: estructura común
    public final void colocate() {
        Coordinate origen  = coordinateController.selectOrigin();
        Coordinate destino = coordinateController.selectTarget();
        validate(origen, destino);
        executeColocate(origen, destino);
        updateView();
    }

    protected abstract void executeColocate(Coordinate origen, Coordinate destino);
    protected abstract void updateView();

    private void validate(Coordinate origen, Coordinate destino) {
        // validación común a poner y mover
    }
}

public class PutController extends ColocateController {
    public PutController(CoordinateController coordinateController) {
        super(coordinateController);
    }

    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // poner ficha en el destino
    }

    @Override
    protected void updateView() { /* actualizar tablero */ }
}

public class MoveController extends ColocateController {
    public MoveController(CoordinateController coordinateController) {
        super(coordinateController);
    }

    @Override
    protected void executeColocate(Coordinate origen, Coordinate destino) {
        // quitar ficha del origen y poner en el destino
    }

    @Override
    protected void updateView() { /* actualizar tablero */ }
}
```

> [!note] Relación con el temario
> El Método Plantilla se usa para resolver [[4. Codigo sucio por herencia rechazada|herencia rechazada]] y [[4. Codigo sucio por clases alternativas con interfaces diferentes|clases alternativas con interfaces diferentes]]: se **homogeneíza** la interfaz (`colocate`) y se deja que cada controlador implemente sus pasos.

## 🎬 Principio de Hollywood

> [!quote] «Don't call us, we'll call you»
> La clase base **llama** a los métodos de las subclases; las subclases **no** llaman al algoritmo del padre para controlar el flujo. Esto invierte el control y protege la estructura del algoritmo.

---

## ⚖️ Ventajas y desventajas

| Ventajas | Desventajas |
|----------|-------------|
| Elimina **código duplicado** en el esqueleto | La herencia **acopla** las subclases al padre |
| Centraliza el **orden** y las invariantes del algoritmo | Cambiar el esqueleto afecta a **todas** las subclases |
| Facilita **extender** pasos sin tocar al cliente | Muchos pasos abstractos → jerarquía **rígida** |
| Aplica **[[6. Principio abierto - cerrado|Open/Closed]]** | Puede violar [[1. Principio de sustitucion de LISCOV|LSP]] si las subclases no respetan los hooks |

> [!warning] Cuándo NO usarlo
> Si el número de variantes es pequeño o los pasos cambian mucho, la **composición** o la **estrategia** puede ser más flexible que la herencia.

---

## 🎯 Conclusión para examen

1. **Método Plantilla** define el **esqueleto** de un algoritmo y **difiere pasos** a las subclases.
2. El **método plantilla** controla el orden (normalmente `final`); las subclases implementan **métodos abstractos** y pueden redefinir **hooks**.
3. Evita duplicar la estructura del algoritmo y facilita la extensión (**[[6. Principio abierto - cerrado|Open/Closed]]**).
4. Se apoya en la **herencia**, por lo que hay que vigilar [[1. Principio de sustitucion de LISCOV|LSP]].
5. En el temario se aplica a `ColocateController` (`PutController` / `MoveController`) y a la preparación de bebidas como ejemplo canónico.

> [!question] Pregunta típica
> *"Explica el patrón Método Plantilla con un ejemplo."*
> **Respuesta:** consiste en definir en una clase base el esqueleto de un algoritmo (el método plantilla, a menudo `final`), dejando pasos abstractos y hooks que las subclases implementan. Así se comparte la estructura y se varían los detalles. Ejemplo: `Bebida.preparar()` fija hervir agua, preparar, verter y condimentar; `Cafe` y `Te` implementan `prepararBebida()` y `agregarCondimento()`. En el temario, `ColocateController.colocate()` fija el esquema y `PutController`/`MoveController` implementan `executeColocate()`.
