# 2. Relación de herencia vs composición

> [!info] Herencia («es un») frente a composición («tiene un»)
> Dos formas de relacionar clases. Elegir mal genera acoplamiento, violaciones de [[1. Principio de sustitucion de LISCOV|LSP]] y jerarquías rígidas.
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]], [[4. Codigo sucio por herencia rechazada|Herencia rechazada]] y [[5. Codigo sucio por jerarquias  paralelas de herencia|Jerarquías paralelas]].

---

## 📖 ¿Qué significa cada relación?

| Relación | Pregunta | Verbo | Ejemplo |
|----------|----------|-------|---------|
| **Herencia** | ¿A **es un** B? | `extends` / `implements` | `Perro` **es un** `Animal` |
| **Composición** | ¿A **tiene un** B? | atributo + delegación | `Coche` **tiene un** `Motor` |

> [!tip] Idea clave
> La **composición** es la opción por defecto; la **herencia** se reserva para relaciones **«es un» reales y estables** en las que el subtipo **cumple el contrato** del padre.

---

## ⚠️ El problema: «tener» no es siempre «ser»

- Un **propietario de un coche es una persona**, pero **no es un coche**; **tiene** un coche.
- Un **ingeniero de software es un ingeniero**: en cada ingeniero de software **hay** un ingeniero. Aquí «ser» también implica «tener», y la herencia puede tener sentido.

> [!warning] Trampa habitual
> Que dos conceptos compartan datos o comportamiento **no** significa que uno sea un subtipo del otro. Si dudas, probablemente sea **composición**.

---

## 🧭 Cuándo elegir cada una

### ❌ Casos que suelen pedir composición

- El objeto compuesto puede **cambiar de “parte” en tiempo de ejecución** (regla de cambio).
- Solo quieres **reutilizar código**, no modelar un subtipo real.
- La subclase **no puede cumplir** todo el contrato del padre (rompería LSP).
- La jerarquía crece por **combinaciones** (jerarquías paralelas).
- El “es un” es discutible o depende del contexto.

### ✅ Casos en los que la herencia encaja

- Existe un **«es un»** claro y estable.
- El subtipo **respeta el contrato** (precondiciones/postcondiciones) del padre.
- Se necesita **polimorfismo** sobre una abstracción común.
- El comportamiento especializado **no cambia de tipo** en tiempo de ejecución.

---

## 🔄 Reglas del temario

| Regla | Qué dice |
|-------|----------|
| **Incumplimiento de LSP** | Si la derivada no es sustituible por la base, no uses herencia |
| **Regla de cambio** | No uses herencia para un «es un» si el objeto compuesto puede **cambiar en tiempo de ejecución**: la composición lo permite, la herencia no |
| **Reglas de polimorfismo** | La herencia es apropiada para un «es un» si una entidad del tipo general puede quedar **enlazada** a objetos del tipo especializado |

> [!note] Recuerda
> **Siempre** que analizas una relación de herencia puedes plantearte su **contrapartida en composición**. Es una buena revisión de diseño.

---

## 🛠️ Solución: delegación

La **delegación** sustituye a la herencia: en lugar de heredar comportamiento, el objeto **contiene** al antiguo padre y **le reenvía** las llamadas.

- Dos objetos intervienen en una petición: uno la **recibe** y **delega** en su delegado.
- La **clase padre** actúa como **parte delegada**.
- La **clase hija** actúa como el **todo**.

| Método en la jerarquía original | Qué se hace al delegar |
|---------------------------------|------------------------|
| **Método transmitido** (no redefinido) | Se delega **íntegro** al delegado, con la misma cabecera |
| **Método redefinido** | Se codifica en el «todo» y delega en el padre **solo si necesita reutilizarlo** |
| **Método abstracto** | **No** se implementa en el delegado; lo implementa el «todo» |

---

## 🔧 Ejemplo: de herencia a composición

### ❌ Antes: herencia que viola LSP

```java
public class Coordinate {
    protected int fila;
    protected int columna;

    public Coordinate(int fila, int columna) {
        this.fila = fila;
        this.columna = columna;
    }

    public int getFila()   { return fila; }
    public int getColumna(){ return columna; }
}

// El tablero 3x3 solo admite [0, 2]: refuerza la precondición
public class TicTacToeCoordinate extends Coordinate {
    public TicTacToeCoordinate(int fila, int columna) {
        super(validar(fila), validar(columna));
    }

    private static int validar(int valor) {
        if (valor < 0 || valor > 2) {
            throw new IllegalArgumentException("Fuera del tablero 3x3");
        }
        return valor;
    }
}
```

### ✅ Después: composición + delegación

```java
public class TicTacToeCoordinate {
    private final Coordinate coordinate; // «tiene una» Coordinate

    public TicTacToeCoordinate(int fila, int columna) {
        if (fila < 0 || fila > 2 || columna < 0 || columna > 2) {
            throw new IllegalArgumentException("Fuera del tablero 3x3");
        }
        this.coordinate = new Coordinate(fila, columna);
    }

    // Delegación de los métodos transmitidos
    public int getFila()    { return coordinate.getFila(); }
    public int getColumna() { return coordinate.getColumna(); }
}
```

> [!success] Ventajas
> `Coordinate` sigue admitiendo cualquier valor; `TicTacToeCoordinate` **valida solo su propio caso** y **no rompe** el contrato de `Coordinate` porque ya no es su subtipo.

## 🧩 Ejemplo cotidiano: `Coche` y `Motor`

```java
// ✅ Composición: un coche TIENE un motor
public class Motor {
    private int caballos;

    public Motor(int caballos) { this.caballos = caballos; }
    public int getCaballos()   { return caballos; }
}

public class Coche {
    private Motor motor; // se puede cambiar en tiempo de ejecución

    public Coche(Motor motor) { this.motor = motor; }

    public void cambiarMotor(Motor nuevo) { this.motor = nuevo; }
    public int potencia()                 { return motor.getCaballos(); }
}
```

```java
// ❌ Herencia absurda: un coche no ES un motor
public class Coche extends Motor { /* ... */ }
```

## 🔌 Mantener el polimorfismo con interfaces

Si al eliminar la herencia se pierde un **polimorfismo necesario**, se puede **heredar de interfaces** comunes: las interfaces habilitan el polimorfismo sin arrastrar implementación.

```java
public interface Repositorio {
    void guardar(String clave, String valor);
    String buscar(String clave);
}

public class RepositorioMemoria implements Repositorio {
    private final Map<String, String> datos = new HashMap<>();

    @Override
    public void guardar(String clave, String valor) { datos.put(clave, valor); }

    @Override
    public String buscar(String clave) { return datos.get(clave); }
}

public class RepositorioFichero implements Repositorio {
    @Override
    public void guardar(String clave, String valor) { /* ... */ }

    @Override
    public String buscar(String clave) { /* ... */ }
}
```

> [!tip] Regla práctica
> **Implementa interfaces** (contratos) y **compón** implementaciones. La herencia de **clase** se usa solo cuando hay un «es un» real con contrato respetado.

---

## ⚖️ Comparativa rápida

| Criterio | Herencia | Composición |
|----------|----------|-------------|
| Relación | «es un» | «tiene un» |
| Acoplamiento | **Fuerte** (depende de la implementación del padre) | **Débil** (depende de la interfaz del componente) |
| Cambio en tiempo de ejecución | ❌ No | ✅ Sí |
| Reutilización | Cómoda, pero expone toda la interfaz del padre | Selectiva (solo lo que se delega) |
| Encapsulación | Rompe encapsulación (`protected`) | La conserva |
| Complejidad | Jerarquías profundas y frágiles | Objetos pequeños y combinables |
| Riesgo principal | Violar LSP, herencia rechazada, jerarquías paralelas | Más código de delegación |

> [!quote] Gamma et al. (*Design Patterns*)
> «Favorece la composición de objetos frente a la herencia de clases.»

---

## 🎯 Conclusión para examen

1. **Herencia = «es un»**; **composición = «tiene un»**.
2. La composición es más **flexible**: permite cambiar la parte en tiempo de ejecución y **no rompe encapsulación**.
3. La herencia exige **cumplir el contrato** del padre ([[1. Principio de sustitucion de LISCOV|LSP]]); si no, usa composición.
4. **Delegación**: el objeto «todo» contiene al «delegado» y le reenvía los métodos transmitidos.
5. Para conservar **polimorfismo** sin herencia de clase, usa **interfaces**.
6. En el temario, `TicTacToeCoordinate` pasa de heredar de `Coordinate` a **componerla y delegar**.

> [!question] Pregunta típica
> *"¿Cuándo usarías composición en lugar de herencia? ¿Qué es la delegación?"*
> **Respuesta:** usaría composición cuando la relación no sea un «es un» real, cuando la parte pueda cambiar en tiempo de ejecución, cuando la subclase no pueda cumplir el contrato del padre o cuando solo quiera reutilizar código. La delegación consiste en que el objeto que recibe la petición la reenvía a un objeto contenido (el delegado): los métodos transmitidos se delegan íntegros, los redefinidos se implementan en el «todo» y los abstractos no se implantan en el delegado.
