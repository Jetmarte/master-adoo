# 2. Principio del menor compromiso y mínima sorpresa

> [!info] Dos principios complementarios
> - **Menor compromiso** (Abelson y Sussman): la interfaz de un objeto proporciona su **comportamiento esencial, y nada más**.
> - **Mínima sorpresa** (Booch): una abstracción captura **todo el comportamiento de un objeto, ni más ni menos**, y no ofrece sorpresas ni efectos secundarios que vayan más allá del ámbito de la abstracción.

---

## 🏷️ Sinónimos y antónimos

| Tipo | Término | Fuente |
|------|---------|--------|
| Sinónimo | **Los nombres de las funciones deberían decir lo que hacen** (*Function Names Should Say What They Do*) | *Clean Code* (Code Smells) — Robert C. Martin |
| Sinónimo | **Principio de la mínima sorpresa** (*Principle of Least Astonishment*) | Literatura de diseño de interfaces |
| Antónimo (smell) | **Comportamiento obvio no implementado** (*Obvious Behavior Is Unimplemented*) | *Clean Code* (Code Smells) — Robert C. Martin |
| Antónimo (smell) | **Responsabilidad fuera de lugar** (*Misplaced Responsibility*) | *Clean Code* (Code Smells) — Robert C. Martin |

---

## 📖 Las dos caras del principio

| Principio | Pregunta clave | Si se viola… |
|-----------|----------------|--------------|
| **Menor compromiso** | ¿La interfaz promete **solo lo esencial**? | El cliente queda atado a detalles internos o a decisiones que no necesita |
| **Mínima sorpresa** | ¿El objeto hace **exactamente** lo que su nombre y su contrato prometen? | El cliente se lleva sorpresas, efectos colaterales o comportamientos “ocultos” |

> [!tip] Idea clave
> La interfaz debe ser **pequeña y honesta**: ni promete de más (menor compromiso) ni hace menos —o distinto— de lo que promete (mínima sorpresa).

---

## 1️⃣ Principio del menor compromiso

### 📖 Definición

La interfaz de un objeto debe proporcionar su **comportamiento esencial, y nada más**. No debe obligar al cliente a conocer ni a depender de la **representación interna** ni de decisiones de implementación que no le corresponden.

> [!note] Otra acepción habitual: decisión tardía
> En metodologías ágiles, *least commitment* también se usa para **posponer decisiones** (base de datos, tecnología, formato) hasta tener información suficiente. Es compatible con la definición anterior: no te comprometes ni con detalles internos ni con decisiones prematuras.

### 🧩 Ejemplo: no exponer la representación

```java
// ❌ La interfaz expone más de lo esencial
public class Pila<T> {
    private final List<T> elementos = new ArrayList<>();

    public List<T> getElementos() {        // el cliente depende de la representación
        return elementos;
    }

    public void apilar(T elemento) {
        elementos.add(elemento);
    }

    public T desapilar() {
        return elementos.remove(elementos.size() - 1);
    }
}
```

Problemas:

- El cliente puede hacer `pila.getElementos().clear()`, `add(0, ...)`, etc. → **rompe la abstracción**.
- Si mañana la pila se implementa con un array o una lista enlazada, el cliente deja de compilar.

```java
// ✅ La interfaz ofrece solo lo esencial
public interface Pila<T> {
    void apilar(T elemento);
    T desapilar();
    T cima();
    boolean estaVacia();
}
```

El cliente solo puede usar la pila **como una pila**. La implementación queda libre para cambiar.

### 🧩 Ejemplo: no comprometerse con una tecnología

```java
// ❌ Compromiso temprano con MySQL
public class RepositorioClientes {
    private Connection conexionMySQL;

    public RepositorioClientes() {
        this.conexionMySQL = DriverManager.getConnection("jdbc:mysql://...");
    }

    public void guardar(Cliente cliente) { /* SQL específico */ }
}
```

```java
// ✅ El cliente depende de una abstracción, no de MySQL
public interface RepositorioClientes {
    void guardar(Cliente cliente);
    Optional<Cliente> buscarPorId(int id);
}

public class RepositorioClientesMySQL implements RepositorioClientes { /* ... */ }
public class RepositorioClientesMongo implements RepositorioClientes { /* ... */ }
```

> [!tip] Resultado
> No me comprometo con la base de datos desde el principio: puedo cambiar la implementación sin tocar a los clientes. Relacionado con [[5. Principio de inversion de dependencias|DIP]] e [[4. Inyeccion de dependencias|inyección de dependencias]].

### 🔍 Cómo detectarlo

- Getters que devuelven **colecciones o estructuras internas**.
- Métodos `setX` para **todos** los atributos: el cliente decide las invariantes del objeto.
- Constructores que reciben **clases concretas** en lugar de interfaces.
- Parámetros con **banderas o formatos** que obligan a una implementación concreta.
- Métodos “extra” que solo necesita un cliente particular.

## 2️⃣ Principio de mínima sorpresa

### 📖 Definición

El sistema debe comportarse de la forma **más natural y esperada** para quien lo usa. Una abstracción:

- captura **todo** el comportamiento que promete, **ni más ni menos**;
- **no** produce efectos secundarios fuera de su ámbito;
- tiene nombres **consistentes** con lo que hace;
- mantiene convenciones estables en toda la API.

> [!warning] Señal de alarma
> Si el nombre del método no coincide con lo que realmente hace, o si un método “inocente” provoca efectos colaterales, el diseño viola la mínima sorpresa.

### 🧩 Ejemplo 1: nombres que no sorprenden

```java
List<String> lista = new ArrayList<>(List.of("A", "B", "C"));

System.out.println(lista.size());   // ✅ 3: lo esperado
System.out.println(lista.length()); // ❌ no existe: en Java es size()
```

En Java, `String.length()` y `List.size()` son convenciones distintas pero **estables**. Lo sorprendente sería que una `List` tuviera `length()` en un sitio y `size()` en otro.

### 🧩 Ejemplo 2: un método que hace más de lo que dice

```java
// ❌ guardar() también envía un correo y limpia la caché
public void guardar(Pedido pedido) {
    baseDeDatos.save(pedido);
    emailService.enviarConfirmacion(pedido); // efecto secundario inesperado
    cache.clear();                            // efecto secundario inesperado
}
```

```java
// ✅ cada método dice exactamente lo que hace
public void guardar(Pedido pedido) {
    baseDeDatos.save(pedido);
}

public void confirmar(Pedido pedido) {
    emailService.enviarConfirmacion(pedido);
}
```

Quien llama a `guardar` espera **guardar**, no enviar correos ni vaciar cachés.

### 🧩 Ejemplo 3: “Eliminar” que en realidad desactiva

```java
// ❌ El botón “Eliminar” no elimina: desactiva sin avisar
public void eliminar(Usuario usuario) {
    usuario.setActivo(false);
}
```

```java
// ✅ O se elimina de verdad, o el nombre lo dice
public void desactivar(Usuario usuario) {
    usuario.setActivo(false);
}
```

### 🧩 Ejemplo 4: comportamiento obvio no implementado

```java
// ❌ Se puede crear un pedido, pero no cancelarlo ni consultar su estado
public class Pedido {
    public void crear() { /* ... */ }
    public void agregarProducto(Producto producto) { /* ... */ }
}
```

Si el dominio exige cancelar un pedido, la **ausencia** de `cancelar()` también sorprende al cliente: es el smell *Obvious Behavior Is Unimplemented*.

### 🧩 Ejemplo 5: responsabilidad fuera de lugar

```java
// ❌ Cliente calcula el total del pedido (responsabilidad del Pedido)
public class Cliente {
    public double calcularTotal(Pedido pedido) {
        return pedido.getProductos().stream()
                     .mapToDouble(Producto::getPrecio)
                     .sum();
    }
}
```

```java
// ✅ El Pedido es quien conoce sus productos y su cálculo
public class Pedido {
    public double calcularTotal() {
        return productos.stream()
                        .mapToDouble(Producto::getPrecio)
                        .sum();
    }
}
```

Esto es *Misplaced Responsibility* y, además, un caso de [[7. Codigo sucio por envidia de caracteristicas|envidia de características]].

### 🔍 Cómo detectarlo

- Nombres **mentirosos**: `guardar` que también envía correos, `get...` que modifica estado.
- Comentarios que **explican** un comportamiento raro (`// ojo: esto además borra...`).
- Métodos con **efectos secundarios** no reflejados en el nombre.
- Nombres **inconsistentes** entre clases parecidas (`size`, `length`, `count`).
- **Comportamiento obvio ausente**: si todo el mundo espera `cancelar()`, debe existir.
- Lógica de una clase **dentro de otra** que no es la dueña de los datos.

## ⚖️ Relación entre ambos principios

| Menor compromiso | Mínima sorpresa |
|------------------|-----------------|
| **No prometer de más** | **Cumplir exactamente lo prometido** |
| Interfaz mínima y sin filtrar la representación | Comportamiento predecible, sin efectos ocultos |
| Se viola exponiendo detalles internos | Se viola haciendo algo distinto de lo que sugiere el nombre |

> [!important] Son dimensiones distintas
> Una interfaz puede ser **pequeña y aun así sorprender** (un único `guardar` que borra la caché), o ser **grande y no sorprender** (una API amplia pero coherente). Una buena interfaz cumple **las dos**.

---

## 🎯 Conclusión para examen

1. **Menor compromiso**: la interfaz ofrece el comportamiento esencial y nada más; no ata al cliente a la representación ni a decisiones internas.
2. **Mínima sorpresa**: la abstracción hace exactamente lo que promete, sin efectos secundarios fuera de su ámbito y con nombres coherentes.
3. **Menor compromiso** evita el exceso de interfaz; **mínima sorpresa** evita el comportamiento inesperado.
4. Se detectan con nombres mentirosos, getters que exponen la representación, efectos colaterales ocultos y responsabilidades mal ubicadas.
5. Se relacionan con **Clean Code** (*Function Names Should Say What They Do*, *Obvious Behavior Is Unimplemented*, *Misplaced Responsibility*).

> [!question] Pregunta típica
> *"¿Qué es el principio de mínima sorpresa y cómo se aplica?"*
> **Respuesta:** una abstracción debe capturar todo el comportamiento de un objeto, ni más ni menos, sin sorpresas ni efectos secundarios fuera de su ámbito. Se aplica con **nombres que digan lo que hacen** (un `guardar` no debe enviar correos), evitando efectos ocultos, manteniendo convenciones consistentes e implementando el comportamiento obvio del dominio. Ej.: `List.size()` en lugar de un `length()` inexistente; separar `guardar` de `confirmar`.
