# 5. Código sucio por listas de parámetros largas

> [!info] Code smell · Long Parameter List
> *Refactoring* (Code Smells) — Martin Fowler · *Too Many Arguments* — *Clean Code*, Robert C. Martin.
> Relacionado con [[4. Codigo sucio por grupos de datos|Grupos de datos]] y [[3. Codigo sucio por obsecion de tipos primitivos|Obsesión por los tipos primitivos]].

---

## 📖 ¿Qué es?

Un método tiene una **lista de parámetros larga** cuando recibe **demasiados argumentos**, especialmente si muchos son del mismo tipo o si varios de ellos **siempre viajan juntos**.

```java
// ❌ Firma difícil de leer y de usar correctamente
public void crearPedido(String nombreCliente,
                        String emailCliente,
                        String calle,
                        String ciudad,
                        String codigoPostal,
                        String producto,
                        int cantidad,
                        double precio,
                        boolean urgente) {
    // ...
}
```

### 🧩 El problema en la llamada

```java
crearPedido("Ana", "ana@mail.com", "Mayor 10", "Madrid",
            "28001", "Teclado", 2, 49.99, true);
```

- ¿Qué significa `true`? ¿Urgente? ¿Pagado? ¿Enviar correo?
- ¿El orden es `calle, ciudad, cp` o `calle, cp, ciudad`?
- Si mañana hay que añadir un campo, **todos los clientes** cambian.

---

## ❓ Por qué es un problema (justificación)

- Son **difíciles de entender**: hay que recordar el significado y el orden de cada parámetro.
- Son **difíciles de probar**: el número de combinaciones de argumentos crece muchísimo.
- Favorecen **errores de orden**: dos `String` seguidos pueden intercambiarse y el compilador no avisa.
- **Banderas booleanas** (`true`, `false`) hacen la llamada ilegible (*boolean trap*).
- **Duplican datos** que ya están en algún objeto.
- Dificultan la **evolución**: añadir un parámetro obliga a tocar todas las llamadas.

> [!tip] Idea clave
> Si varios parámetros **siempre van juntos**, probablemente forman un **concepto** que merece su propio objeto.

---

## 🧩 Ejemplo: parámetros que siempre viajan juntos

```java
// ❌ Datos de envío sueltos por todas partes
public void enviarPedido(String calle, String ciudad, String codigoPostal, String pais,
                         String producto, int cantidad) {
    // ...
}
```

```java
// ✅ El envío es un concepto con su propia clase
public final class DireccionEnvio {
    private final String calle;
    private final String ciudad;
    private final String codigoPostal;
    private final String pais;

    public DireccionEnvio(String calle, String ciudad, String codigoPostal, String pais) {
        this.calle = calle;
        this.ciudad = ciudad;
        this.codigoPostal = codigoPostal;
        this.pais = pais;
    }

    // getters...
}

public void enviarPedido(DireccionEnvio direccion, String producto, int cantidad) {
    // ...
}
```

La firma pasa de **6 parámetros** a **3**, y además `DireccionEnvio` puede validar el código postal, el país, etc.

---

## ✅ Solución

| Técnica | Qué hace | Cuándo usarla |
|---------|----------|---------------|
| **Replace Parameter with Method Call** | Elimina un parámetro que el método puede obtener por sí mismo de otro objeto | El valor ya está accesible desde el receptor o desde otro parámetro |
| **Preserve Whole Object** | En vez de pasar varios campos de un objeto, se pasa el objeto completo | Los parámetros son campos de un objeto que ya existe |
| **Introduce Parameter Object** | Agrupa varios parámetros que siempre van juntos en una nueva clase | Los parámetros forman un **concepto cohesionado** |
| **Remove Flag Argument** | Sustituye un booleano por dos métodos con nombre claro | Hay un `boolean` que cambia el comportamiento |
| **Builder** | Construye el objeto paso a paso | Muchos parámetros, muchos opcionales |

> [!warning] Cuidado: no agrupar lo que no es un concepto
> Si los parámetros no forman una abstracción coherente, crear un objeto solo para “quitarlos de en medio” produce una [[2. Codigo sucio por clases perezosas|clase perezosa]] o un [[4. Codigo sucio por grupos de datos|grupo de datos]] disfrazado.

## 🔧 Ejemplo (después): objeto de parámetros

```java
// ✅ Concepto: datos del pedido
public final class DatosPedido {
    private final Cliente cliente;
    private final DireccionEnvio direccion;
    private final LineaPedido linea;
    private final boolean urgente;

    public DatosPedido(Cliente cliente, DireccionEnvio direccion,
                       LineaPedido linea, boolean urgente) {
        this.cliente = cliente;
        this.direccion = direccion;
        this.linea = linea;
        this.urgente = urgente;
    }

    // getters...
}
```

```java
public class ServicioPedidos {
    public void crear(DatosPedido datos) {
        // ...
    }
}
```

```java
// ✅ Llamada legible (y con significado en cada valor)
DatosPedido datos = new DatosPedido(
        cliente,
        new DireccionEnvio("Mayor 10", "Madrid", "28001", "ES"),
        new LineaPedido("Teclado", 2, 49.99),
        true
);

servicio.crear(datos);
```

> [!success] Resultado
> La firma es corta, cada valor tiene **nombre y tipo**, y añadir un dato nuevo no obliga a cambiar la firma de `crear`.

## 🧩 Ejemplo: eliminar la bandera booleana

```java
// ❌ boolean trap: ¿qué significa true?
imprimirFactura(factura, true);
```

```java
// ✅ Dos métodos con nombres claros
public void imprimirFacturaNormal(Factura factura) { /* ... */ }
public void imprimirFacturaSimplificada(Factura factura) { /* ... */ }

imprimirFacturaSimplificada(factura); // se entiende sin mirar la firma
```

> [!tip] Regla
> Un `boolean` en una firma suele indicar **dos comportamientos distintos** escondidos en un mismo método. Si cambia lo que hace, sepáralo en dos métodos o usa un **enum** con significado (`TipoFactura.NORMAL`, `TipoFactura.SIMPLIFICADA`).

---

## 🧩 Ejemplo: `Preserve Whole Object`

```java
// ❌ Se pasan tres campos del mismo objeto
public double calcularDistancia(int x1, int y1, int x2, int y2) {
    // ...
}
```

```java
// ✅ Se pasan los objetos completos
public double calcularDistancia(Punto origen, Punto destino) {
    return Math.hypot(destino.getX() - origen.getX(),
                      destino.getY() - origen.getY());
}
```

> [!note] Matiz
> A veces interesa pasar solo un valor (p. ej. `calcularDescuento(double importe)` en vez de `calcularDescuento(Pedido pedido)`) para **no acoplar** el método a toda la clase. El criterio es la **cohesión del parámetro**, no la comodidad.

---

## 📏 Métrica

> [!important] Regla de los parámetros
> Funciones con un número **pequeño** de argumentos:
> - **0** argumentos es lo mejor.
> - **1 o 2** es aceptable.
> - **3** debería evitarse.
> - **más de 3** es muy cuestionable y debe considerarse un **prejuicio** (mala señal).

No es una regla matemática: depende del contexto. Pero cada parámetro **extra** aumenta la carga cognitiva y las combinaciones de prueba.

---

## 🔍 Cómo detectarlo

- **Más de 3 parámetros** en la firma.
- Parámetros del **mismo tipo** seguidos (`String`, `String`, `String`).
- **Booleanos** en la llamada (`true`, `false`) sin nombre.
- Parámetros que **siempre aparecen juntos** en varias firmas.
- El método **extrae valores** de un objeto que el cliente ya tiene (podría recibir el objeto).
- Comentarios en la llamada para recordar el orden: `crear("Ana", /*email*/ ..., /*cp*/ ...)`.

---

## 🎯 Conclusión para examen

1. **Long Parameter List** = método con demasiados argumentos; difícil de entender, probar y evolucionar.
2. **Problemas:** errores de orden, booleanos ilegibles, combinaciones de prueba enormes, cambios en cascada.
3. **Soluciones:** **Replace Parameter with Method Call**, **Preserve Whole Object**, **Introduce Parameter Object**, **Remove Flag Argument** y **Builder**.
4. **Métrica:** 0–2 parámetros bien; 3 evitarse; más de 3 es muy cuestionable.
5. **Cuidado:** agrupar solo parámetros que formen un **concepto cohesionado**, no crear objetos artificiales.

> [!question] Pregunta típica
> *"¿Qué es Long Parameter List y cómo se corrige?"*
> **Respuesta:** es un método con demasiados parámetros, que resulta difícil de entender y probar. Se corrige eliminando parámetros que se pueden obtener de otro objeto (**Replace Parameter with Method Call**), pasando el objeto completo (**Preserve Whole Object**), agrupando parámetros que van juntos en una clase (**Introduce Parameter Object**) o sustituyendo banderas booleanas por métodos con nombre (**Remove Flag Argument**).
