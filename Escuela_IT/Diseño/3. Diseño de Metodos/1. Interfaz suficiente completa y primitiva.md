# 1. Interfaz suficiente, completa y primitiva

> [!info] Principios de diseño de interfaces
> Una buena interfaz (de una clase, módulo o API) debe ser **suficiente**, **completa** y **primitiva** a la vez. Son tres propiedades complementarias que proceden de los principios de diseño de interfaces de **Barbara Liskov**.

---

## 🏷️ Vocabulario

| Propiedad | Pregunta que responde | Si falla… |
|-----------|----------------------|-----------|
| **Suficiente** | ¿Puedo hacer lo esencial con esta interfaz? | El componente es inútil o el cliente debe reimplementar lógica |
| **Completa** | ¿Están cubiertos todos los aspectos **significativos** de la abstracción? | El cliente accede a detalles internos o hace “trucos” para lograr lo que falta |
| **Primitiva** | ¿Cada operación es básica y no redundante? | La interfaz se hincha con operaciones que podrían derivarse de otras |

---

## 📖 Idea clave

> [!tip] Definición corta
> Una interfaz bien diseñada da **lo necesario** (suficiente), **todo lo significativo** (completa) y **sin operaciones de más** (primitiva).

Las tres propiedades se descubren **construyendo clientes reales**: si al usarla echas en falta algo, no es suficiente; si tienes que hurgar dentro, no es completa; si sobran métodos que podrías componer con otros, no es primitiva.

---

## 1️⃣ Interfaz **suficiente**

Una interfaz es **suficiente** cuando la clase o módulo **captura suficientes características de la abstracción** para permitir una interacción **significativa y eficiente**. Si no, el componente es inútil: el cliente no puede hacer nada útil con él.

> [!warning] Se detecta muy pronto
> Las violaciones de suficiencia aparecen **casi siempre al construir el primer cliente** de la abstracción. Es la propiedad más fácil de descubrir.

### 🧩 Ejemplo: un conjunto de elementos

```java
// ❌ No es suficiente: puedo eliminar, pero no añadir
public interface Conjunto<T> {
    void eliminar(T elemento);
}
```

```java
// ✅ Suficiente: las operaciones básicas están presentes
public interface Conjunto<T> {
    void agregar(T elemento);
    void eliminar(T elemento);
    boolean contiene(T elemento);
}
```

> Si una clase ofrece `eliminar`, debe contemplar también `agregar`: de lo contrario no se puede **construir** el estado que se quiere modificar.

### Otro ejemplo: una pila

```java
public interface Pila<T> {
    void apilar(T elemento);
    T desapilar();
    T cima();
    boolean estaVacia();
}
```

Aquí está lo necesario para usar una pila. Añadir `insertarEn(int posicion, T elemento)` no tendría sentido: una pila no permite insertar en medio.

---

## 2️⃣ Interfaz **completa**

Una interfaz es **completa** cuando **captura todas las características significativas** de la abstracción. Es decir, es lo suficientemente **general** como para ser utilizada por cualquier cliente.

> [!warning] La completitud es subjetiva y se puede exagerar
> Incluir **todas** las operaciones imaginables abruma al usuario y suele ser innecesario: muchas operaciones de alto nivel se pueden **componer** con las de bajo nivel.

### 🧩 Ejemplo: una lista incompleta

```java
// ❌ Incompleta: no puedo borrar ni recorrer
public interface Lista<T> {
    void agregar(T elemento);
    T obtener(int indice);
}
```

Faltan operaciones básicas como `eliminar`, `tamanio` o un iterador. El cliente tendría que acceder a la implementación para suplirlas.

### 🧩 Ejemplo: ¿hasta dónde llegar con `String`?

La clase `String` cubre las operaciones significativas de una cadena (`length`, `substring`, `indexOf`, `equals`…). Pero **no** sería razonable incluir `esPalindromo`, `esEmail`, `toCamelCase`… aunque sean “previsibles”:

- no son significativas para **todos** los clientes;
- pueden componerse con las operaciones existentes;
- llenarían la interfaz de métodos que casi nadie usa.

> [!tip] Regla práctica
> **Completa ≠ enorme.** La interfaz debe cubrir lo significativo, no todo lo imaginable.

---

## 3️⃣ Interfaz **primitiva**

Una operación es **primitiva** cuando:

- solo puede implementarse de forma eficiente **accediendo a la representación subyacente** de la abstracción, **o**
- podría implementarse con otras operaciones existentes, pero a **mucho más coste computacional**.

> [!note] Idea
> Las operaciones primitivas son los **ladrillos básicos**. Las operaciones de alto nivel se construyen encima de ellas y **no** deben formar parte de la interfaz mínima.

### 🧩 Ejemplo: conjunto de elementos

```java
public interface Conjunto<T> {
    void agregar(T elemento);      // ✅ primitiva
    void eliminar(T elemento);     // ✅ primitiva
    boolean contiene(T elemento);  // ✅ primitiva
}
```

- `agregar` es primitiva: necesita conocer la estructura interna.
- `agregarCuatro(elemento)` **no** es primitiva: se puede implementar llamando cuatro veces a `agregar`.
- `agregarTodos(coleccion)` **no** es primitiva en general, aunque puede añadirse como **operación de conveniencia** si la implementación la hace mucho más eficiente.

### ❌ Ejemplo de interfaz no primitiva

```java
public interface Calculadora {
    int sumar(int a, int b);
    int restar(int a, int b);
    int incrementar(int a); // redundante: sumar(a, 1)
}
```

`incrementar` es cómoda, pero **no aporta** una capacidad nueva. Si se añade, debe estar justificada (rendimiento, claridad de uso muy extendido).

## ⚖️ Cómo se combinan las tres propiedades

| Vista | Propiedad | Pregunta |
|-------|-----------|----------|
| Del **cliente** | Suficiente | ¿Puedo interactuar de forma significativa? |
| De la **abstracción** | Completa | ¿Están todos los aspectos significativos? |
| De la **implementación** | Primitiva | ¿Las operaciones son básicas y no redundantes? |

> [!example] Interfaz ideal vs. interfaz inflada
> ```java
> // ✅ Interfaz de primitivas + alguna conveniencia justificada
> public interface Coleccion<T> {
>     void agregar(T elemento);
>     boolean eliminar(T elemento);
>     boolean contiene(T elemento);
>     int tamanio();
> }
> ```
> ```java
> // ❌ Interfaz inflada: mezcla primitivas con operaciones derivables
> public interface ColeccionInflada<T> {
>     void agregar(T elemento);
>     boolean eliminar(T elemento);
>     boolean contiene(T elemento);
>     int tamanio();
>     void agregarDos(T a, T b);       // se compone con agregar
>     void agregarTres(T a, T b, T c); // se compone con agregar
>     void vaciar();                   // se compone con eliminar
> }
> ```

---

## 🚫 Errores frecuentes

- **Interfaz mínima pero inútil:** ofrecer `eliminar` sin `agregar` (falla la **suficiencia**).
- **Interfaz gigante “por si acaso”:** añadir decenas de operaciones que nadie usa (falla la **primitividad** y contradice **YAGNI**).
- **Exponer la representación interna** para que el cliente haga la operación por su cuenta: `getElementos()`, `getArrayInterno()`… (rompe la encapsulación).
- **Añadir métodos para un único cliente concreto:** la interfaz deja de ser general.
- **Confundir “completa” con “todas las operaciones imaginables”.**

---

## 🔗 Relación con YAGNI y TDD

> [!important] No adelantes operaciones
> **TDD se apoya en YAGNI**: no añadas una operación hasta que un **test o un cliente real** la necesite. Si no ves **clarísimo** que el método será necesario, **no lo crees**.

- La interfaz crece **guiada por clientes reales**, no por especulación.
- Una interfaz “completa” se **descubre iterando**, no se adivina al principio.
- Añadir métodos “por si acaso” produce código muerto y aumenta el coste de mantenimiento → [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]].

---

## 🎯 Conclusión para examen

1. **Suficiente**: la interfaz permite una interacción significativa y eficiente; si falta algo básico, el componente es inútil.
2. **Completa**: cubre todos los aspectos significativos de la abstracción y es general para cualquier cliente; no debe exagerarse.
3. **Primitiva**: sus operaciones son básicas, no redundantes y solo pueden implementarse eficientemente con acceso a la representación.
4. Las tres se complementan: **suficiente** (vista del cliente), **completa** (vista de la abstracción) y **primitiva** (vista de la implementación).
5. Se descubren con **clientes y tests reales**; añadir métodos especulativos contradice **YAGNI**.

> [!question] Pregunta típica
> *"Explica qué significa que una interfaz sea suficiente, completa y primitiva."*
> **Respuesta:** **Suficiente** = permite interactuar de forma significativa y eficiente; **completa** = cubre todos los aspectos significativos de la abstracción; **primitiva** = sus operaciones son básicas y no redundantes, implementables de forma eficiente solo con acceso a la representación. Ej.: una `Pila` con `apilar`, `desapilar`, `cima` y `estaVacia` es suficiente y completa; `agregarCuatro` no sería primitiva porque se compone con `apilar`.
