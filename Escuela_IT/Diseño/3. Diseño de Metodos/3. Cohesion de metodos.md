# 3. Cohesión de métodos

> [!info] Code smell · Funciones que deberían hacer una sola cosa
> **Sinónimo:** *Functions Should Do One Thing* — *Refactoring* (Code Smells), Martin Fowler.
> Relacionado con [[10. Principio de unica responsabilidad|SRP]] y con [[3. Alta cohesion|Alta cohesión (GRASP)]].

---

## 📖 ¿Qué es la cohesión?

La **cohesión** mide **qué tan relacionadas están las responsabilidades internas** de una unidad de código (un método, una clase o un módulo).

| Tipo | Qué significa | Consecuencia |
|------|---------------|--------------|
| **Alta cohesión** | El método hace **una sola cosa** bien definida; todas sus instrucciones persiguen el mismo objetivo | Fácil de entender, mantener, reutilizar y probar |
| **Baja cohesión** | El método mezcla tareas **no relacionadas**: validar, calcular, guardar, imprimir… | Difícil de entender, reutilizar y probar; cambios en una tarea afectan a las demás |

> [!tip] Idea clave
> Un método cohesivo tiene **una única razón para existir**. Si para describirlo necesitas la palabra “y”, probablemente hace demasiado.

---

## ❓ Por qué es un problema (justificación)

- Se crean funciones con **múltiples secciones** que realizan operaciones distintas.
- Las líneas del método **no son cohesivas** porque persiguen **objetivos diferentes**.
- Producen **acoplamiento temporal**: una parte depende de que otra se haya ejecutado antes, aunque no tenga relación con ella.
- **Imposibilitan la reutilización**: si solo necesitas una parte, te llevas todas las demás.

> [!example] Ejemplo del temario: `Intervalo`
> Un método que **calcula la longitud de un `Intervalo`** y **muestra el resultado por pantalla**.
> Cuando otro cliente solo necesita el cálculo, **no puede reutilizar** el método: se ve obligado a repetir la lógica o a “tragarse” la impresión.

```java
// ❌ Dos responsabilidades en un solo método
public void calcularLongitudYMostrar(Intervalo intervalo) {
    int longitud = intervalo.getMaximo() - intervalo.getMinimo();
    System.out.println("Longitud: " + longitud);
}
```

```java
// ✅ Una responsabilidad por método; el cliente decide qué hacer con el resultado
public int calcularLongitud(Intervalo intervalo) {
    return intervalo.getMaximo() - intervalo.getMinimo();
}

// El cliente que quiera mostrarlo lo hace explícitamente
int longitud = calcularLongitud(intervalo);
System.out.println("Longitud: " + longitud);
```

> [!warning] Acoplamiento temporal
> Mezclar cálculo y presentación obliga al método a depender de la consola. Si mañana la salida es una app web o móvil, hay que reescribirlo. La lógica de negocio debe ser **independiente de la vista** (consola, web, móvil…).

---

## 🔍 Cómo detectarlo

- El método tiene **varias secciones** separadas por comentarios o líneas en blanco.
- El nombre contiene **“Y”**: `validarYGuardar`, `calcularYMostrar`, `procesarYNotificar`.
- Mezcla **niveles de abstracción**: lógica de negocio, acceso a datos, validación, impresión, envío de correos…
- Hay **muchas variables locales** que solo se usan en una parte del método.
- Cambiar una parte obliga a **volver a probar** todo el método.
- Es difícil ponerle un nombre preciso sin usar “y”.

---

## 🧩 Ejemplo en Java: baja cohesión

```java
public void procesarPedido(Pedido pedido) {
    // 1. Validar datos
    if (pedido.getCliente() == null) {
        throw new IllegalArgumentException("El pedido no tiene cliente");
    }

    // 2. Calcular total
    double total = 0;
    for (Producto producto : pedido.getProductos()) {
        total += producto.getPrecio();
    }

    // 3. Guardar en la base de datos
    System.out.println("Guardando pedido en la base de datos...");

    // 4. Enviar correo de confirmación
    System.out.println("Enviando email al cliente...");
}
```

### ❌ Problemas

- **Valida, calcula, guarda y envía correo** → cuatro responsabilidades diferentes.
- Si cambia la lógica del correo o de la base de datos, este método se ve afectado **sin necesidad**.
- No se puede reutilizar el cálculo del total sin ejecutar también el guardado y el correo.
- Es difícil de **probar unitariamente**: para probar el total hay que lidiar con la BD y el correo.

---

## ✅ Refactorización: alta cohesión

Separar cada responsabilidad en su propio método:

```java
public void procesarPedido(Pedido pedido) {
    validarPedido(pedido);
    double total = calcularTotal(pedido);
    guardarPedido(pedido, total);
    enviarConfirmacion(pedido);
}

private void validarPedido(Pedido pedido) {
    if (pedido.getCliente() == null) {
        throw new IllegalArgumentException("El pedido no tiene cliente");
    }
}

private double calcularTotal(Pedido pedido) {
    double total = 0;
    for (Producto producto : pedido.getProductos()) {
        total += producto.getPrecio();
    }
    return total;
}

private void guardarPedido(Pedido pedido, double total) {
    System.out.println("Guardando pedido en la base de datos con total: " + total);
}

private void enviarConfirmacion(Pedido pedido) {
    System.out.println("Enviando email al cliente " + pedido.getCliente().getEmail());
}
```

### ✅ Ventajas

- Cada método tiene **alta cohesión**: hace solo una cosa.
- `procesarPedido()` se lee como un **flujo de pasos claros** (lenguaje del dominio).
- `calcularTotal()` es **reutilizable** y se puede probar **sin** base de datos ni correo.
- Los cambios quedan **localizados** en el método correspondiente.
- Facilita el mantenimiento y las pruebas unitarias.

> [!tip] Técnica de refactorización
> **Extract Method**: buscar un bloque que “vaya bien junto”, convertirlo en un método y nombrarlo por **lo que hace** (no por cómo lo hace).

---

## ⚖️ Cohesión y tamaño

- Un método cohesivo suele ser **corto**, pero la longitud no es el criterio principal: un método largo puede ser cohesivo si hace una única tarea compleja.
- Lo importante es que **todas sus instrucciones contribuyan al mismo objetivo**.
- Si el método mezcla varias tareas, se divide; si sigue siendo complejo, se vuelve a dividir (**Refactorización**).
- La cohesión de métodos es la base de la [[10. Principio de unica responsabilidad|responsabilidad única]] a nivel de clase.

> [!warning] No confundir con “partir por partir”
> Extraer métodos sin criterio puede producir métodos triviales y una navegación interminable. Se extrae cuando hay una **responsabilidad identificable** o una parte **reutilizable**.

## 🎯 Conclusión para examen

1. **Cohesión** = grado en que las instrucciones de un método están enfocadas en **una sola tarea**.
2. **Alta cohesión** → métodos cortos, claros y con una única responsabilidad; **baja cohesión** → métodos que mezclan validación, cálculo, persistencia y presentación.
3. **Problema:** acoplamiento temporal, nula reutilización, dificultad de prueba y mantenimiento.
4. **Solución:** dividir en varios métodos pequeños que hagan una sola cosa (**Extract Method**).
5. **Señal típica:** el nombre necesita una “y” (`calcularYMostrar`) o hay comentarios que separan secciones con objetivos distintos.

> [!question] Pregunta típica
> *"¿Qué es la cohesión de métodos y cómo se mejora?"*
> **Respuesta:** es el grado en que todas las instrucciones de un método persiguen una única tarea. Un método que calcula la longitud de un intervalo **y** la muestra por pantalla tiene baja cohesión: no es reutilizable y acopla la lógica a la vista. Se mejora **extrayendo métodos** (`calcularLongitud` y que el cliente decida imprimir) para que cada uno haga una sola cosa.
