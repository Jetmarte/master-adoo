# 8. Diseño por contrato

> [!info] Design by Contract
> Enfoque de diseño en el que la relación entre una clase y sus clientes se ve como un **contrato formal** que expresa los **derechos y obligaciones** de cada parte. Popularizado por **Bertrand Meyer** (Eiffel).
> Relacionado con [[1. Principio de sustitucion de LISCOV|LSP]], [[2. Leyes de Demeter|Ley de Demeter]] y [[10. Principio de unica responsabilidad|SRP]].

---

## 1️⃣ Corrección, fallo, defecto y error

La **corrección** de un sistema solo tiene sentido **en relación con una especificación**: un sistema es correcto si se comporta como dice su especificación.

| Concepto | Definición | Ejemplo |
|----------|------------|---------|
| **Fallo** (*failure*) | El sistema **se aparta** de su comportamiento especificado **durante una ejecución** | La aplicación lanza una excepción al dividir entre cero |
| **Defecto** (*defect*) | **Propiedad** del sistema que **puede** hacer que se aparte de su comportamiento especificado | El método `dividir` no comprueba si el divisor es cero |
| **Error** (*error*) | **Mala decisión** tomada durante el desarrollo que produce defectos | El programador decide no validar el divisor “porque nadie lo va a poner a cero” |

> [!tip] La cadena causa-efecto
> **Error** (decisión humana) → produce **defectos** (código defectuoso) → provocan **fallos** (en ejecución).
>
> El fallo es el **hecho real**; el defecto es la **posibilidad potencial**.

### 🧩 Ejemplo completo

```java
// Error: el programador no contempla el divisor cero
// Defecto: el código no valida b
public int dividir(int a, int b) {
    return a / b; // fallo cuando b == 0
}
```

```java
// ✅ Defecto corregido: se valida la precondición
public int dividir(int a, int b) {
    if (b == 0) {
        throw new IllegalArgumentException("El divisor no puede ser cero");
    }
    return a / b;
}
```

## 2️⃣ Tipos de error

| Tipo | Origen | Ejemplos |
|------|--------|----------|
| **Errores excepcionales** | Recursos **fuera del ámbito** del software: ficheros, comunicaciones, bibliotecas… | Abrir un fichero inexistente, red caída, base de datos no disponible |
| **Errores lógicos** | La **lógica del programa** no contempla todos los valores posibles de los datos | Factorial de un número negativo, bucle infinito, división entre cero |

> [!warning] El contexto cambia la clasificación
> Un mismo error puede ser **lógico** o **excepcional** según quién sea el responsable:
>
> | Contexto | Responsabilidad |
> |----------|-----------------|
> | **Aplicación** | Debe detectar y subsanar los errores lógicos **dentro de su ámbito** durante el desarrollo y las pruebas |
> | **Biblioteca** | **No** puede responsabilizarse del uso indebido de sus servicios y **nunca** debe encargarse de subsanar esos errores. Se consideran **excepcionales** porque la causa está fuera de los límites de la biblioteca |
>
> Ejemplo: pasar `-1` a un factorial es un **error lógico** de la aplicación que lo llama, pero para la biblioteca de matemáticas es un **error excepcional** (uso indebido).

---

## 3️⃣ Gestión de errores

| Capacidad | Qué persigue | Errores que cubre | Mecanismo habitual |
|-----------|--------------|-------------------|--------------------|
| **Robustez** | Reaccionar a casos **no incluidos** en la especificación | Excepcionales | **Excepciones** |
| **Corrección** | Ejecutar **de acuerdo con la especificación** | Lógicos | **Aserciones** (adecuado) · **Programación defensiva** (inadecuado) |

> [!example] Ejemplos
> - **Robustez con excepciones:** abrir un fichero sobre un soporte dañado, enviar datos sin conexión, usar mal una biblioteca.
> - **Corrección con aserciones:** factorial de un negativo, bucle infinito, división entre cero.

### 🛡️ Programación defensiva

Para obtener software fiable, cada componente se diseña para **protegerse a sí mismo** tanto como sea posible: comprueba la viabilidad de operar con `if-then-else`.

```java
// Programación defensiva: el componente se protege a sí mismo
public double retirar(double cantidad) {
    if (cantidad <= 0) {
        System.out.println("Cantidad inválida"); // informa por pantalla
        return -1;                                // código de error
    }
    // ...
}
```

> [!danger] Problemas de la programación defensiva
> - **Informar por pantalla acopla el componente a la vista**: no sirve para consola, web, móvil… y no avisa al cliente para que tome medidas.
> - **Un código de error no siempre es posible**: si `0` o `-1` son valores válidos del dominio, no se pueden usar como “error”.
> - El componente y **todos** sus clientes se llenan de `if-then-else` para comprobar la viabilidad y la ausencia de error → **complejidad innecesaria** y **código duplicado**.

### ✅ Aserciones

Una **aserción** es una expresión que establece una **propiedad** que ciertas entidades del software deben satisfacer en determinados estados de la ejecución.

- Es una sentencia del lenguaje que comprueba las **suposiciones** sobre el estado del programa.
- Contiene una expresión lógica que **se supone cierta** al ejecutarse.
- Si es falsa, el sistema **finaliza la ejecución** y avisa del error detectado.

```java
assert n >= 0 : "La precondición n >= 0 no se cumple: n = " + n;
```

| Uso | Para qué | Efecto |
|-----|----------|--------|
| **Producción** | Documentar **formalmente** (de forma compilable) los límites del componente | Sin efecto sobre la ejecución (en Java, `assert` está desactivado por defecto) |
| **Pre-producción** | Comprobaciones automáticas durante la ejecución | Si falla, eleva una excepción que termina la ejecución e informa claramente |

> [!note] En Java
> Las aserciones se activan con `-ea` (`java -ea MiPrograma`). Por eso no deben usarse para validar datos de entrada de una **API pública**: para eso se usan excepciones explícitas (`IllegalArgumentException`, `IllegalStateException`). Las aserciones son ideales para **invariantes internas** y comprobaciones de desarrollo.

## 4️⃣ ¿Qué es el diseño por contrato?

> [!important] Definición
> El **diseño por contrato** considera la relación entre una clase y sus clientes como un **contrato formal** que expresa los **derechos y obligaciones** de cada parte.

- La **vista exterior** de cada objeto define un **contrato** sobre los objetos que pueden depender de él.
- Esa vista exterior debe ser llevada a cabo por la **vista interior** del propio objeto, a menudo colaborando con otros.
- El contrato establece **todas las asunciones** que un cliente puede hacer sobre el comportamiento de un servidor.

> [!tip] La metáfora del contrato
> - El **cliente** se compromete a cumplir la **precondición** (llamar en condiciones válidas).
> - El **servidor** se compromete a cumplir la **postcondición** (devolver un resultado válido y dejar el objeto consistente).
> - Si el cliente incumple, el servidor no está obligado a nada.
> - Si el servidor incumple, el cliente puede dejar de confiar en él.

### 🎯 Objetivos

1. Producir **software correcto desde el principio**, porque está diseñado para ser correcto.
2. Obtener una **mejor comprensión** del problema y de sus posibles soluciones.
3. **Facilitar la documentación** del software.

### 📜 Protocolo

El **protocolo** es el **conjunto entero de operaciones** que un cliente puede realizar sobre un objeto, junto con las **“consideraciones legales”** en las que pueden invocarse.

> [!example] Protocolo de una cuenta bancaria
> - `abrir()` → solo si la cuenta **no** está abierta.
> - `ingresar(cantidad)` → solo si la cuenta está abierta y `cantidad > 0`.
> - `retirar(cantidad)` → solo si la cuenta está abierta y `cantidad <= saldo`.
> - `cerrar()` → solo si la cuenta está abierta.
>
> Llamar a `retirar` antes de `abrir` **viola el protocolo**, aunque la precondición numérica sea correcta.

## 5️⃣ Precondiciones y postcondiciones

Para cada operación asociada a un objeto se definen **precondiciones** y **postcondiciones**:

```text
{P} A {Q}
```

| Símbolo | Significado |
|---------|-------------|
| `A` | La operación |
| `P` | **Precondición**: aserción sobre el estado de los parámetros y del objeto servidor |
| `Q` | **Postcondición**: aserción sobre el valor devuelto y el estado del objeto servidor |

> [!important] Semántica
> Cualquier ejecución de `A` **comienza en un estado que cumple `P`** y **termina en un estado que cumple `Q`**.

- Si se viola la **precondición** → el **cliente** no ha cumplido su parte; el servidor no puede proceder con fiabilidad.
- Si se viola la **postcondición** → el **servidor** no ha cumplido su parte; los clientes no pueden confiar en su comportamiento.

La pareja **precondición/postcondición** de una rutina describe el contrato que la rutina (servidor) define para sus usuarios (clientes).

---

### 🔒 Precondiciones: obligan al cliente

> [!note] Definición
> Restricciones sobre el **estado de los parámetros** y del **objeto servidor** que deben cumplirse para una llamada **legítima** a la operación y que funcione apropiadamente.
> **Obligación del cliente, beneficio del servidor.**

| Tipo | Exige al cliente | Efecto en el servidor |
|------|------------------|-----------------------|
| **Fuerte** | **Más** (condiciones de partida más restrictivas) | Trabajo **más fácil**: menos casos que contemplar |
| **Débil** | **Menos** | Trabajo **más complicado**: debe manejar más situaciones |

```java
// Precondición FUERTE: el cliente garantiza que hay saldo suficiente
// El servidor no necesita comprobar la insuficiencia
public void retirar(double cantidad) {
    assert cantidad > 0 && cantidad <= saldo;
    saldo -= cantidad;
}
```

```java
// Precondición DÉBIL: el cliente solo garantiza cantidad > 0
// El servidor debe decidir qué hacer si no hay saldo
public void retirar(double cantidad) {
    assert cantidad > 0;
    if (cantidad > saldo) {
        throw new IllegalArgumentException("Saldo insuficiente");
    }
    saldo -= cantidad;
}
```

---

### 📤 Postcondiciones: obligan al servidor

> [!note] Definición
> Restricciones sobre el **estado del valor devuelto** y del **objeto servidor** que deben cumplirse **tras el retorno** de la operación para que el cliente progrese adecuadamente.
> **Obligación del servidor, beneficio del cliente.**

| Tipo | Exige al servidor | Efecto en el cliente |
|------|-------------------|----------------------|
| **Fuerte** | **Más**: resultado más restringido y garantizado | Trabajo **más fácil**: puede confiar en un resultado concreto |
| **Débil** | **Menos**: resultado más abierto | Trabajo **más complicado**: debe comprobar más cosas |

```java
// Postcondición FUERTE: el resultado siempre es no negativo
/**
 * @requires n >= 0
 * @ensures resultado >= 0
 */
public long factorial(int n) { /* ... */ }
```

> [!tip] Fuerte y débil no significan “mejor” y “peor”
> Una precondición fuerte **facilita** al servidor pero **carga** al cliente. Una precondición débil **facilita** al cliente pero **carga** al servidor. El diseño consiste en **repartir** las obligaciones de forma razonable.

---

### 🧩 Ejemplo completo: `factorial`

```java
/**
 * Calcula el factorial de n.
 *
 * Precondición:  n >= 0
 * Postcondición: devuelve n! (y el resultado es >= 1)
 */
public long factorial(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
                "Precondición violada: n debe ser >= 0, recibido " + n);
    }

    long resultado = 1;
    for (int i = 2; i <= n; i++) {
        resultado *= i;
    }

    assert resultado >= 1 : "Postcondición violada: factorial negativo";
    return resultado;
}
```

- `n = -1` es un **error lógico** del cliente: se detecta con la precondición.
- El bucle y el resultado son responsabilidad del servidor: se comprueban con la postcondición.

## 6️⃣ Invariantes de clase

> [!important] Definición
> Una **invariante de clase** es una aserción expresada como una **restricción general de consistencia** que debe cumplir **cada objeto de la clase como un todo**.

- Es **distinta** de las precondiciones y postcondiciones, que caracterizan **rutinas individuales** sobre sus parámetros de entrada y sus resultados.
- La **invariante solo involucra el estado del objeto**.

### 🧩 Ejemplo: cuenta bancaria

```java
public final class CuentaBancaria {
    private double saldo;

    // INVARIANTE: saldo >= 0

    public CuentaBancaria(double saldoInicial) {
        if (saldoInicial < 0) {
            throw new IllegalArgumentException("El saldo inicial no puede ser negativo");
        }
        this.saldo = saldoInicial;
        assert invariante();
    }

    public void ingresar(double cantidad) {
        if (cantidad <= 0) {
            throw new IllegalArgumentException("La cantidad debe ser positiva");
        }
        saldo += cantidad;
        assert invariante();
    }

    public void retirar(double cantidad) {
        if (cantidad <= 0 || cantidad > saldo) {
            throw new IllegalArgumentException("Retirada no válida");
        }
        saldo -= cantidad;
        assert invariante();
    }

    private boolean invariante() {
        return saldo >= 0;
    }
}
```

### 🧩 Ejemplo: intervalo cerrado

```java
public final class Intervalo {
    private final int minimo;
    private final int maximo;

    // INVARIANTE: minimo <= maximo

    public Intervalo(int minimo, int maximo) {
        if (minimo > maximo) {
            throw new IllegalArgumentException("minimo no puede superar a maximo");
        }
        this.minimo = minimo;
        this.maximo = maximo;
    }

    public int longitud() {
        // Gracias a la invariante, sabemos que el resultado es >= 0
        return maximo - minimo;
    }
}
```

> [!tip] La invariante como “verdad permanente”
> Si `minimo <= maximo` se cumple siempre, `longitud()` puede devolver `maximo - minimo` **sin comprobar nada**: la invariante garantiza que no será negativo.

---

### ⚖️ Efecto de las invariantes sobre precondiciones y postcondiciones

Añadir invariantes de clase **fortalece o, como mínimo, mantiene** las precondiciones y postcondiciones:

| Efecto | Por qué |
|--------|---------|
| **Facilita** el trabajo del componente | Además de la precondición, puede **asumir** que el estado inicial cumple la invariante → menos casos que contemplar |
| **Complica** el trabajo del componente | Además de la postcondición, debe garantizar que el estado final **sigue cumpliendo** la invariante → puede requerir más acciones |

> [!example] Ejemplo
> En `CuentaBancaria`, la invariante `saldo >= 0` permite que `ingresar` asuma un saldo inicial válido; pero obliga a `retirar` a no dejar el saldo negativo.

## 7️⃣ Corrección de una clase

> [!important] Una clase es correcta si…
> 1. **Cada constructor**, cuando se aplica satisfaciendo su precondición en un estado donde los atributos tienen sus valores por defecto, al terminar **satisface la invariante**:
>    ```text
>    {P} constructor {Q and I}
>    ```
> 2. **Cada operación**, cuando se aplica satisfaciendo su precondición **y** su invariante, al terminar **satisface su postcondición y su invariante**:
>    ```text
>    {P and I} operación {Q and I}
>    ```

- `P` = precondición.
- `Q` = postcondición.
- `I` = invariante de clase.

> [!note] Lectura intuitiva
> - El **constructor** parte de un estado “vacío” (valores por defecto), cumple su precondición y debe dejar el objeto **consistente** (`I`).
> - Cada **operación** parte de un objeto consistente (`I`) y con su precondición cumplida (`P`), y debe terminar con su postcondición cumplida (`Q`) **sin romper** la consistencia (`I`).

## 8️⃣ Resumen visual del contrato

```text
Cliente                         Servidor
   │                               │
   │  cumple P (precondición)      │
   │ ─────────────────────────────>│
   │                               │  ejecuta A
   │                               │  cumple Q (postcondición)
   │<───────────────────────────── │
   │                               │
   │      I (invariante) se cumple antes y después de cada operación
```

| Elemento | Obligación de | Beneficio de |
|----------|---------------|--------------|
| **Precondición** (`P`) | Cliente | Servidor |
| **Postcondición** (`Q`) | Servidor | Cliente |
| **Invariante** (`I`) | Servidor (mantenerla) | Cliente y servidor (pueden asumirla) |

## 🎯 Conclusión para examen

1. **Error** (mala decisión) → **defecto** (propiedad potencial) → **fallo** (desviación real en ejecución).
2. **Errores excepcionales** (recursos externos) se cubren con **excepciones** (robustez); **errores lógicos** (lógica incompleta) se cubren adecuadamente con **aserciones** y no con programación defensiva.
3. **Diseño por contrato** = relación cliente-servidor como contrato formal de **derechos y obligaciones**.
4. **Precondición** `{P}`: obligación del **cliente**, beneficio del **servidor**; **postcondición** `{Q}`: obligación del **servidor**, beneficio del **cliente**.
5. **Precondiciones fuertes** facilitan al servidor y cargan al cliente; **postcondiciones fuertes** facilitan al cliente y cargan al servidor.
6. **Invariante de clase** `{I}`: restricción de consistencia de **todo** el objeto; se cumple antes y después de cada operación.
7. **Corrección:** `{P} constructor {Q and I}` y `{P and I} operación {Q and I}`.

> [!question] Pregunta típica
> *"Explica el diseño por contrato con un ejemplo."*
> **Respuesta:** es un enfoque que formaliza la relación cliente-servidor mediante un contrato: el cliente garantiza la **precondición** y el servidor garantiza la **postcondición** y la **invariante**. Ejemplo: en `retirar(cantidad)`, la precondición `cantidad > 0 && cantidad <= saldo` obliga al cliente; la postcondición `saldo == saldoAnterior - cantidad` obliga al servidor; la invariante `saldo >= 0` debe cumplirse antes y después. Si el cliente viola la precondición, el servidor no puede garantizar nada; si el servidor viola la postcondición, el cliente no puede confiar en él.
