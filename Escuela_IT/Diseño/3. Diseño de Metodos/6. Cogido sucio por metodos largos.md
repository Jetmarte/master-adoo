# 6. Código sucio por métodos largos

> [!info] Code smell · Long Method

## 📖 ¿Qué es?

Un **método largo** es un método con demasiadas líneas, demasiada lógica o demasiados niveles de anidamiento. Es uno de los malos olores más fáciles de reconocer y uno de los más perjudiciales.

> [!warning] Señal de alarma
> Si para entender el método tienes que **desplazarte** varias pantallas, o si necesitas **comentarios** para separar secciones, el método probablemente sea demasiado largo.

```java
// ❌ Un método que lo hace todo
public void procesarFactura(Factura factura) {
    // validar...
    // calcular impuestos...
    // aplicar descuentos...
    // guardar...
    // imprimir...
    // enviar correo...
    // actualizar inventario...
}
```

---

## ❓ Por qué es un problema (justificación)

- **Cuanto más largo es un procedimiento, más difícil es de entender.**
- Históricamente, los lenguajes antiguos tenían una **sobrecarga** en las llamadas a subrutinas, lo que **desanimaba** escribir métodos pequeños. Hoy esa excusa ya no existe.
- Un método largo suele mezclar **varias responsabilidades** → baja [[3. Cohesion de metodos|cohesión]].
- Es **difícil de probar**: hay muchos caminos y combinaciones.
- Es **difícil de reutilizar**: una parte no se puede usar sin arrastrar el resto.
- Los cambios en una parte pueden **romper** otra parte sin que se note.
- Acumula **variables temporales** que complican la lectura.

> [!tip] Idea clave
> Un método debe contar **una historia breve** y delegar los detalles en métodos con nombre. Si la historia es larga, se divide en capítulos.

---

## ✅ Solución: Extract Method

> [!success] Regla del 99 %
> **El 99 % de las veces, un método largo se acorta extrayendo otro método.** Se busca una parte que “vaya bien junta” y se convierte en un método nuevo.

### 🧩 Cómo encontrar las partes

1. Buscar **comentarios** o **líneas en blanco** que separen bloques → son señales de **distancia semántica**.
2. Un bloque con un comentario suele indicar que debe convertirse en un método **cuyo nombre se base en el comentario**.
3. Extraer también **condicionales complejos** (**Decompose Conditional**) y **bucles** con lógica propia.
4. Si el método extraído necesita muchos parámetros, considerar **Introduce Parameter Object** o **Replace Temp with Query**.
5. Repetir hasta que cada método haga **una sola cosa**.

> [!example] Del comentario al nombre del método
> ```java
> // ❌ Antes: el comentario delata la responsabilidad
> // calcular el total con impuestos
> double total = 0;
> for (LineaFactura linea : factura.getLineas()) {
>     total += linea.getSubtotal() * (1 + linea.getIVA());
> }
> ```
> ```java
> // ✅ Después: el comentario se convierte en el nombre
> double total = calcularTotalConImpuestos(factura);
> ```

## 🔧 Ejemplo (antes): método largo

```java
public void procesarFactura(Factura factura) {
    // 1. Validar la factura
    if (factura == null || factura.getCliente() == null) {
        throw new IllegalArgumentException("Factura inválida");
    }
    if (factura.getLineas().isEmpty()) {
        throw new IllegalArgumentException("La factura no tiene líneas");
    }

    // 2. Calcular el total
    double total = 0;
    for (LineaFactura linea : factura.getLineas()) {
        total += linea.getSubtotal() * (1 + linea.getIVA());
    }
    if (factura.getCliente().esVIP()) {
        total = total * 0.9;
    }

    // 3. Guardar en la base de datos
    System.out.println("Guardando factura en la base de datos...");
    System.out.println("Total: " + total);

    // 4. Imprimir la factura
    System.out.println("FACTURA");
    System.out.println("Cliente: " + factura.getCliente().getNombre());
    for (LineaFactura linea : factura.getLineas()) {
        System.out.println(linea.getDescripcion() + ": " + linea.getSubtotal());
    }
    System.out.println("TOTAL: " + total);

    // 5. Enviar por correo
    System.out.println("Enviando factura a " + factura.getCliente().getEmail());

    // 6. Actualizar inventario
    for (LineaFactura linea : factura.getLineas()) {
        System.out.println("Actualizando stock de " + linea.getDescripcion());
    }
}
```

### ❌ Problemas

- **Seis responsabilidades** en un único método.
- Variables y bucles repetidos por todo el cuerpo.
- Imposible probar el cálculo del total sin imprimir, guardar y enviar correo.
- Cualquier cambio (formato de impresión, envío, base de datos) obliga a tocar el mismo método.

## ✅ Ejemplo (después): métodos pequeños y con nombre

```java
public void procesarFactura(Factura factura) {
    validarFactura(factura);
    double total = calcularTotalConImpuestos(factura);
    guardarFactura(factura, total);
    imprimirFactura(factura, total);
    enviarFacturaPorCorreo(factura);
    actualizarInventario(factura);
}

private void validarFactura(Factura factura) {
    if (factura == null || factura.getCliente() == null) {
        throw new IllegalArgumentException("Factura inválida");
    }
    if (factura.getLineas().isEmpty()) {
        throw new IllegalArgumentException("La factura no tiene líneas");
    }
}

private double calcularTotalConImpuestos(Factura factura) {
    double total = factura.getLineas().stream()
            .mapToDouble(l -> l.getSubtotal() * (1 + l.getIVA()))
            .sum();

    return factura.getCliente().esVIP() ? total * 0.9 : total;
}

private void guardarFactura(Factura factura, double total) {
    System.out.println("Guardando factura en la base de datos...");
    System.out.println("Total: " + total);
}

private void imprimirFactura(Factura factura, double total) {
    System.out.println("FACTURA");
    System.out.println("Cliente: " + factura.getCliente().getNombre());
    factura.getLineas().forEach(l ->
            System.out.println(l.getDescripcion() + ": " + l.getSubtotal()));
    System.out.println("TOTAL: " + total);
}

private void enviarFacturaPorCorreo(Factura factura) {
    System.out.println("Enviando factura a " + factura.getCliente().getEmail());
}

private void actualizarInventario(Factura factura) {
    factura.getLineas().forEach(l ->
            System.out.println("Actualizando stock de " + l.getDescripcion()));
}
```

> [!success] Resultado
> `procesarFactura()` se lee como un **índice de pasos**. Cada método se puede entender, probar y modificar por separado. Además, `calcularTotalConImpuestos()` es **reutilizable** sin efectos secundarios.

## 📏 Métricas

> [!important] Umbrales del temario
> | Métrica | Valor máximo orientativo |
> |---------|--------------------------|
> | **Número de líneas** | **10 – 15** |
> | **Caracteres por línea** | **80 – 120** |
> | **Complejidad ciclomática** | **10 – 15** |
>
> Son **orientativas**, no dogmas: un método de 20 líneas muy cohesivo puede ser mejor que dos de 10 mal separados.

### 🧩 Complejidad ciclomática

Cuenta los **caminos independientes** del método: cada `if`, `else if`, `for`, `while`, `case`, `catch` y operador lógico (`&&`, `||`) suma.

```java
// Complejidad ciclomática = 4 (tres if + camino base)
public String clasificar(int edad) {
    if (edad < 0) return "inválida";
    if (edad < 18) return "menor";
    if (edad < 65) return "adulto";
    return "jubilado";
}
```

> [!tip] Qué hacer si sube
> Extraer condiciones (**Decompose Conditional**), usar **polimorfismo** en lugar de `switch`, extraer bucles y retornos tempranos.

## 💡 Implicaciones: la “objeción” de la delegación

> [!note] Sensación habitual en programadores novatos
> Los nuevos programadores orientados a objetos a menudo sienten que “la computación no se hace en ninguna parte” y que los programas son **secuencias interminables de delegación**.

Con el tiempo se comprende el valor de los métodos pequeños. Todos los **costes de indirección** quedan compensados:

- **Explicación:** el nombre del método documenta la intención.
- **Compartición:** se puede reutilizar en otros contextos.
- **Selección:** se puede sobrescribir o sustituir (polimorfismo).

> [!tip] La indirección es una inversión
> Un método pequeño con un buen nombre **ahorra** tiempo de lectura y de depuración. La “llamada extra” es irrelevante frente al coste de entender un método mal estructurado.

---

## 🔍 Cómo detectarlo

- Método que ocupa **más de una pantalla**.
- **Comentarios** que separan secciones dentro del método.
- **Muchos niveles de anidamiento** (`if` dentro de `for` dentro de `if`…).
- **Variables temporales** que solo se usan en un bloque.
- El nombre del método es **genérico** (`procesar`, `gestionar`, `hacer`) porque hace demasiadas cosas.
- Hay que **desplazarse** para ver el final del método.
- No se puede describir el método sin usar **“y”**.

---

## 🎯 Conclusión para examen

1. **Long Method** = método demasiado largo o complejo, difícil de entender, probar y mantener.
2. **Causa:** métodos antiguos evitaban subrutinas por sobrecarga; hoy no hay excusa.
3. **Solución:** **Extract Method** en el 99 % de los casos; los comentarios y líneas en blanco indican dónde cortar.
4. **Métricas:** 10–15 líneas, 80–120 caracteres por línea y complejidad ciclomática 10–15 como máximos orientativos.
5. **Implicación:** la delegación en métodos pequeños no es un coste, sino una **inversión** en explicación, compartición y selección.

> [!question] Pregunta típica
> *"¿Qué es un método largo y cómo se refactoriza?"*
> **Respuesta:** es un método con demasiadas líneas o responsabilidades que resulta difícil de comprender y mantener. Se refactoriza con **Extract Method**: se localizan bloques cohesivos (a menudo delimitados por comentarios o líneas en blanco), se extraen a métodos cuyo nombre refleja el comentario y se repite hasta que cada método haga una sola cosa. Métricas orientativas: 10–15 líneas y complejidad ciclomática 10–15.
