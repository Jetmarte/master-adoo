# 7. Código sucio por envidia de características

> [!info] Code smell · Feature Envy
> *Refactoring* (Code Smells) — Martin Fowler.
> Relacionado con [[1. Inapropiada intimidad|Inapropiada intimidad]], [[2. Leyes de Demeter|Leyes de Demeter]] y [[5. Codigo sucio por clases de datos|Clases de datos]].

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Feature Envy** | *Refactoring* (Code Smells) — Martin Fowler |
| **Envidia de características / de funcionalidad** | Traducción al español |

## 📖 ¿Qué es?

Un método sufre **envidia de características** cuando **parece más interesado en otra clase que en la suya propia**: usa muchos datos y métodos de otro objeto para hacer su trabajo.

> [!warning] Señal de alarma
> Un método que llama a **media docena de getters** de otro objeto para calcular algo probablemente **quiere estar en ese otro objeto**.

### 🧩 Ejemplo típico

```java
public class Pedido {
    private final Cliente cliente;
    private final List<Producto> productos;

    // ❌ Este método usa sobre todo datos del Cliente
    public double calcularDescuento() {
        double descuento = 0;

        if (cliente.esVIP()) {
            descuento += 0.10;
        }
        if (cliente.getAntiguedadAnios() > 5) {
            descuento += 0.05;
        }
        if (cliente.getComprasUltimoAnio() > 10) {
            descuento += 0.05;
        }

        return descuento;
    }
}
```

`calcularDescuento()` está en `Pedido`, pero **casi todo lo que necesita** (VIP, antigüedad, compras) está en `Cliente`.

---

## ❓ Por qué es un problema (justificación)

- **Rompe la encapsulación:** para calcular algo se accede a muchos detalles internos de otro objeto.
- **Baja cohesión:** la lógica vive en la clase equivocada.
- **Duplicación:** si otro cliente necesita el mismo cálculo, lo copia.
- **Acoplamiento:** `Pedido` queda atado a los datos internos de `Cliente`.
- **Difícil de mantener:** un cambio en `Cliente` obliga a tocar `Pedido`.
- **Contradice el diseño orientado a objetos:** los datos y los procesos que operan sobre ellos deben estar **juntos**.

> [!tip] Idea clave
> La esencia de los objetos es **empaquetar datos con los procesos que usan esos datos**. Si un método usa sobre todo los datos de otro objeto, está en el sitio equivocado.

---

## ✅ Solución

| Técnica | Qué hace |
|---------|----------|
| **Move Method** | Mueve el método completo a la clase cuyos datos usa |
| **Extract Method + Move Method** | Si solo **una parte** del método sufre envidia, se extrae esa parte y se mueve |
| **Move Field** | Si el problema es un campo que se usa desde otra clase, se mueve junto con su lógica |
| **Introduce Parameter Object** | Si el método usa datos de **varias** clases, se agrupan los datos relevantes |

> [!note] ¿A qué clase moverlo?
> - Si el método usa datos de **una** clase → moverlo a **esa** clase.
> - Si usa datos de **varias** clases → colocarlo en la clase que **más atributos aporta** al cálculo.
> - Si los datos de varias clases se usan **conjuntamente**, considerar crear un objeto que los agrupe.

## 🔧 Ejemplo (después): el método vive donde están los datos

```java
public class Cliente {
    private final boolean vip;
    private final int antiguedadAnios;
    private final int comprasUltimoAnio;

    public double calcularDescuento() {
        double descuento = 0;

        if (vip) {
            descuento += 0.10;
        }
        if (antiguedadAnios > 5) {
            descuento += 0.05;
        }
        if (comprasUltimoAnio > 10) {
            descuento += 0.05;
        }

        return descuento;
    }
}
```

```java
public class Pedido {
    private final Cliente cliente;
    private final List<Producto> productos;

    public double calcularTotal() {
        double subtotal = productos.stream()
                .mapToDouble(Producto::getPrecio)
                .sum();

        return subtotal * (1 - cliente.calcularDescuento());
    }
}
```

> [!success] Resultado
> `Cliente` conoce sus propios datos y calcula su descuento. `Pedido` **pregunta** el descuento y aplica el total. El cálculo es **reutilizable** y no accede a los detalles internos del cliente.

## 🧩 Ejemplo: solo una parte del método tiene envidia

```java
// ❌ El método está en Pedido, pero el cálculo del IVA usa datos de Cliente
public double calcularTotal(Pedido pedido) {
    double subtotal = pedido.getProductos().stream()
            .mapToDouble(Producto::getPrecio)
            .sum();

    // Esta parte envidia a Cliente
    double iva = pedido.getCliente().getPais().getIva();

    return subtotal * (1 + iva);
}
```

```java
// ✅ Se extrae la parte envidiosa y se mueve a Cliente
public class Cliente {
    public double getIvaAplicable() {
        return pais.getIva();
    }
}

public class Pedido {
    public double calcularTotal() {
        double subtotal = productos.stream()
                .mapToDouble(Producto::getPrecio)
                .sum();

        return subtotal * (1 + cliente.getIvaAplicable());
    }
}
```

> [!tip] Regla
> No hace falta mover **todo** el método: si solo una parte usa datos ajenos, se extrae esa parte (**Extract Method**) y se mueve (**Move Method**).

## 🧩 Ejemplo: “Tell, don’t ask”

```java
// ❌ Pedir datos y decidir fuera (envidia)
if (cliente.getSaldo() >= importe) {
    cliente.setSaldo(cliente.getSaldo() - importe);
}
```

```java
// ✅ Decirle al objeto que haga la operación
cliente.retirar(importe); // Cliente comprueba su saldo y actualiza su estado
```

Este estilo se conoce como **Tell, don’t ask** (“dile qué hacer, no le preguntes sus datos”) y reduce la envidia de características. También está relacionado con la [[2. Leyes de Demeter|Ley de Demeter]].

---

## 🔍 Cómo detectarlo

- Un método invoca **muchos getters** de otro objeto.
- Hay **cadenas de llamadas**: `pedido.getCliente().getPais().getIva()`.
- El método **no usa** (o usa muy poco) los atributos de su propia clase.
- Al leerlo parece que “está en la clase equivocada”.
- Se repite el mismo cálculo en varias clases porque cada una accede a los datos ajenos.
- El método recibe un objeto y **solo utiliza sus getters**.

---

## ⚠️ Cuándo NO es envidia

> [!warning] No todo uso de otro objeto es envidia
> - Un **servicio** o **repositorio** puede leer datos de varias entidades legítimamente (por ejemplo, un generador de informes).
> - Un **patrón Strategy** o **Visitor** puede necesitar navegar por varios objetos.
> - A veces conviene separar el **cálculo** del **modelo** por motivos de diseño (por ejemplo, lógica de presentación).
>
> El smell aparece cuando el método **depende mayoritariamente** de los datos internos de otra clase y **debería** estar allí por cohesión.

## 🎯 Conclusión para examen

1. **Feature Envy** = método que se interesa más por los datos de **otra clase** que por los de la suya.
2. **Problema:** rompe la encapsulación, baja la cohesión, duplica lógica y acopla clases.
3. **Solución:** **Move Method**; si solo una parte tiene envidia, **Extract Method + Move Method**; si intervienen varias clases, mover a la que más datos aporta.
4. **Criterio:** empaquetar **datos y procesos** en el mismo objeto (**Tell, don’t ask**).
5. **Cuidado:** servicios, informes y patrones como Strategy/Visitor pueden usar varios objetos sin ser envidia.

> [!question] Pregunta típica
> *"¿Qué es la envidia de características y cómo se corrige?"*
> **Respuesta:** es un método que parece más interesado en otra clase porque accede a muchos de sus datos para calcular un valor. Se corrige con **Move Method** (mover el método a la clase cuyos datos usa) o, si solo una parte del método sufre envidia, con **Extract Method + Move Method**. Si los datos vienen de varias clases, se coloca en la que más atributos aporta. Ej.: `Pedido.calcularDescuento()` que usa `cliente.esVIP()`, `getAntiguedad()`… debe pasar a `Cliente`.
