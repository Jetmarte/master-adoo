# 4. Código sucio por clases alternativas con interfaces diferentes

> [!info] Code smell · Alternative Classes with Different Interfaces
> *Refactoring* (Code Smells) — Martin Fowler.
> Relacionado con [[6. Patron metodo plantilla|Método Plantilla]], [[1. Principio de sustitucion de LISCOV|LSP]] y [[7. Principio No te repitas DRY|DRY]].

---

## 🏷️ Sinónimos

| Término | Fuente |

---

## 📖 ¿Qué es?

Dos o más clases realizan **la misma función** (o funciones equivalentes), pero exponen **interfaces distintas**: métodos con nombres diferentes, parámetros diferentes o responsabilidades repartidas de forma inconsistente.

> [!warning] Señal de alarma
> El cliente se ve obligado a escribir **código condicional** para usar una u otra clase, o a recordar “con esta clase se llama así y con la otra asá”.

### 🧩 Ejemplo típico

```java
public class RepositorioClientesMySQL {
    public void guardarCliente(Cliente cliente) { /* ... */ }
    public Cliente buscarClientePorId(int id) { /* ... */ }
}

public class RepositorioClientesMongo {
    public void insertar(Cliente cliente) { /* ... */ }
    public Cliente obtener(int id) { /* ... */ }
}
```

El cliente tiene que saber **qué implementación** está usando:

```java
// ❌ El cliente conoce los detalles de cada clase
if (configuracion.usaMySQL()) {
    repositorioMySQL.guardarCliente(cliente);
} else {
    repositorioMongo.insertar(cliente);
}
```

---

## ❓ Por qué es un problema (justificación)

- **Complejidad innecesaria**: el cliente debe conocer varias interfaces para hacer lo mismo.
- **Código duplicado**: se repiten bucles, validaciones y condiciones en los clientes.
- **Difícil de sustituir**: no se puede intercambiar una clase por otra sin tocar al cliente.
- **Mantenimiento frágil**: un cambio en una clase obliga a revisar todos los `if/else` que la usan.
- **Viola **DRY** y dificulta cumplir **LSP** (no son sustituibles entre sí).

> [!tip] Idea clave
> Si dos clases son **alternativas** (hacen lo mismo), deben ofrecer **la misma interfaz**. Así el cliente depende de la **abstracción**, no de la implementación concreta.

---

## ✅ Solución

| Técnica | Cuándo usarla |
|---------|---------------|
| **Rename Method** | Los métodos hacen lo mismo pero se llaman distinto (`guardar` vs `insertar`) |
| **Move Method / Move Field** | Una responsabilidad está en la clase equivocada; se mueve hasta que ambas interfaces coincidan |
| **Extract Superclass** | Las clases comparten comportamiento e interfaz; se crea una superclase común |
| **Extract Interface** | Solo comparten la interfaz, no la implementación; se extrae una interfaz |
| **Método Plantilla** | El esqueleto del algoritmo es común y solo cambian algunos pasos |

> [!note] Pasos prácticos
> 1. **Renombrar** los métodos que hacen lo mismo para que tengan el mismo nombre.
> 2. **Mover** responsabilidades hasta que las clases hagan lo mismo con los mismos nombres (**homogeneizar**).
> 3. **Extraer** una superclase o una interfaz común y hacer que los clientes dependan de ella.

---

## 🔧 Ejemplo (después): interfaz común

```java
// Abstracción común: el cliente solo conoce esta interfaz
public interface RepositorioClientes {
    void guardar(Cliente cliente);
    Optional<Cliente> buscarPorId(int id);
}
```

```java
public class RepositorioClientesMySQL implements RepositorioClientes {
    @Override
    public void guardar(Cliente cliente) { /* ... */ }

    @Override
    public Optional<Cliente> buscarPorId(int id) { /* ... */ }
}
```

```java
public class RepositorioClientesMongo implements RepositorioClientes {
    @Override
    public void guardar(Cliente cliente) { /* ... */ }

    @Override
    public Optional<Cliente> buscarPorId(int id) { /* ... */ }
}
```

```java
// ✅ El cliente ya no necesita saber qué implementación usa
public class ServicioClientes {
    private final RepositorioClientes repositorio;

    public ServicioClientes(RepositorioClientes repositorio) {
        this.repositorio = repositorio;
    }

    public void registrar(Cliente cliente) {
        repositorio.guardar(cliente);
    }
}
```

> [!success] Resultado
> Se elimina el `if/else`, el cliente depende de una **interfaz estable** y se pueden añadir nuevas implementaciones sin tocar el código cliente (**[[6. Principio abierto - cerrado|Open/Closed]]**).

## 🧩 Ejemplo del temario: `PutController` y `MoveController`

Ambos controladores realizan **semánticamente la misma función de control**, pero exponen métodos distintos (`put` y `move`):

```java
// ❌ Interfaces diferentes para la misma responsabilidad
public class PutController {
    public void put(Coordinate coordinate) { /* colocar ficha */ }
}

public class MoveController {
    public void move(Coordinate origin, Coordinate destination) { /* mover ficha */ }
}
```

Solución del temario:

- **Homogeneizar** los métodos.
- Crear una jerarquía de herencia con una clase base `ColocateController`.
- Aplicar **Método Plantilla**: la superclase define el esqueleto y las subclases implementan los pasos variables.

```java
// ✅ Interfaz homogénea con Método Plantilla (ejemplo simplificado)
public abstract class ColocateController {
    public final void colocar(Coordinate origen, Coordinate destino) {
        validar(origen, destino);
        ejecutarColocacion(origen, destino);
        actualizarVista();
    }

    protected abstract void ejecutarColocacion(Coordinate origen, Coordinate destino);
    protected abstract void actualizarVista();

    private void validar(Coordinate origen, Coordinate destino) { /* común */ }
}

public class PutController extends ColocateController {
    @Override
    protected void ejecutarColocacion(Coordinate origen, Coordinate destino) {
        // colocar ficha en destino
    }

    @Override
    protected void actualizarVista() { /* ... */ }
}

public class MoveController extends ColocateController {
    @Override
    protected void ejecutarColocacion(Coordinate origen, Coordinate destino) {
        // mover ficha de origen a destino
    }

    @Override
    protected void actualizarVista() { /* ... */ }
}
```

---

## 🔍 Cómo detectarlo

- Dos clases con **métodos equivalentes y nombres distintos**: `guardar` / `insertar` / `add` / `save`.
- Clientes con **`if/else` o `switch`** para elegir entre clases alternativas.
- **Parámetros en distinto orden** o con distinto tipo para la misma operación.
- Una clase tiene la responsabilidad que **debería estar** en la otra.
- Al cambiar una clase, hay que cambiar **también** la otra para mantener la coherencia.

---

## 🎯 Conclusión para examen

1. **Clases alternativas con interfaces diferentes** = clases que hacen lo mismo pero el cliente las usa de forma distinta.
2. **Problema:** complejidad innecesaria, código duplicado, difícil sustitución y mantenimiento.
3. **Solución:** **renombrar** métodos equivalentes, **mover** responsabilidades para homogeneizar y **extraer** una superclase o interfaz común.
4. En el temario, `PutController` y `MoveController` se unifican con **herencia** y **Método Plantilla** sobre `ColocateController`.
5. El cliente debe depender de la **abstracción**, no de las clases concretas.

> [!question] Pregunta típica
> *"¿Qué es el smell 'Alternative Classes with Different Interfaces' y cómo se corrige?"*
> **Respuesta:** son clases que realizan la misma función pero exponen interfaces distintas (p. ej. `guardarCliente` vs `insertar`). Provoca `if/else` en los clientes y código duplicado. Se corrige **renombrando** los métodos equivalentes, **moviendo** responsabilidades hasta homogeneizarlas y **extrayendo una superclase o interfaz común**; en el temario se aplica con `ColocateController` y **Método Plantilla**.
