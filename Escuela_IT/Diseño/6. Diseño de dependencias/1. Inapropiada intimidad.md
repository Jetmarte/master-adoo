# 1. Inapropiada intimidad

> [!info] Code smell · Inapropiada intimidad (Inappropriate Intimacy)
> *Refactoring* — Martin Fowler · Relacionado con [[2. Leyes de Demeter|Leyes de Demeter]], [[5. Principio de inversion de dependencias|Inversión de dependencias]] y [[2. Relacion de herencia vs composicion|Herencia vs composición]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Inappropriate Intimacy** | *Refactoring* (Code Smells) — Martin Fowler |
| **Sobre-intimidad / Intimidad inapropiada** | Traducción habitual al español |
| **Clases íntimas** | Clases que se conocen demasiado entre sí |

---

## 📖 ¿Qué es?

Dos clases mantienen una **relación demasiado estrecha**: una **husmea en las partes privadas** de la otra y depende de sus detalles internos.

Se manifiesta de varias formas:

- **Relaciones bidireccionales:** `Cliente` conoce sus `Pedido`s y cada `Pedido` conoce a su `Cliente`.
- **Acceso a atributos internos** a través de *getters/setters* para manipular el estado ajeno.
- **Colecciones internas expuestas** que el exterior modifica a su antojo.
- **Herencia abusiva:** la subclase conoce y usa detalles de la superclase que no le corresponden.
- **Cadenas de mensajes:** `a.getB().getC().hacer()` (ver [[2. Leyes de Demeter|Leyes de Demeter]]).

> [!warning] Señal de alarma
> Si para cambiar una clase tienes que **tocar otra**, o si una clase **sabe cómo está implementada** otra, hay sobre-intimidad. Las clases deberían ser *estrictas con reglas puritanas*: cada una guarda sus secretos.

---

## ❓ Por qué es un problema (justificación)

- **Acoplamiento fuerte:** un cambio en una clase arrastra a la otra.
- **Dificulta las pruebas:** hay que construir y coordinar dos objetos a la vez.
- **Rompe la encapsulación:** los invariantes se pueden violar desde fuera.
- **Baja legibilidad:** la lógica de un concepto aparece repartida entre varias clases.
- **Relaciones cíclicas:** complican la serialización, el empaquetado y la comprensión del diseño.
- **Herencia frágil:** la subclase depende de detalles que la superclase puede cambiar.
- **Dificulta la reutilización:** una clase íntima no se puede usar sin arrastrar a la otra.

> [!tip] Idea clave
> Una relación **unidireccional** y **explícita** es más fácil de entender, probar y cambiar que una relación bidireccional mantenida a mano.

---

## 🔍 Cómo detectarla

- Atributos de una clase que **apuntan a otra** y viceversa.
- Métodos que **leen y escriben** atributos ajenos mediante *getters/setters*.
- El exterior **modifica colecciones internas** (`objeto.getLista().add(...)`).
- Subclases que usan **atributos protegidos** o métodos pensados para uso interno.
- **Feature Envy:** un método usa más datos de otra clase que de la suya.
- Cadenas largas de llamadas: `cliente.getDireccion().getCiudad().getPais()`.

> [!note] Test rápido
> Pregúntate: *¿esta clase podría funcionar y probarse sin conocer los detalles internos de la otra?* Si la respuesta es no, la intimidad es excesiva.

## 💥 Ejemplo 1 (antes): relación bidireccional

```java
public class Cliente {
    private final List<Pedido> pedidos = new ArrayList<>();

    public void addPedido(Pedido pedido) {
        pedidos.add(pedido);
        pedido.setCliente(this);          // mantiene la relación a mano
    }

    public List<Pedido> getPedidos() {
        return pedidos;
    }
}

public class Pedido {
    private Cliente cliente;

    public void setCliente(Cliente cliente) {
        this.cliente = cliente;
    }

    public Cliente getCliente() {
        return cliente;
    }
}
```

> [!danger] Problemas
> - La consistencia depende de que **ambos lados** se actualicen a la vez.
> - Se pueden crear estados incoherentes: un `Pedido` con `cliente == null` o un `Cliente` que no conoce un pedido suyo.
> - Aparece una **referencia circular** que complica la serialización y las pruebas.
> - El `Cliente` conoce detalles de `Pedido` y viceversa.

---

## ✅ Solución 1: romper la bidireccionalidad

Se elige **un único dueño de la relación** y el otro lado se consulta a través de un repositorio o servicio.

```java
public class Pedido {
    private final Cliente cliente;

    public Pedido(Cliente cliente) {
        this.cliente = Objects.requireNonNull(cliente);
    }

    public Cliente getCliente() {
        return cliente;
    }
}

public class Cliente {
    // Ya no guarda la lista de pedidos: no hay referencia de vuelta
}
```

```java
public class PedidoRepository {
    public List<Pedido> findByCliente(Cliente cliente) {
        // consulta los pedidos del cliente
    }
}
```

> [!success] Resultado
> La relación es **unidireccional**: `Pedido → Cliente`. Solo hay un punto donde se crea la relación, no hay ciclos y cada clase se prueba por separado.

## 🔧 Solución 2: mover métodos y atributos (Move Method / Move Field)

El clásico del tres en raya: `Coordinate` miraba dentro de `Board` para validarse.

```java
// ❌ Antes: Board y Coordinate se conocen mutuamente
public class Board {
    public static final int DIMENSION = 3;
    private final Coordinate[] casillas;
}

public class Coordinate {
    private int x, y;

    public boolean isValid() {
        return x >= 0 && x < Board.DIMENSION
            && y >= 0 && y < Board.DIMENSION;   // depende de Board
    }
}
```

```java
// ✅ Después: DIMENSION vive donde pertenece
public class Coordinate {
    public static final int DIMENSION = 3;
    private final int x, y;

    public Coordinate(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public boolean isValid() {
        return x >= 0 && x < DIMENSION
            && y >= 0 && y < DIMENSION;
    }
}

public class Board {
    private final Coordinate[] casillas =
        new Coordinate[Coordinate.DIMENSION * Coordinate.DIMENSION];
}
```

> [!note] Resultado
> Solo queda `Board → Coordinate`. Se ha **movido el atributo** (la constante) a la clase que realmente lo delimita.

## 🔧 Solución 3: extraer una clase con los intereses comunes (Extract Class)

Cuando dos clases **comparten un interés** y ambas lo manipulan, se extrae ese interés a una **tercera clase** y las demás pasan a ser **honestas** sobre ella.

```java
// ❌ Antes: Cliente manipula el saldo interno de Cuenta
public class Cuenta {
    private double saldo;

    public double getSaldo() { return saldo; }
    public void setSaldo(double saldo) { this.saldo = saldo; }
}

public class Cliente {
    private final List<Cuenta> cuentas = new ArrayList<>();

    public void aplicarInteres(Cuenta cuenta) {
        double saldo = cuenta.getSaldo();
        cuenta.setSaldo(saldo + saldo * 0.02);   // husmea en Cuenta
    }
}
```

```java
// ✅ Después: el interés (Dinero) se encapsula y Cuenta ofrece comportamiento
public record Dinero(BigDecimal cantidad) {
    public Dinero mas(Dinero otro) {
        return new Dinero(cantidad.add(otro.cantidad));
    }

    public Dinero por(BigDecimal factor) {
        return new Dinero(cantidad.multiply(factor));
    }
}

public class Cuenta {
    private Dinero saldo;

    public Dinero saldo() { return saldo; }

    public void aplicarInteres(BigDecimal tasa) {
        saldo = saldo.mas(saldo.por(tasa));
    }
}

public class Cliente {
    private final List<Cuenta> cuentas = new ArrayList<>();

    public void aplicarInteres(Cuenta cuenta, BigDecimal tasa) {
        cuenta.aplicarInteres(tasa);   // "dilo, no lo preguntes"
    }
}
```

> [!tip] Tell, Don't Ask
> En lugar de **preguntar** por el estado y modificarlo desde fuera, se **dice** al objeto que haga la operación. Así la lógica vive con los datos que protege.

## 🔧 Solución 4: ocultar los detalles internos (Hide Delegate / Encapsulate Collection)

```java
// ❌ Antes: el exterior modifica la lista interna
public class Curso {
    private final List<Alumno> alumnos = new ArrayList<>();

    public List<Alumno> getAlumnos() {
        return alumnos;   // devuelve la colección real
    }
}

public class Secretaria {
    public void matricular(Curso curso, Alumno alumno) {
        curso.getAlumnos().add(alumno);   // salta las reglas de Curso
    }
}
```

```java
// ✅ Después: Curso controla sus invariantes
public class Curso {
    private final List<Alumno> alumnos = new ArrayList<>();

    public void matricular(Alumno alumno) {
        if (alumnos.contains(alumno)) {
            throw new IllegalStateException("El alumno ya está matriculado");
        }
        alumnos.add(alumno);
    }

    public List<Alumno> alumnos() {
        return List.copyOf(alumnos);   // copia inmutable
    }
}
```

> [!note] Resultado
> El exterior ya **no puede violar** las reglas de `Curso`. Solo se ofrece lo necesario y en modo lectura.

## 🔧 Solución 5: sustituir herencia por delegación

La herencia hace que la subclase **conozca demasiado** de la superclase.

```java
// ❌ Antes: Pila hereda toda la interfaz de ArrayList
public class Pila<T> extends ArrayList<T> {
    public void push(T elemento) { add(elemento); }
    public T pop() { return remove(size() - 1); }
}
```

> [!danger] Problemas
> `Pila` hereda `add(int, T)`, `remove(Object)`, `clear()`… Cualquiera puede **saltarse la disciplina LIFO**. Además, la subclase depende de la implementación de `ArrayList`.

```java
// ✅ Después: composición + delegación
public class Pila<T> {
    private final List<T> elementos = new ArrayList<>();

    public void push(T elemento) { elementos.add(elemento); }

    public T pop() {
        if (elementos.isEmpty()) {
            throw new NoSuchElementException("La pila está vacía");
        }
        return elementos.remove(elementos.size() - 1);
    }

    public int tamanio() { return elementos.size(); }
}
```

> [!note] Resultado
> `Pila` solo expone su **contrato** (`push`, `pop`, `tamanio`) y depende de la **interfaz `List`**, no de una implementación concreta. Ver [[2. Relacion de herencia vs composicion|Herencia vs composición]].

## 📋 Resumen de refactorizaciones

| Técnica | Cuándo usarla |
|---------|---------------|
| **Change Bidirectional Association to Unidirectional** | Dos clases se apuntan mutuamente y solo un lado necesita la navegación |
| **Move Method / Move Field** | Un método o atributo usa más datos de otra clase que de la suya |
| **Extract Class** | Las clases comparten un interés que conviene aislar |
| **Hide Delegate** | Se expone un objeto interno para que otros lo manipulen |
| **Encapsulate Collection** | Se devuelve una colección interna mutable |
| **Replace Inheritance with Delegation** | La subclase solo reutiliza comportamiento y no es realmente un subtipo |

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Cuidado |
|---------------|------------|
| **Menor acoplamiento** entre clases | No toda relación bidireccional es mala: en ORM (JPA/Hibernate) a veces se necesita y se gestiona con `mappedBy` |
| **Encapsulación real** de los invariantes | Encapsular en exceso puede generar *getters* y *setters* triviales |
| **Pruebas unitarias** más sencillas | Demasiada delegación añade **indirección** y llamadas extra |
| **Cambios localizados** | Si el dominio exige navegación en ambos sentidos, valora el coste antes de romperla |
| **Mejor legibilidad** del diseño | No aplicar a ciegas: [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]] |

## ✅ Conclusión para examen

1. **Inapropiada intimidad** = dos clases se **conocen demasiado** y dependen de los detalles internos de la otra.
2. Síntomas típicos: **relaciones bidireccionales**, acceso a colecciones internas, **Feature Envy**, herencia abusiva y **cadenas de mensajes**.
3. Es un problema de **acoplamiento, encapsulación, pruebas y legibilidad**.
4. **Soluciones:** pasar de **bidireccional a unidireccional**, **mover** métodos/atributos, **extraer** una clase con lo común, **ocultar** detalles y **sustituir herencia por delegación**.
5. **Cuidado:** no romper relaciones que el dominio realmente necesita; evitar la indirección innecesaria.

> [!question] Pregunta típica
> *"¿Qué es la inapropiada intimidad y cómo se corrige?"*
> **Respuesta:** es un *code smell* en el que dos clases están demasiado acopladas y una conoce los detalles internos de la otra (relaciones bidireccionales, acceso a atributos/colecciones internas, herencia abusiva). Se corrige rompiendo la bidireccionalidad, moviendo métodos y atributos a la clase que corresponde, extrayendo una clase para los intereses comunes, ocultando delegados y sustituyendo la herencia por delegación.

---

> [!quote] Martin Fowler
> *"Algunas clases llegan a alcanzar demasiada intimidad y gastan mucho tiempo ahondando en las partes privadas de otras clases. Nosotros pensamos que nuestras clases deberían ser estrictas con reglas puritanas."*
