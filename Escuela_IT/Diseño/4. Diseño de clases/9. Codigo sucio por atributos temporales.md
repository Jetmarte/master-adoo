# 9. Código sucio por atributos temporales

> [!info] Code smell · Atributos temporales (Temporary Field)
> Relacionado con [[1. Codigo sucio por clases grandes|Clase grande]] · [[4. Codigo sucio por grupos de datos|Data Clumps]] · [[10. Principio de unica responsabilidad|SRP]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Temporary Field** | *Refactoring* (Code Smells) — Martin Fowler |
| **Atributos temporales / Campos temporales** | Traducción habitual al español |
| **Objeto método** | *Method Object* — Kent Beck (la solución) |

---

## 📖 ¿Qué es?

A veces se ve un objeto en el que **una variable de instancia solo se establece y se usa en ciertas circunstancias**. En el resto de la vida del objeto está **vacía, a `null` o sin sentido**.

> [!warning] Señal de alarma
> Tú esperas que un objeto **necesite todas sus variables**. Cuando ves un campo que **a veces está y a veces no**, te preguntas: *"¿por qué está aquí? ¿cuándo es válido?"*. Esa incertidumbre genera **complejidad innecesaria**.

> [!tip] El caso más común
> Un **algoritmo complicado** necesita varias variables auxiliares. Como el autor **no quería pasar una lista enorme de parámetros**, las guardó como **atributos** del objeto. Pero esos atributos **solo son válidos durante la ejecución del algoritmo**; en cualquier otro contexto **confunden**.

---

## ❓ Por qué es un problema (justificación)

- **Código difícil de comprender:** no sabes cuándo un campo es válido y cuándo no.
- **Estado inconsistente:** el objeto puede existir con campos "a medias".
- **Errores silenciosos:** si usas el campo fuera de su contexto, obtienes `null` o un valor viejo.
- **Acoplamiento oculto:** los métodos dependen de un estado que solo algunos flujos establecen.
- **Difícil de testear:** hay que reproducir el flujo exacto que inicializa los campos.
- **Baja cohesión:** el objeto mezcla el "estado permanente" con el "estado de un cálculo puntual".

---

## 🔍 Cómo detectarla

Señales típicas:

- Campos que **solo se asignan dentro de un método** (`calcular()`, `procesar()`) y no en el constructor.
- Campos que son **`null` la mayor parte del tiempo**.
- Métodos que empiezan comprobando si un campo está inicializado.
- Comentarios como `// solo válido durante calcular()`.
- **Muchos parámetros** que, en lugar de pasarse, se guardaron como atributos para no escribir una firma larga.
- Un campo que solo tiene sentido **junto con otro** dentro de una misma operación.

---

## 💥 Ejemplo (antes): `CalculadoraNomina` con estado temporal

```java
public class CalculadoraNomina {
    private double salarioBase;
    private int horasExtra;
    private double resultadoParcial;   // solo válido durante calcular()
    private double descuentoAplicado;  // solo válido durante calcular()

    public double calcular(double salarioBase, int horasExtra) {
        this.salarioBase = salarioBase;
        this.horasExtra = horasExtra;
        this.resultadoParcial = salarioBase;

        aplicarHorasExtra();
        aplicarDescuentos();

        double total = resultadoParcial;
        // limpiamos "a mano" para no dejar basura
        this.resultadoParcial = 0;
        this.descuentoAplicado = 0;
        return total;
    }

    private void aplicarHorasExtra() {
        resultadoParcial += horasExtra * 15.0;
    }

    private void aplicarDescuentos() {
        descuentoAplicado = resultadoParcial * 0.07;
        resultadoParcial -= descuentoAplicado;
    }
}
```

> [!danger] Problemas
> `resultadoParcial` y `descuentoAplicado` **solo existen durante `calcular()`**. Si otro método los lee, obtiene basura o un valor viejo. La clase **no es segura entre llamadas** y el autor tiene que **limpiarlos a mano**. Además, el estado temporal **no tiene nada que ver** con la responsabilidad permanente de la calculadora.

---

## ✅ Solución

> [!success] Regla general
> **Extraer en una clase los atributos y los métodos que los requieren.** El nuevo objeto es un **objeto método** (*Method Object*): vive **solo durante el cálculo**, encapsula su estado temporal y desaparece al terminar.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Extract Class** (Extraer clase) | Los atributos temporales forman un concepto con sus métodos |
| **Replace Method with Method Object** | Un algoritmo complejo usa muchos campos temporales → convertirlo en objeto método |
| **Introduce Null Object** | El campo "a veces está" puede sustituirse por un objeto neutro con el mismo contrato |
| **Encapsulate Field / Optional** | El campo es legítimamente opcional → modelarlo explícitamente |
| **Replace Temp with Query** | El temporal se calcula y solo se usa dentro de un método |

## 🔧 Ejemplo (después): objeto método `CalculoNomina`

```java
// El estado temporal vive en un objeto que solo dura el cálculo
public final class CalculoNomina {
    private final double salarioBase;
    private final int horasExtra;
    private double resultado;

    public CalculoNomina(double salarioBase, int horasExtra) {
        this.salarioBase = salarioBase;
        this.horasExtra = horasExtra;
        this.resultado = salarioBase;
    }

    public double ejecutar() {
        aplicarHorasExtra();
        aplicarDescuentos();
        return resultado;
    }

    private void aplicarHorasExtra() {
        resultado += horasExtra * 15.0;
    }

    private void aplicarDescuentos() {
        resultado -= resultado * 0.07;
    }
}
```

```java
// La calculadora ya no guarda estado temporal
public class CalculadoraNomina {
    public double calcular(double salarioBase, int horasExtra) {
        return new CalculoNomina(salarioBase, horasExtra).ejecutar();
    }
}
```

> [!note] Resultado
> Los campos temporales **desaparecen de `CalculadoraNomina`**. `CalculoNomina` nace, calcula y muere: su estado es **válido durante toda su vida** y no queda basura entre llamadas. El algoritmo complejo queda **aislado, testeable y comprensible**.

---

## 🔁 Variante: campo opcional legítimo → `Null Object` / `Optional`

No todo campo que "a veces no está" es un smell. Si el concepto es **realmente opcional**, mode(l)lo explícitamente:

```java
// ❌ Antes: descuento puede ser null y todos los métodos lo comprueban
class Pedido {
    private Descuento descuento; // puede ser null
    double total() {
        return descuento == null ? base : base - descuento.aplicar(base);
    }
}
```

```java
// ✅ Después: Null Object con el mismo contrato
interface Descuento { double aplicar(double base); }

class SinDescuento implements Descuento {
    public double aplicar(double base) { return base; }
}

class Pedido {
    private final Descuento descuento;
    Pedido(Descuento descuento) { this.descuento = descuento; }
    double total() { return descuento.aplicar(base); }
}
```

> [!tip] Regla práctica
> Si el campo es **parte de un cálculo puntual**, extráelo a un **objeto método**. Si es **una opción real del dominio**, usa **Null Object** o un `Optional`. Lo que **no** debe pasar es que el resto de la clase tenga que preguntar *"¿este campo está inicializado?"*.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| El objeto principal queda **sin estado temporal** | Crear un objeto por cálculo puede tener **coste** (normalmente despreciable) |
| Algoritmo **aislado y testeable** | En **código muy simple**, extraer una clase puede ser excesivo |
| No hay **basura entre llamadas** | Si el campo es **opcional de verdad**, mejor `Null Object`/`Optional` que extraer |
| Mejor **cohesión** y comprensión | Un objeto método **por cada cálculo** puede multiplicar clases |

> [!warning] No confundir con caché
> Un campo que se calcula **de forma perezosa y se reutiliza** (caché) **no es** un atributo temporal: es una optimización legítima. El smell es cuando el campo **solo tiene sentido en un contexto** y el resto del tiempo **estorba**.

## ✅ Conclusión para examen

1. **Temporary Field** = variable de instancia que **solo se usa en ciertas circunstancias** (a menudo, dentro de un algoritmo).
2. Es un problema de **comprensión y estado inconsistente**: no se sabe cuándo el campo es válido.
3. **Detección:** campos asignados solo dentro de un método, campos casi siempre `null`, comentarios "solo válido durante…", parámetros convertidos en atributos para acortar la firma.
4. **Solución:** **Extract Class** o **Replace Method with Method Object** (objeto método), de modo que el estado temporal viva en un objeto que **solo dura el cálculo**; si el campo es opcional de verdad, **Null Object**/`Optional`.
5. **Cuidado:** no confundir con caché perezosa legítima ni extraer clases para cálculos triviales.

> [!question] Pregunta típica
> *"¿Qué es un Temporary Field y cómo se corrige?"*
> **Respuesta:** es un atributo que solo tiene sentido en ciertas circunstancias, normalmente durante la ejecución de un algoritmo complejo, y que el resto del tiempo está vacío o confunde. Se detecta porque el campo solo se asigna dentro de un método o suele ser `null`. Se corrige **extrayendo los atributos y sus métodos a una nueva clase** (objeto método) que viva solo durante el cálculo (Extract Class / Replace Method with Method Object); si el campo es una opción real, se modela con **Null Object** o `Optional`.
