# 2. Código sucio por clases perezosas

> [!info] Code smell · Clase perezosa (Lazy Class)
> Relacionado con [[1. Codigo sucio por clases grandes|Clase grande]] · [[5. Codigo sucio por clases de datos|Clase de datos]] · [[10. Principio de unica responsabilidad|SRP]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Lazy Class** | *Refactoring* (Code Smells) — Martin Fowler |
| **Clase perezosa / Clase vaga** | Traducción habitual al español |
| **Clase artificial** | Nombre coloquial: se creó "por si acaso" |

---

## 📖 ¿Qué es?

Una **clase perezosa** es una clase que **no hace lo suficiente para justificar su existencia**: ocupa espacio en el diseño, añade complejidad, pero apenas tiene lógica o responsabilidad real.

Suele aparecer por dos caminos:

1. **Sobró después de refactorizar:** antes tenía responsabilidades, se las quitaron y quedó vacía.
2. **Se creó para un futuro que nunca llegó:** "algún día tendrá más lógica" (pero ese día no llega).

> [!warning] Señal de alarma
> Cada clase que se crea **cuesta dinero mantenerla y entenderla**. Si una clase no aporta lo suficiente, está cobrando un precio sin dar valor.

---

## ❓ Por qué es un problema (justificación)

- **Cuesta entenderla y mantenerla** sin aportar nada a cambio.
- **Aumenta el número de clases** y obliga a navegar entre archivos triviales.
- **Rompe la regla de la mínima abstracción:** no crear más abstracciones de las necesarias.
- Puede **ocultar** que una responsabilidad está mal ubicada (delegación excesiva).
- Si es parte de una jerarquía, **complica el modelo** sin añadir polimorfismo útil.

> [!tip] Idea clave
> Una clase debe **ganarse su sitio**. Si solo guarda dos datos o reenvía llamadas a otra clase, probablemente **no debería existir**.

---

## 🔍 Cómo detectarla

Señales típicas:

- Tiene **muy pocos métodos** (uno o dos, o solo getters/setters).
- Sus métodos son **triviales** y **delegan casi todo** en otra clase.
- Solo se usa en **un único lugar**.
- No tiene **invariantes** ni reglas propias: no valida, no calcula, no protege nada.
- Su nombre describe un **campo**, no un concepto con comportamiento (`Datos`, `Wrapper`, `Helper`).
- Fue una subclase que ya no aporta nada distinto a su superclase.

---

## 💥 Ejemplo (antes): una `Direccion` que solo guarda datos

```java
class Direccion {
    private String calle;
    private String ciudad;

    Direccion(String calle, String ciudad) {
        this.calle = calle;
        this.ciudad = ciudad;
    }

    String getCalle() { return calle; }
    String getCiudad() { return ciudad; }
}

class Cliente {
    private String nombre;
    private Direccion direccion;

    Cliente(String nombre, String calle, String ciudad) {
        this.nombre = nombre;
        this.direccion = new Direccion(calle, ciudad);
    }

    String mostrarInfo() {
        return nombre + ", " + direccion.getCalle() + ", " + direccion.getCiudad();
    }
}
```

> [!danger] Problemas
> `Direccion` **no valida, no normaliza y no calcula nada**: solo es una bolsa de dos Strings. La clase `Cliente` sigue accediendo a `getCalle()`/`getCiudad()` para hacer el trabajo. La abstracción no aporta comportamiento, solo **indirección**.

---

## ✅ Solución

> [!success] Regla general
> **Asignar la escasa responsabilidad a otra clase y dejar morir la clase con dignidad.** Si forma parte de una jerarquía y no aporta nada, **contraer la jerarquía**.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Inline Class** (Integrar clase) | La clase solo se usa en un lugar y no aporta comportamiento |
| **Collapse Hierarchy** (Colapsar jerarquía) | Una subclase no añade nada a la superclase |
| **Inline Method** | Un método solo reenvía a otro |
| **Eliminar directamente** | La clase no cumple ninguna función |
| **Extract Class** (la solución *contraria*) | La clase es perezosa **hoy**, pero el grupo de datos empieza a tener comportamiento propio |

> [!tip] Heurística práctica
> Antes de eliminarla, pregúntate: **¿tiene invariantes o reglas propias?** Si la respuesta es sí (validar un CP, calcular un impuesto), entonces el problema no es la clase, sino que **le falta comportamiento** → auméntalo. Si es no, elimínala.

## 🔧 Ejemplo (después)

### Opción A – Integrar la clase en `Cliente` (Inline Class)

```java
class Cliente {
    private String nombre;
    private String calle;
    private String ciudad;

    Cliente(String nombre, String calle, String ciudad) {
        this.nombre = nombre;
        this.calle = calle;
        this.ciudad = ciudad;
    }

    String mostrarInfo() {
        return nombre + ", " + calle + ", " + ciudad;
    }
}
```

### Opción B – Darle una responsabilidad real (la clase deja de ser perezosa)

```java
class Direccion {
    private final String calle;
    private final String ciudad;
    private final String codigoPostal;

    Direccion(String calle, String ciudad, String codigoPostal) {
        if (calle == null || calle.isBlank()) {
            throw new IllegalArgumentException("La calle es obligatoria");
        }
        if (!codigoPostal.matches("\\d{5}")) {
            throw new IllegalArgumentException("CP inválido");
        }
        this.calle = calle;
        this.ciudad = ciudad;
        this.codigoPostal = codigoPostal;
    }

    String formateada() {
        return calle + ", " + codigoPostal + " " + ciudad;
    }
}
```

> [!note] Resultado
> En la **opción A** desaparece una clase que no aportaba nada. En la **opción B** la clase se justifica porque **valida y formatea** (tiene invariantes y comportamiento). En ambos casos el diseño queda más simple o más rico, pero **sin clases de relleno**.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios de eliminarla | ⚠️ Contraindicaciones / cuidado |
|------------------------------|----------------------------------|
| Menos clases y **menos navegación** | Si la clase **puede crecer** y ya tiene un concepto claro, quizá conviene mantenerla |
| Diseño más **simple y honesto** | En **DTOs, entidades JPA o serialización** una clase "solo de datos" es legítima |
| Se elimina **indirección inútil** | Eliminar una clase usada en **muchos sitios** puede generar un cambio grande |
| Se detectan responsabilidades **mal ubicadas** | No confundir "poca lógica *hoy*" con "no debe existir" (YAGNI al revés) |

> [!warning] No eliminar por eliminar
> Una clase pequeña pero con **una responsabilidad clara y futura** (por ejemplo, un Value Object que valida) **no es perezosa**. El smell es cuando **no aporta ni aportará** valor.

## ✅ Conclusión para examen

1. **Clase perezosa (Lazy Class)** = clase que **no justifica su existencia** por su escasa responsabilidad.
2. Es un problema de **coste y complejidad**: mantener clases vacías encarece el diseño.
3. **Detección:** pocos métodos, solo getters/setters, delega casi todo, se usa en un solo lugar, no tiene invariantes.
4. **Solución:** **Inline Class**, **Collapse Hierarchy**, eliminar; o bien **darle comportamiento real** si el concepto lo merece.
5. **Cuidado:** DTOs y entidades de persistencia son "clases de datos" legítimas; no toda clase pequeña es perezosa.

> [!question] Pregunta típica
> *"¿Qué es una Lazy Class y cómo se corrige?"*
> **Respuesta:** es una clase que no hace lo suficiente para justificar su coste (pocos métodos, solo getters/setters, delega todo). Se corrige **integrándola** en la clase que la usa (*Inline Class*), **colapsando la jerarquía** si es una subclase vacía, **eliminándola**, o dándole **comportamiento e invariantes** si el concepto lo merece. Ej.: `Direccion` con solo `calle` y `ciudad` → integrarla en `Cliente` o añadirle validación y formateo.
