# 10. Principio de única responsabilidad

> [!info] Principio SOLID · SRP (Single Responsibility Principle)
> Definido por **Robert C. Martin (Uncle Bob)** · Relacionado con [[8. Codigo sucio por Cambios Divergentes|Divergent Change]] · [[1. Codigo sucio por clases grandes|Clase grande]]

---

## 🏷️ Origen y sinónimos

| Término | Fuente |
|---------|--------|
| **Single Responsibility Principle (SRP)** | Robert C. Martin — uno de los principios **SOLID** |
| **Principio de responsabilidad única** | Traducción habitual al español |
| **Cohesión** | DeMarco y Page-Jones: *relación funcional de los elementos de un módulo* |

> [!note] De la cohesión a la razón de cambio
> El SRP se inspira en el concepto clásico de **cohesión** de DeMarco y Page-Jones, pero **desplaza el significado**: ya no mide solo "qué tan relacionados están los elementos", sino que relaciona la cohesión con **la causa de cambio de un módulo**.

---

## 📖 ¿Qué es?

> [!quote] Definición
> **Una clase debería tener un único motivo de cambio.**
> Si puedes pensar en **más de un motivo de cambio** para una clase, entonces la clase tiene **más de una responsabilidad**.

El SRP define **responsabilidad** como **razón de cambio**. No se trata de "que la clase haga una sola cosa" en sentido literal (una clase siempre hace varias operaciones), sino de que **todas sus operaciones cambien por la misma causa**.

> [!warning] Señal de alarma
> Si al preguntarte *"¿por qué tendría que cambiar esta clase?"* obtienes respuestas de **áreas distintas** (negocio, presentación, persistencia, formato…), la clase tiene **demasiadas responsabilidades**.

> [!tip] Idea clave
> **Una responsabilidad = una razón de cambio = un actor interesado.** Si dos personas distintas (el contable y el diseñador gráfico) pueden pedir cambios en la misma clase por motivos distintos, hay dos responsabilidades.

---

## ❓ Por qué es un problema (justificación)

- **Acoplamiento entre responsabilidades:** si una clase tiene más de una, pueden llegar a **acoplarse**.
- **Cambios que se contaminan:** los cambios de una responsabilidad pueden **perjudicar o inhibir** la capacidad de otras, afectando a su funcionalidad.
- **Diseños frágiles:** este acoplamiento produce sistemas que **se rompen de forma inesperada**.
- **Difícil de entender y testear:** hay que tener en cuenta varios intereses a la vez.
- **Reutilización difícil:** para usar una parte hay que arrastrar toda la clase.

> [!example] Ejemplo conceptual
> Si una clase `Board` es responsable de **las fichas de los jugadores** y además de **presentarse por consola**, cuando se cambie a un **entorno gráfico** puede afectar a la clase que crea el tablero, porque ahora tiene que suministrar los **aspectos gráficos** necesarios para su nueva presentación.

> [!example] Otro ejemplo conceptual
> Si una **entidad del dominio** (`Student`, `Pedido`…) **se autoguarda en la base de datos**, cambiar la tecnología de **persistencia** repercute en todas las clases que manejan la entidad.

---

## 🔍 Cómo detectar responsabilidades mezcladas

Señales típicas:

- **Comentarios que separan secciones:** `// --- dominio ---`, `// --- vista ---`, `// --- persistencia ---`.
- **Grupos de métodos** que cambian por motivos distintos.
- **Imports de áreas dispares** en una misma clase (SQL, HTML, email, fechas…).
- Nombres como `Manager`, `Gestor`, `Utilidades`, `Sistema` que lo abarcan todo.
- La clase aparece en **commits de temas muy diferentes**.
- Preguntas del tipo: *"¿quién pediría este cambio?"* → si son **varios actores**, hay varias responsabilidades.

> [!tip] La prueba de los actores
> Asigna cada método a **quién pediría cambiarlo**: el equipo de negocio, el de diseño, el de infraestructura… Si un método no encaja con el resto, **pertenece a otra clase**.

---

## 💥 Ejemplo (antes): `Board` que gestiona y se dibuja

```java
import java.util.*;

public class Board {
    private final List<Ficha> fichas = new ArrayList<>();

    // --- Responsabilidad 1: gestión de fichas (dominio) ---
    public void agregarFicha(Ficha f) { fichas.add(f); }
    public void quitarFicha(Ficha f) { fichas.remove(f); }
    public List<Ficha> fichas() { return fichas; }

    // --- Responsabilidad 2: presentación por consola (vista) ---
    public void mostrarPorConsola() {
        for (Ficha f : fichas) {
            System.out.println(f.getJugador() + " -> " + f.getPosicion());
        }
    }
}
```

> [!danger] Problemas
> `Board` mezcla **el modelo del juego** con **cómo se muestra**. Si mañana se pasa a una **interfaz gráfica** (Swing, JavaFX, web), hay que tocar `Board` para que suministre los datos que la nueva vista necesita. El **dominio** queda atado a la **tecnología de presentación**.

---

## ✅ Solución

> [!success] Regla general
> **Partir la funcionalidad en dos clases.** Cada clase maneja **una única responsabilidad** y, en el futuro, cualquier cambio se realizará **en la clase que lo maneje**.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Extract Class** | Un grupo de métodos/atributos forma otra responsabilidad |
| **Move Method / Move Field** | Un método usa más datos de otra clase que de la suya |
| **Extract Interface** | Los clientes usan solo una parte de la clase |
| **Patrón DAO / Repository** | Separar la entidad de dominio de su grabación y recuperación |
| **Patrón MVC / MVP** | Separar modelo, vista y controlador |

---

## 🔧 Ejemplo (después): `Board` + `BoardView`

```java
// --- Dominio: solo gestiona las fichas ---
public class Board {
    private final List<Ficha> fichas = new ArrayList<>();

    public void agregarFicha(Ficha f) { fichas.add(f); }
    public void quitarFicha(Ficha f) { fichas.remove(f); }
    public List<Ficha> fichas() { return List.copyOf(fichas); }
}
```

```java
// --- Presentación: solo se encarga de mostrar ---
public class BoardView {
    private final Board board;

    public BoardView(Board board) {
        this.board = board;
    }

    public void mostrarPorConsola() {
        for (Ficha f : board.fichas()) {
            System.out.println(f.getJugador() + " -> " + f.getPosicion());
        }
    }
}
```

> [!note] Resultado
> Los cambios en la **tecnología de visualización** afectan **únicamente a las clases de presentación**. `Board` queda **limpia**: modela el tablero y no sabe nada de consolas ni de ventanas. Se puede cambiar `BoardView` por una vista gráfica **sin tocar el dominio**.

## 🔁 Ejemplo: entidad de dominio vs persistencia (DAO)

```java
// ❌ Antes: la entidad se autoguarda → atada a la BD
public class Estudiante {
    private String nombre;
    private String matricula;

    public void guardarEnBD() {
        // SQL, conexiones, transacciones...
    }
}
```

```java
// ✅ Después: entidad de dominio pura
public class Estudiante {
    private final String nombre;
    private final String matricula;

    public Estudiante(String nombre, String matricula) {
        this.nombre = nombre;
        this.matricula = matricula;
    }

    public String nombre() { return nombre; }
    public String matricula() { return matricula; }
}
```

```java
// ✅ La persistencia vive en su propia clase (patrón DAO)
public class EstudianteDAO {
    public void guardar(Estudiante e) {
        // INSERT INTO estudiantes ...
    }

    public Estudiante buscarPorMatricula(String matricula) {
        // SELECT ... WHERE matricula = ?
        return null;
    }
}
```

> [!note] Resultado
> Cambiar de **MySQL a MongoDB** afecta solo a `EstudianteDAO`. La entidad `Estudiante` **no se entera** y puede **reutilizarse** en tests, en memoria o en otras capas. Cada clase tiene **una sola razón de cambio**.

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| Cada clase con **una razón de cambio** | Es uno de los principios **más fáciles de enunciar y más difíciles de aplicar** |
| Cambios **localizados** y menos frágiles | Partir **sin criterio** crea [[2. Codigo sucio por clases perezosas\|clases perezosas]] |
| Mayor **cohesión** y menor acoplamiento | Más clases → más **navegación** |
| Mejor **reutilización** y testeo | En **proyectos pequeños** puede ser sobreingeniería |
| Reduce [[8. Codigo sucio por Cambios Divergentes\|Divergent Change]] | Si las responsabilidades **cambian siempre juntas**, separarlas puede ser artificial |

> [!warning] YAGNI: no aplicar SRP sin síntoma
> **Un eje de cambio solo es un eje de cambio si el cambio ocurre actualmente.** No es prudente aplicar el SRP (ni ningún principio) si **no hay ningún síntoma**: **YAGNI** (*You Aren't Gonna Need It*). Si no hay evidencia de que la clase cambie por varios motivos, **no la partas de forma especulativa**.

> [!tip] SRP no significa "una clase, un método"
> Una clase puede tener **muchos métodos** y seguir cumpliendo SRP si **todos cambian por la misma razón**. `Calculadora` con `sumar`, `restar`, `multiplicar` tiene **una sola responsabilidad**: calcular.

> [!tip] La pareja que hay que equilibrar
> **Clase grande** ⟷ **Clase perezosa**: el SRP no es "partir todo", sino que **cada clase tenga una responsabilidad real y suficiente**. El punto medio es una clase **cohesionada**.

## ✅ Conclusión para examen

1. **SRP (Robert C. Martin, SOLID):** una clase debe tener **un único motivo de cambio**.
2. **Responsabilidad = razón de cambio:** si puedes pensar en más de un motivo de cambio, hay más de una responsabilidad.
3. **Origen:** se inspira en la **cohesión** de DeMarco y Page-Jones, pero la liga a la **causa de cambio**.
4. **Problema:** responsabilidades acopladas → diseños **frágiles** que se rompen de forma inesperada.
5. **Solución:** **partir la funcionalidad** en clases con una responsabilidad (Extract Class, Move Method); separar dominio de presentación (`Board` / `BoardView`) y de persistencia (patrón **DAO**).
6. **Cuidado:** es fácil de enunciar y difícil de aplicar; **YAGNI** — no separar sin síntomas reales de cambio.

> [!question] Pregunta típica
> *"¿Qué es el Principio de Única Responsabilidad y cómo se aplica?"*
> **Respuesta:** es un principio SOLID de Robert C. Martin según el cual **una clase debe tener un único motivo de cambio**; la responsabilidad se define como **razón de cambio**. Se aplica identificando los motivos de cambio (o los actores que pedirían cambios) y **partiendo la clase** en clases con una sola responsabilidad. Ejemplos: separar `Board` (gestión de fichas) de `BoardView` (visualización), y la entidad `Estudiante` de su `EstudianteDAO` (persistencia). No debe aplicarse sin síntomas reales (**YAGNI**).
