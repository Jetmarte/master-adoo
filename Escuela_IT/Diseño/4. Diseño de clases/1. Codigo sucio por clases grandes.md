# 1. Código sucio por clases grandes

> [!info] Code smell · Clase demasiado grande
> Relacionado con [[10. Principio de unica responsabilidad|SRP]] · [[2. Codigo sucio por clases perezosas|Lazy Class]] · [[8. Codigo sucio por Cambios Divergentes|Divergent Change]] · [[4. Codigo sucio por grupos de datos|Data Clumps]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Big Large Object – BLOB** | Antipatrón de Desarrollo — William H. Brown et al. |
| **Too Much Information** | *Clean Code* — Robert C. Martin (Uncle Bob) |
| **Large Class** | *Refactoring* (Code Smells) — Martin Fowler |
| **God Class** | Nombre coloquial para una clase que "lo sabe y lo hace todo" |

---

## 📖 ¿Qué es?

Una **clase grande** es una clase que **intenta hacer demasiado**: acumula demasiadas variables de instancia, demasiados métodos y responsabilidades poco relacionadas entre sí.

> [!warning] Señal de alarma
> Cuando una clase hace demasiado, **a menudo aparece con demasiadas variables de instancia**. Y cuando hay muchas variables, el **código duplicado no suele estar lejos**.

Los archivos pequeños son generalmente **más fáciles de entender** que los de gran tamaño.

---

## ❓ Por qué es un problema (justificación)

- **Difícil de comprender:** hay que retener demasiada información a la vez.
- **Difícil de mantener:** un cambio pequeño obliga a leer y entender mucha clase.
- **Difícil de reutilizar:** para usar una parte hay que arrastrar toda la clase.
- **Frágil:** mezcla intereses que cambian por motivos distintos → [[8. Codigo sucio por Cambios Divergentes|cambios divergentes]].
- **Baja cohesión:** muchos métodos y atributos no tienen relación entre sí → viola [[10. Principio de unica responsabilidad|SRP]].
- **Favorece la duplicación:** el mismo cálculo se repite en varios métodos.

> [!tip] Idea clave
> Una clase grande suele ser una **clase con varias responsabilidades disfrazadas**. La solución no es "ordenarla mejor", sino **partirla**.

---

## 📏 Métricas (solo como referencia)

> [!note] No son reglas rígidas
> Las métricas son **una guía**, no una obligación. Una clase de 600 líneas puede ser correcta si tiene una única responsabilidad clara; una de 100 puede ser un desastre.

| Métrica | Valor orientativo |
|---------|-------------------|
| **Líneas por archivo** | ~200 típico · **máx. ~500** |
| **Atributos de instancia** | ~3 de media · **máx. 5** |
| **Métodos** | **máx. ~20** |

> [!tip] Cómo usar la métrica
> Úsala para **detectar candidatas**, no para aprobar o suspender código. Si una clase supera varios umbrales a la vez, revisa su cohesión.

---

## 🔍 Cómo detectarla

Señales típicas:

- **Muchísimos atributos** que no se usan todos juntos.
- **Métodos que solo usan un subconjunto de atributos** → ese subconjunto probablemente es otra clase.
- **Nombres genéricos:** `Sistema`, `Gestor`, `Manager`, `Utilidades`, `Procesador`, `PedidoManager`.
- **Nombre con "y":** `ClienteYFactura`, `GestorPedidosYReportes`.
- **Bloques de código duplicado** repartidos por la clase.
- **Comentarios que separan secciones:** `// --- persistencia ---`, `// --- presentación ---` → intereses distintos.
- **Métodos con prefijos de áreas distintas:** `calcular...`, `imprimir...`, `guardar...`, `enviar...`.

---

## 💥 Ejemplo (antes): una `Pedido` que lo hace todo

```java
class Pedido {
    // --- datos del pedido ---
    int id;
    List<LineaPedido> lineas;

    // --- datos del cliente (¿por qué están aquí?) ---
    String clienteNombre, clienteEmail, clienteTelefono;

    // --- dirección de envío ---
    String calleEnvio, ciudadEnvio, cpEnvio;

    // --- dirección de facturación ---
    String calleFacturacion, ciudadFacturacion, cpFacturacion;

    // --- pago ---
    String tarjeta, caducidad, cvv;

    // --- negocio ---
    double calcularTotal() { /* recorre lineas */ }
    double calcularImpuestos() { /* IVA */ }
    double aplicarDescuento() { /* reglas */ }

    // --- presentación ---
    String generarFacturaHTML() { /* HTML */ }
    void imprimirTicket() { /* consola / impresora */ }

    // --- persistencia ---
    void guardarEnBD() { /* SQL */ }
    void cargarDeBD(int id) { /* SQL */ }

    // --- comunicación ---
    void enviarEmailConfirmacion() { /* SMTP */ }

    // --- inventario ---
    void actualizarStock() { /* otro sistema */ }
}
```

> [!danger] Problemas
> `Pedido` mezcla **dominio, presentación, persistencia, comunicación e inventario**. Cambiar el formato del ticket, el motor de BD o el proveedor de email obliga a tocar la misma clase → **varios motivos de cambio** (viola SRP) y **alto acoplamiento**.

---

## ✅ Solución

> [!success] Regla general
> **Descomponer la clase otorgando grupos de atributos relacionados a otras clases.** Si es una clase de interfaz, **separar los datos y cálculos del dominio** en una clase de entidad.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Extract Class** (Extraer clase) | Un grupo de atributos/métodos forma un concepto propio (dirección, pago) |
| **Extract Subclass** (Extraer subclase) | Un subconjunto de la clase se usa solo en algunos casos |
| **Extract Interface** (Extraer interfaz) | Los clientes usan solo una parte de la clase |
| **Move Method / Move Field** | Un método/atributo usa más datos de otra clase que de la suya |
| **Extract Superclass** | Varias clases comparten un grupo de datos/comportamiento |

> [!tip] Heurística práctica
> Agrupa los atributos que **se usan juntos** y dales un nombre de concepto. Si ese grupo tiene sentido por sí mismo → **extrae una clase**.

## 🔧 Ejemplo (después)

```java
// Entidad del dominio: solo su responsabilidad
class Pedido {
    private int id;
    private Cliente cliente;
    private List<LineaPedido> lineas = new ArrayList<>();
    private Direccion direccionEnvio;

    double total() {
        return lineas.stream().mapToDouble(LineaPedido::subtotal).sum();
    }
}

class LineaPedido {
    private Producto producto;
    private int cantidad;
    double subtotal() { return producto.precio() * cantidad; }
}

class Cliente {
    private String nombre, email, telefono;
}

class Direccion {
    private String calle, ciudad, cp;
}

class DatosPago {
    private String tarjeta, caducidad, cvv;
}
```

```java
// Responsabilidades extraídas a clases propias
class CalculadoraImpuestos { double calcular(Pedido p) { ... } }
class GeneradorFactura    { String html(Pedido p) { ... } }
class ImpresoraTicket     { void imprimir(Pedido p) { ... } }
class RepositorioPedidos  { void guardar(Pedido p) { ... } Pedido buscar(int id) { ... } }
class ServicioNotificaciones { void enviarConfirmacion(Pedido p) { ... } }
class ServicioInventario  { void actualizarStock(Pedido p) { ... } }
```

> [!note] Resultado
> Cada clase tiene **una sola razón de cambio**:
> - Cambia el formato del ticket → `GeneradorFactura`.
> - Cambia la BD → `RepositorioPedidos`.
> - Cambia el email → `ServicioNotificaciones`.
> `Pedido` queda limpia y **cohesionada** con el dominio.

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| Clases **más pequeñas y comprensibles** | Partir **sin un concepto claro** genera clases artificiales y confusión |
| **Alta cohesión** y bajo acoplamiento | Puede aumentar el **número de clases** y la navegación |
| Cambios **localizados** → menos frágiles | En **código generado** o DTOs es normal tener clases con muchos campos |
| Mejor **reutilización** de cada parte | Métricas no deben aplicarse de forma **dogmática** |

> [!warning] No partir por partir
> Si no hay **síntomas reales** de cambio o de baja cohesión, no apliques la refactorización de forma especulativa (**YAGNI**). Una clase grande pero **cohesiva** puede ser aceptable.

> [!tip] La pareja que hay que equilibrar
> **Clase grande** ⟷ **Clase perezosa**: ni una que lo haga todo, ni muchas que no hagan nada. El punto medio es una clase **cohesionada** con una responsabilidad clara.

---

## ✅ Conclusión para examen

1. **Clase grande (Large Class / BLOB / Too Much Information / God Class)** = clase con demasiados atributos, métodos y responsabilidades.
2. Es un problema de **cohesión y SRP**: varios motivos de cambio y código frágil.
3. **Métricas orientativas:** ~200 líneas (máx. 500), ~3 atributos (máx. 5), ~20 métodos — **no son reglas rígidas**.
4. **Solución:** descomponer por **grupos de atributos relacionados** (Extract Class, Extract Subclass, Extract Interface, Move Method/Field); en clases de interfaz, **separar dominio de presentación**.
5. **No refactorizar sin síntomas** (YAGNI); una clase grande y cohesiva puede ser válida.

> [!question] Pregunta típica
> *"¿Qué es el code smell de clase grande, cómo se detecta y cómo se corrige?"*
> **Respuesta:** una clase que hace demasiado (muchos atributos/métodos y responsabilidades no relacionadas). Se detecta por baja cohesión, nombres genéricos, secciones comentadas y métodos que usan solo parte de los atributos. Se corrige **extrayendo clases** por grupos de atributos afines y moviendo responsabilidades (presentación, persistencia, etc.) a clases propias. Ej.: `Pedido` → `Cliente`, `Direccion`, `RepositorioPedidos`, `GeneradorFactura`.
