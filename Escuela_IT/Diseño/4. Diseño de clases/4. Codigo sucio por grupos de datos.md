# 4. Código sucio por grupos de datos

> [!info] Code smell · Grupos de datos (Data Clumps)
> Relacionado con [[3. Codigo sucio por obsecion de tipos primitivos|Primitive Obsession]] · [[1. Codigo sucio por clases grandes|Clase grande]] · [[5. Codigo sucio por clases de datos|Data Class]]

| Término | Fuente |
|---------|--------|

| **Grupos de datos / Racimos de datos** | Traducción habitual al español |

---

## 📖 ¿Qué es?

Sucede cuando **los mismos dos, tres o cuatro elementos de datos aparecen siempre juntos**:

- en los **atributos** de varias clases,
- en los **parámetros** de muchas cabeceras de métodos,
- o en los **valores que se pasan y se devuelven** continuamente.

El orden importa: `calle, ciudad, codigoPostal` siempre en ese orden, siempre los tres, siempre en los mismos sitios. Eso indica que **falta modelar un concepto**.

> [!warning] Señal de alarma
> Si **quitando uno del grupo, los demás dejan de tener sentido**, entonces forman un **grupo de datos** que debería ser un objeto propio. Ej.: `latitud` sin `longitud` no es una coordenada.

---

## ❓ Por qué es un problema (justificación)

- **Duplicación de firmas:** si añades un dato (p. ej. `pais`), tocas **todos** los métodos.
- **Errores de orden:** con 3 Strings seguidos es fácil intercambiar `ciudad` y `codigoPostal`.
- **Poca expresividad:** `void registrar(String, String, String, String)` no dice nada.
- **Lógica dispersa:** las validaciones del grupo se repiten donde se usa.
- **Aumenta el [[1. Codigo sucio por clases grandes|tamaño de las clases]]** y la [[10. Principio de unica responsabilidad|baja cohesión]].
- **Dificulta el cambio:** el grupo no tiene un único punto donde evolucionar.

> [!tip] Idea clave
> Un grupo de datos que viaja junto es **un concepto esperando a ser una clase**. El nombre del concepto suele estar en la cabeza del programador (dirección, coordenada, rango, período).

---

## 🔍 Cómo detectarla

Señales típicas:

- **Los mismos 3–4 parámetros** se repiten en varias firmas.
- **Los mismos atributos** aparecen juntos en dos o más clases.
- Métodos que reciben **muchos parámetros** y la llamada ocupa varias líneas.
- **Comentarios en las llamadas:** `registrar("Ana", calle, ciudad, cp); // calle, ciudad, cp`.
- Un método **devuelve varios valores** que siempre se usan juntos.
- Aparece el mismo grupo en **capas distintas** (vista, servicio, repositorio).

> [!note] Test rápido de decisión
> Pregúntate: *¿estos datos describen una sola cosa?* Si `calle`, `ciudad` y `cp` describen "una dirección", es un clump. Si son `nombre`, `edad` y `salario`, **no** lo son: no forman un concepto único.

---

## 💥 Ejemplo (antes): dirección repetida en todos los métodos

```java
public class ClienteService {

    public void registrarCliente(String nombre, String calle, String ciudad, String codigoPostal) {
        System.out.println("Registrando cliente " + nombre + " en " + calle + ", " + ciudad + ", " + codigoPostal);
    }

    public void actualizarDireccion(String calle, String ciudad, String codigoPostal) {
        System.out.println("Actualizando dirección a " + calle + ", " + ciudad + ", " + codigoPostal);
    }

    public void imprimirDireccion(String calle, String ciudad, String codigoPostal) {
        System.out.println("Dirección: " + calle + ", " + ciudad + ", " + codigoPostal);
    }
}
```

> [!danger] Problemas
> `calle, ciudad, codigoPostal` aparecen **siempre juntos** en tres métodos. Si mañana se añade `pais`, hay que modificar **las tres firmas** y todas sus llamadas. Además, `actualizarDireccion("Madrid", "Calle Mayor", "28013")` **compila** aunque el orden sea incorrecto.

---

## ✅ Solución

> [!success] Regla general
> **Los grupos de datos que se presentan juntos deben componer su propio objeto.** Se crea una clase que encapsule el grupo (a menudo un **Value Object**) y se pasan **objetos**, no listas de primitivos.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Introduce Parameter Object** | El grupo viaja como parámetros de métodos |
| **Extract Class** | El grupo aparece como atributos dentro de otra clase |
| **Preserve Whole Object** | Un método recibe `calle, ciudad, cp` y ya tiene el objeto `Direccion` a mano |
| **Introduce Parameter Object + Move Method** | Además de agrupar, la lógica del grupo se mueve al nuevo objeto |

## 🔧 Ejemplo (después): `Direccion` como concepto

```java
public final class Direccion {
    private final String calle;
    private final String ciudad;
    private final String codigoPostal;

    public Direccion(String calle, String ciudad, String codigoPostal) {
        if (calle == null || calle.isBlank()) {
            throw new IllegalArgumentException("La calle es obligatoria");
        }
        if (!codigoPostal.matches("\\d{5}")) {
            throw new IllegalArgumentException("Código postal inválido");
        }
        this.calle = calle;
        this.ciudad = ciudad;
        this.codigoPostal = codigoPostal;
    }

    public String getCalle() { return calle; }
    public String getCiudad() { return ciudad; }
    public String getCodigoPostal() { return codigoPostal; }

    @Override
    public String toString() {
        return calle + ", " + codigoPostal + " " + ciudad;
    }
}
```

```java
public class ClienteService {

    public void registrarCliente(String nombre, Direccion direccion) {
        System.out.println("Registrando cliente " + nombre + " en " + direccion);
    }

    public void actualizarDireccion(Direccion direccion) {
        System.out.println("Actualizando dirección a " + direccion);
    }

    public void imprimirDireccion(Direccion direccion) {
        System.out.println("Dirección: " + direccion);
    }
}
```

> [!note] Resultado
> Si se añade `pais`, se modifica **solo `Direccion`** (y, si acaso, su constructor). Los métodos son más **cortos y expresivos**, ya no se puede confundir el orden, y la validación del CP vive en **un solo sitio**.

## 🔁 Otro ejemplo: coordenadas y rangos

```java
// ❌ Antes: dos doubles que siempre van juntos en todas partes
void mover(double lat, double lon) { ... }
void dibujarRuta(double lat1, double lon1, double lat2, double lon2) { ... }
```

```java
// ✅ Después
record Coordenada(double latitud, double longitud) {
    Coordenada {
        if (latitud < -90 || latitud > 90) throw new IllegalArgumentException("Latitud inválida");
        if (longitud < -180 || longitud > 180) throw new IllegalArgumentException("Longitud inválida");
    }
}

void mover(Coordenada destino) { ... }
void dibujarRuta(Coordenada origen, Coordenada destino) { ... }
```

> [!tip] Regla del "y"
> Si al nombrar el concepto necesitas una "y" (*latitud **y** longitud*, *fecha inicio **y** fecha fin*), casi seguro tienes un Data Clump. Búscale un sustantivo: `Coordenada`, `Periodo`, `Rango`, `Direccion`, `Dinero`.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| Métodos **más cortos y expresivos** | No agrupar datos que **no forman un concepto** (solo coinciden) |
| Cambios **localizados** en la nueva clase | Crear un objeto **solo con getters** puede derivar en [[5. Codigo sucio por clases de datos\|Data Class]] |
| Validaciones **centralizadas** | En **DTOs de APIs externas** a veces el grupo es artificial |
| Menos errores de **orden de parámetros** | Exceso de objetos puede añadir **indirección innecesaria** |

> [!warning] Data Clump ≠ grupo arbitrario
> `nombre`, `edad` y `salario` siempre aparecen juntos en `Persona`, pero **no forman un concepto**. El Data Clump exige que los datos **describan una sola cosa** y que **no tengan sentido por separado**.

## ✅ Conclusión para examen

1. **Data Clumps** = los mismos 2–4 datos aparecen **siempre juntos** en atributos y parámetros.
2. Es un problema de **duplicación, orden de parámetros y evolución**: cambiar el grupo obliga a tocar muchos sitios.
3. **Test:** si quitando un elemento los demás pierden sentido, forman un grupo → **crear una clase**.
4. **Solución:** **Introduce Parameter Object** / **Extract Class** / **Preserve Whole Object**; el nuevo objeto debe tener **comportamiento y validaciones**, no solo getters.
5. **Cuidado:** no agrupar datos que solo coinciden; evitar crear [[5. Codigo sucio por clases de datos|Data Classes]].

> [!question] Pregunta típica
> *"¿Qué es un Data Clump y cómo se corrige?"*
> **Respuesta:** es un grupo de datos que siempre aparece junto en atributos y firmas (`calle, ciudad, cp`). Se detecta porque al quitar un elemento los demás pierden sentido y porque el grupo se repite en varios métodos o clases. Se corrige **extrayendo una clase** que represente el concepto (`Direccion`, `Coordenada`, `Periodo`) con **Introduce Parameter Object** o **Extract Class**, añadiéndole validaciones para que no sea una simple Data Class.
