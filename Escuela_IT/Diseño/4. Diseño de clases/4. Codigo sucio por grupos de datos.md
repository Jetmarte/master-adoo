Sinónimos: Data Clumps [Smell Code (Refactoring) - Martin Fowler]

 Justificación:

▫ Si se encuentran los mismos dos, tres o cuatro elementos de datos  juntos en muchos lugares: atributos en un par de clases, los parámetros de muchas cabeceras de métodos.

 Solución:

▫ Los grupos de datos que se presentan juntos realmente deben  componer su propio objeto.

▫ Ante la duda, una buena comprobación sería preguntarse si quitando uno del grupo, ¿los demás tendrían sentido? Si la respuesta es no, forman un grupo de datos

---

El **smell code por grupo de datos** es otro clásico dentro de los _code smells_ descritos por Martin Fowler.

---

## 🚨 ¿Qué es _Data Clumps_ (Grupo de Datos)?

Sucede cuando **varios atributos o parámetros siempre aparecen juntos**:

- Los ves en varios métodos como listas de parámetros.
    
- Los ves repetidos en varias clases.
    
- Es evidente que **representan una entidad o concepto**, pero no se modela como tal.
    

👉 Esto indica que falta crear una **clase o Value Object** para agruparlos.

---

## 🧩 Ejemplo en Java (con smell)

```java
public class ClienteService {

    public void registrarCliente(String nombre, String calle, String ciudad, String codigoPostal) {
        System.out.println("Registrando cliente " + nombre + " en " + calle + ", " + ciudad + ", " + codigoPostal);
    }

    public void actualizarDireccion(String calle, String ciudad, String codigoPostal) {
        System.out.println("Actualizando dirección a " + calle + ", " + ciudad + ", " + codigoPostal);
    }

    public void imprimirDireccion(String calle, String ciudad, String codigoPostal) {
        System.out.println("Dirección: " + calle + ", " + ciudad + ", " + codigoPostal);
    }
}
```

### ❌ Problemas:

- Los parámetros `calle, ciudad, codigoPostal` aparecen **siempre juntos**.
    
- Si hay que cambiar algo (ej. agregar país), hay que modificar todos los métodos.
    
- **Difícil de mantener** y **menos expresivo**.
    

---

## ✅ Refactorización: Extraer Clase (Introduce Parameter Object)

Creamos una clase `Direccion` que agrupe ese **clump** de datos:

```java
public class Direccion {
    private String calle;
    private String ciudad;
    private String codigoPostal;

    public Direccion(String calle, String ciudad, String codigoPostal) {
        this.calle = calle;
        this.ciudad = ciudad;
        this.codigoPostal = codigoPostal;
    }

    public String getCalle() { return calle; }
    public String getCiudad() { return ciudad; }
    public String getCodigoPostal() { return codigoPostal; }

    @Override
    public String toString() {
        return calle + ", " + ciudad + ", " + codigoPostal;
    }
}
```

Y ahora el servicio queda así:

```java
public class ClienteService {

    public void registrarCliente(String nombre, Direccion direccion) {
        System.out.println("Registrando cliente " + nombre + " en " + direccion);
    }

    public void actualizarDireccion(Direccion direccion) {
        System.out.println("Actualizando dirección a " + direccion);
    }

    public void imprimirDireccion(Direccion direccion) {
        System.out.println("Dirección: " + direccion);
    }
}
```

---

## 🎯 Ventajas después del refactor

- `Direccion` encapsula los datos relacionados.
    
- Los métodos son más **limpios y expresivos**.
    
- Si se agrega `pais`, solo se modifica la clase `Direccion`.
    
- A futuro, se pueden añadir validaciones (ej. formato de código postal) dentro de `Direccion`.
    

---

## 📌 Resumen

El **smell “Data Clumps”** aparece cuando ciertos **grupos de datos siempre viajan juntos**.  
La solución típica es **crear una clase o Value Object** que encapsule ese grupo, haciendo el código más **limpio, expresivo y mantenible**.
