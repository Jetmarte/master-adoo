**Sinónimos**:

Divergent Change [Smell Code (Refactoring); Martin Fowler]

**Justificación**:

Ocurre cuando una clase se cambia frecuentemente de diferentes maneras, por diferentes razones. Si nos fijamos en una clase y dice: "Bueno, voy a tener que cambiar estos tres métodos cada vez que tengo una nueva base de datos, tengo que cambiar estos cuatro métodos cada vez que hay un nuevo instrumento financiero, ..."

**Solución**:

Es probable que tenga una situación en la que varios objetos son mejor que uno. De esta manera cada objeto sólo se cambia como resultado de un tipo de cambio. Por supuesto, a menudo se descubre esto sólo después de añadir un par de bases de datos o instrumentos financieros.

Estructuramos nuestro software para hacer el cambio más fácil. Después de todo, el software está destinado a ser blando. Cuando hacemos un cambio queremos la ventaja de ser capaces de saltar a un solo punto en el sistema y hacer el cambio.

Nota: Una claes se debe ocupar de una sola cosa.


---

## 🚨 ¿Qué es _Divergent Change_?

Un **Divergent Change** ocurre cuando **una misma clase necesita modificarse por diferentes motivos no relacionados entre sí**.  
Esto **viola el Principio de Responsabilidad Única (SRP)** de SOLID.

En otras palabras:

- Si cada vez que cambian **reglas de negocio** tocas esa clase...
    
- Y también cada vez que cambian **los reportes**...
    
- Y además cuando cambian **las conexiones a la base de datos**...
    

👉 Entonces tienes un **código con cambios divergentes**.

---

## 🧩 Ejemplo en Java (con smell)

```java
public class Factura {
    private double monto;
    private String cliente;

    public Factura(double monto, String cliente) {
        this.monto = monto;
        this.cliente = cliente;
    }

    // --- 1. Lógica de negocio ---
    public double calcularImpuesto() {
        return monto * 0.19; // 19% de IVA
    }

    // --- 2. Lógica de presentación ---
    public String generarReporte() {
        return "Factura de " + cliente + " por $" + monto + " más IVA.";
    }

    // --- 3. Lógica de persistencia ---
    public void guardarEnBD() {
        System.out.println("Guardando factura en la base de datos...");
        // Código de conexión y persistencia
    }
}
```

### ❌ Problemas

- Si cambia el cálculo de impuestos → hay que modificar esta clase.
    
- Si cambia el formato del reporte → también hay que modificarla.
    
- Si cambia la forma de guardar en BD → otra vez se toca la misma clase.
    

Esto genera **alta fragilidad**: una clase que debería tener **una sola razón de cambio**, ahora tiene tres.

---

## ✅ Refactorización: Separación de responsabilidades

Aplicamos **SRP** y extraemos las responsabilidades en clases separadas:

```java
// --- Entidad ---
public class Factura {
    private double monto;
    private String cliente;

    public Factura(double monto, String cliente) {
        this.monto = monto;
        this.cliente = cliente;
    }

    public double getMonto() { return monto; }
    public String getCliente() { return cliente; }
}
```

```java
// --- Lógica de negocio ---
public class CalculadoraImpuesto {
    public double calcular(Factura factura) {
        return factura.getMonto() * 0.19;
    }
}
```

```java
// --- Lógica de presentación ---
public class GeneradorReporte {
    public String generar(Factura factura, double impuesto) {
        return "Factura de " + factura.getCliente() +
               " por $" + factura.getMonto() +
               " más IVA de $" + impuesto;
    }
}
```

```java
// --- Lógica de persistencia ---
public class FacturaRepository {
    public void guardar(Factura factura) {
        System.out.println("Guardando factura en la base de datos...");
        // código de persistencia
    }
}
```

---

## 🎯 Ventajas después del refactor

- Si cambian los impuestos → solo se toca `CalculadoraImpuesto`.
    
- Si cambia el formato de reporte → solo `GeneradorReporte`.
    
- Si cambia la base de datos → solo `FacturaRepository`.
    
- `Factura` queda limpia y solo representa una **entidad del dominio**.
    

---

👉 En resumen:  
El **smell "Divergent Change"** aparece cuando una clase sufre cambios por múltiples razones distintas.  
La solución más común es **aplicar SRP** y **extraer clases** para que cada una tenga **una única razón de cambio**.
