# 8. Código sucio por cambios divergentes

> [!info] Code smell · Cambios divergentes (Divergent Change)
> Relacionado con [[7. Codigo sucio por cirugia a escopetazos|Shotgun Surgery]] · [[1. Codigo sucio por clases grandes|Clase grande]] · [[10. Principio de unica responsabilidad|SRP]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Divergent Change** | *Refactoring* (Code Smells) — Martin Fowler |
| **Cambios divergentes** | Traducción habitual al español |
| **Clase multipropósito** | Nombre coloquial: cambia por todo |

---

## 📖 ¿Qué es?

Ocurre cuando **una misma clase necesita modificarse por diferentes motivos no relacionados entre sí**. La clase "diverge": cada nuevo requisito de un área distinta la obliga a cambiar.

El ejemplo clásico de Fowler: miras una clase y dices *"tengo que cambiar estos tres métodos cada vez que hay una nueva base de datos, y estos cuatro cada vez que aparece un nuevo instrumento financiero"*.

> [!warning] Señal de alarma
> Si puedes enumerar **varias listas de métodos** dentro de la misma clase, cada lista asociada a un **motivo de cambio distinto**, tienes cambios divergentes. La clase tiene **más de una razón para cambiar**.

> [!tip] La regla
> Una clase **se debe ocupar de una sola cosa**. Si se puede pensar en **más de un motivo de cambio** para una clase, entonces tiene **más de una responsabilidad** → viola [[10. Principio de unica responsabilidad|SRP]].

---

## ❓ Por qué es un problema (justificación)

- **Viola SRP:** la clase acumula **varias razones de cambio**.
- **Alta fragilidad:** tocar una responsabilidad puede romper otra sin querer.
- **Acoplamiento interno:** las partes de la clase dependen de detalles que no les corresponden.
- **Difícil de entender y testear:** mezcla dominios distintos en el mismo sitio.
- **Cambios arriesgados:** cada requisito nuevo obliga a releer toda la clase.
- **Síntoma de [[1. Codigo sucio por clases grandes|clase grande]]:** suele aparecer junto a ella.

> [!warning] Divergent Change ≠ Shotgun Surgery
> Son **inversos**:
> - **Divergent Change:** **una clase** cambia por **muchos motivos** (1 → N).
> - **Shotgun Surgery:** **un motivo** obliga a cambiar **muchas clases** (N → 1).
> Se corrige el primero **partiendo** la clase; el segundo, **centralizando** la lógica.

---

## 🔍 Cómo detectarla

Señales típicas:

- **Comentarios que separan secciones:** `// --- negocio ---`, `// --- reportes ---`, `// --- persistencia ---`.
- **Grupos de métodos** que cambian siempre juntos por el mismo motivo.
- Una clase que se toca cuando cambia **la BD**, cuando cambia **el formato del informe**, cuando cambian **las reglas de negocio**…
- **Muchos `import`** de áreas distintas (SQL, HTML, email, fechas…) en una sola clase.
- En el historial: la misma clase aparece en **commits de temas muy diferentes**.
- Nombres como `Factura`, `Pedido` o `Cliente` que hacen **de todo** (dominio + presentación + persistencia).

---

## 💥 Ejemplo (antes): `Factura` que cambia por tres motivos

```java
public class Factura {
    private double monto;
    private String cliente;

    public Factura(double monto, String cliente) {
        this.monto = monto;
        this.cliente = cliente;
    }

    // --- 1. Lógica de negocio: cambia si cambia el impuesto ---
    public double calcularImpuesto() {
        return monto * 0.19; // 19% de IVA
    }

    // --- 2. Presentación: cambia si cambia el formato del reporte ---
    public String generarReporte() {
        return "Factura de " + cliente + " por $" + monto + " más IVA.";
    }

    // --- 3. Persistencia: cambia si cambia la forma de guardar ---
    public void guardarEnBD() {
        System.out.println("Guardando factura en la base de datos...");
        // Código de conexión y persistencia
    }
}
```

> [!danger] Problemas
> `Factura` tiene **tres razones de cambio independientes**:
> - cambia el cálculo de impuestos → se modifica esta clase;
> - cambia el formato del reporte → otra vez esta clase;
> - cambia la forma de guardar en BD → **otra vez** esta clase.
>
> Un cambio en persistencia puede **romper la presentación** sin que tenga relación. La clase es **frágil** porque mezcla intereses.

---

## ✅ Solución

> [!success] Regla general
> **Es probable que varios objetos sean mejores que uno.** Separar la clase en **una clase por motivo de cambio**, de modo que cada una solo se modifique como resultado de **un tipo de cambio**. Si no existe una clase candidata, **crearla**.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Extract Class** | Un grupo de métodos/atributos forma una responsabilidad propia |
| **Move Method / Move Field** | Un método usa más datos de otra clase que de la suya |
| **Extract Superclass / Subclass** | Hay variaciones por tipos o casos |
| **Divergent Change → SRP** | Aplicar el principio de única responsabilidad |
| **Introduce Strategy** | La variación es de algoritmo (impuestos, descuentos) y debe poder cambiar en runtime |

## 🔧 Ejemplo (después): una clase por responsabilidad

```java
// --- Entidad: solo representa los datos del dominio ---
public class Factura {
    private final double monto;
    private final String cliente;

    public Factura(double monto, String cliente) {
        this.monto = monto;
        this.cliente = cliente;
    }

    public double getMonto() { return monto; }
    public String getCliente() { return cliente; }
}
```

```java
// --- Lógica de negocio: cambia solo si cambian los impuestos ---
public class CalculadoraImpuesto {
    public double calcular(Factura factura) {
        return factura.getMonto() * 0.19;
    }
}
```

```java
// --- Presentación: cambia solo si cambia el formato ---
public class GeneradorReporte {
    public String generar(Factura factura, double impuesto) {
        return "Factura de " + factura.getCliente() +
               " por $" + factura.getMonto() +
               " más IVA de $" + impuesto;
    }
}
```

```java
// --- Persistencia: cambia solo si cambia la BD ---
public class FacturaRepository {
    public void guardar(Factura factura) {
        System.out.println("Guardando factura en la base de datos...");
        // código de persistencia
    }
}
```

> [!note] Resultado
> Cada clase tiene **una sola razón de cambio**:
> - cambian los impuestos → solo `CalculadoraImpuesto`;
> - cambia el formato del reporte → solo `GeneradorReporte`;
> - cambia la BD → solo `FacturaRepository`.
> `Factura` queda limpia como **entidad del dominio**, y los cambios ya **no se contaminan** entre sí.

## 🔁 Otro ejemplo: servicio que cambia por canal y por regla

```java
// ❌ Antes: Notificador cambia si cambia el canal O si cambia el formato
class Notificador {
    void enviarEmail(String destino, String mensaje) { ... }
    void enviarSMS(String destino, String mensaje) { ... }
    String formatearComoHTML(String mensaje) { ... }
    String formatearComoTexto(String mensaje) { ... }
}
```

```java
// ✅ Después: el canal y el formato son responsabilidades separadas
interface Canal { void enviar(String destino, String contenido); }
class CanalEmail implements Canal { ... }
class CanalSMS   implements Canal { ... }

interface Formateador { String formatear(String mensaje); }
class FormatoHTML   implements Formateador { ... }
class FormatoTexto  implements Formateador { ... }
```

> [!tip] Pregunta clave
> *"¿Por qué motivos tendría que cambiar esta clase?"* Si la respuesta tiene **dos o más razones no relacionadas**, hay **cambios divergentes**. Cada motivo debería tener **su propia clase**.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| Cada clase con **una razón de cambio** | Partir **sin criterio** crea [[2. Codigo sucio por clases perezosas\|clases perezosas]] |
| Cambios **localizados y seguros** | Más clases → más **navegación** |
| **Alta cohesión** y bajo acoplamiento | Si las responsabilidades **cambian siempre juntas**, quizá no hay que separar |
| Código **más fácil de testear** | En **aplicaciones pequeñas** puede ser sobreingeniería (YAGNI) |

> [!warning] Cuidado con el exceso
> Separar una clase en 10 trozos es tan malo como tener una God Class. Divide por **motivos de cambio reales** (no imaginarios) y comprueba que las partes **no cambian siempre a la vez**.

## ✅ Conclusión para examen

1. **Divergent Change** = **una clase** cambia por **varios motivos no relacionados**.
2. Es una **violación de SRP**: la clase tiene varias razones de cambio y se vuelve **frágil**.
3. **Detección:** secciones comentadas, grupos de métodos que cambian por motivos distintos, muchos imports de áreas dispares, la clase aparece en commits de temas diferentes.
4. **Solución:** **Extract Class** / **Move Method** para que **cada clase tenga una única razón de cambio**; separar dominio, presentación y persistencia (patrón DAO/Repository).
5. **Distinción clave:** Divergent Change = **1 clase, N motivos**; Shotgun Surgery = **1 motivo, N clases**.

> [!question] Pregunta típica
> *"¿Qué es Divergent Change y cómo se corrige?"*
> **Respuesta:** es un smell en el que una misma clase se modifica por motivos distintos y no relacionados (p. ej. `Factura` cambia por impuestos, por formato de reporte y por base de datos), violando SRP. Se detecta por secciones comentadas, grupos de métodos que cambian por causas distintas y clases que aparecen en cambios de temas muy diferentes. Se corrige **extrayendo una clase por responsabilidad** (`CalculadoraImpuesto`, `GeneradorReporte`, `FacturaRepository`), de forma que cada clase tenga **una sola razón de cambio**.
