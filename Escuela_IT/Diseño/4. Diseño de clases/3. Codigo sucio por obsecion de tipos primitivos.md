Sinónimos: Primitive Obssesion [Smell Code (Refactoring) - Martin Fowler]

 **Justificaión**:

▫ Las nuevos programadores orientados a objetos, por lo general, son 
reacios a utilizar objetos pequeños para pequeñas tareas, como la 
clase Dinero que combinan cantidad y moneda, clase Intervalo con 
límite superior e inferior y clases especiales de cadenas de caracteres 
como números de teléfono y códigos postales.

 **Solución**:

▫ Puede reemplazar un valor de tipo primitivo por una clase en 
incorporar su responsabilidad 
▫ En el caso de que no exista dicha responsabilidad asignable, puede 
crear un enumerado


---

## 🚨 ¿Qué es _Primitive Obsession_?

Sucede cuando abusamos de **tipos primitivos** (`int`, `double`, `String`, etc.) para representar conceptos del dominio que merecen su **propio objeto**.

En vez de modelar la realidad con clases significativas, reducimos todo a strings, números o booleanos.  
Esto:

- Hace el código poco expresivo.
    
- Dificulta validaciones y reglas de negocio.
    
- Duplica lógica en varias partes.
    

---

## 🧩 Ejemplo en Java (con smell)

```java
public class Cliente {
    private String nombre;
    private String email;
    private String telefono;

    public Cliente(String nombre, String email, String telefono) {
        this.nombre = nombre;
        this.email = email;
        this.telefono = telefono;
    }

    public void mostrarInfo() {
        System.out.println("Cliente: " + nombre + ", Email: " + email + ", Teléfono: " + telefono);
    }
}
```

### ❌ Problemas:

- `email` y `telefono` son **Strings desnudos**.
    
- Si mañana quiero validar el formato del email o el teléfono → tendría que repetir la lógica en muchos lados.
    
- No queda claro que representan conceptos importantes del dominio.

## ✅ Refactorización: Objetos de Valor (Value Objects)

```java
// Representa un Email válido
public class Email {
    private String valor;

    public Email(String valor) {
        if (!valor.contains("@")) {
            throw new IllegalArgumentException("Email inválido");
        }
        this.valor = valor;
    }

    public String getValor() {
        return valor;
    }
}
```

```java
// Representa un Teléfono válido
public class Telefono {
    private String valor;

    public Telefono(String valor) {
        if (!valor.matches("\\d{9}")) {
            throw new IllegalArgumentException("Teléfono inválido (debe tener 9 dígitos)");
        }
        this.valor = valor;
    }

    public String getValor() {
        return valor;
    }
}
```

```java
// Ahora Cliente usa objetos ricos en lugar de primitivos
public class Cliente {
    private String nombre;
    private Email email;
    private Telefono telefono;

    public Cliente(String nombre, Email email, Telefono telefono) {
        this.nombre = nombre;
        this.email = email;
        this.telefono = telefono;
    }

    public void mostrarInfo() {
        System.out.println("Cliente: " + nombre +
                           ", Email: " + email.getValor() +
                           ", Teléfono: " + telefono.getValor());
    }
}
```

---

## 🎯 Ventajas

- La validación está **centralizada** en `Email` y `Telefono`.
    
- El código es **más expresivo** (`Email` ≠ `String`).
    
- Se reducen errores (no confundes un `telefono` con un `email`).
    
- Cumple con el principio de **Tell, don’t ask** (los objetos saben validarse).
    

---

👉 En resumen:  
El **smell “Primitive Obsession”** ocurre cuando usamos `int`, `String`, `double`, etc. para todo, en vez de **crear tipos específicos del dominio**.  
La solución es usar **Value Objects** o **clases propias** que encapsulen reglas y den más expresividad.
