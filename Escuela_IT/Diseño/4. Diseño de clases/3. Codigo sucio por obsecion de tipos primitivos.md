# 3. Código sucio por obsesión de tipos primitivos

> [!info] Code smell · Obsesión por los primitivos (Primitive Obsession)
> Relacionado con [[4. Codigo sucio por grupos de datos|Data Clumps]] · [[5. Codigo sucio por clases de datos|Data Class]] · [[2. Codigo sucio por clases perezosas|Lazy Class]]

---

| Término | Fuente |
|---------|--------|

| **Obsesión por los tipos primitivos** | Traducción habitual al español |
| **Primitivos desnudos** | Nombre coloquial (*naked primitives*) |

---

## 📖 ¿Qué es?

Sucede cuando **abusamos de tipos primitivos** (`int`, `double`, `boolean`, `String`…) para representar **conceptos del dominio que merecen su propio objeto**.

En vez de modelar la realidad con clases significativas, reducimos todo a strings, números o booleanos. Es el vicio típico del programador que viene de lenguajes procedurales: "un teléfono es un `String`, un importe es un `double`, y ya está".

> [!warning] Señal de alarma
> Si un `String` puede ser **muchas cosas distintas** (`nombre`, `email`, `teléfono`, `DNI`, `ciudad`), el compilador **no te protege** de confundirlas. Y las reglas sobre ellas (formato, longitud, rango) acaban **repetidas por todo el código**.

---

## ❓ Por qué es un problema (justificación)

- **Código poco expresivo:** `String` no dice *qué* representa ni *qué reglas* cumple.
- **Validaciones duplicadas:** el "email válido" se comprueba en 15 sitios distintos.
- **Errores por confusión de tipos:** nada impide pasar un `telefono` donde va un `email` (ambos son `String`).
- **Lógica de negocio dispersa:** el cálculo de un importe con moneda se repite en cada clase.
- **Difícil de evolucionar:** añadir una regla (p. ej. el IVA cambia) obliga a tocar muchos puntos.
- **Favorece otros smells:** [[4. Codigo sucio por grupos de datos|Data Clumps]] y [[5. Codigo sucio por clases de datos|Data Class]].

> [!tip] Idea clave
> Un primitivo **no tiene comportamiento**. Un concepto del dominio **sí** (validarse, formatearse, compararse). Si un valor necesita reglas propias, merece una **clase**.

---

## 🔍 Cómo detectarla

Señales típicas:

- **Muchos `String`/`int`/`double`** en la misma clase que representan conceptos distintos.
- **Validaciones repetidas** del mismo formato (`contains("@")`, `matches("\\d{9}")`) en varios sitios.
- **Parámetros agrupados mentalmente:** `(cantidad: double, moneda: String)` siempre juntos.
- **Booleanos "bandera":** `esVIP`, `tieneDescuento`, `estado` como `int` con valores 1, 2, 3…
- **Comentarios que explican el primitivo:** `String telefono; // 9 dígitos, sin guiones`.
- **Métodos que reciben 5 Strings** donde cada uno tiene un formato distinto.

## 💥 Ejemplo (antes): todo son `String`

```java
public class Cliente {
    private String nombre;
    private String email;
    private String telefono;

    public Cliente(String nombre, String email, String telefono) {
        this.nombre = nombre;
        this.email = email;
        this.telefono = telefono;
    }

    public void mostrarInfo() {
        System.out.println("Cliente: " + nombre + ", Email: " + email + ", Teléfono: " + telefono);
    }
}
```

```java
// La validación se repite (o se olvida) en cada sitio que crea un Cliente
if (!email.contains("@")) {
    throw new IllegalArgumentException("Email inválido");
}
if (!telefono.matches("\\d{9}")) {
    throw new IllegalArgumentException("Teléfono inválido");
}
```

> [!danger] Problemas
> `email` y `telefono` son **Strings desnudos**: nada garantiza que un `Cliente` tenga datos válidos. Además `new Cliente("Ana", "600123456", "ana@mail.com")` **compila** aunque los argumentos estén intercambiados.

---

## ✅ Solución

> [!success] Regla general
> **Reemplazar el valor primitivo por una clase que incorpore su responsabilidad.** Si no existe responsabilidad que asignar (solo un conjunto cerrado de valores), usar un **enumerado**.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Replace Data Value with Object** | El primitivo tiene reglas propias (Email, Teléfono, DNI) |
| **Replace Type Code with Class / Subclasses / State** | Un `int`/`String` codifica un conjunto de estados |
| **Replace Type Code with Enum** | Conjunto **cerrado y simple** de valores (`Talla`, `DiaSemana`) |
| **Introduce Parameter Object** | Varios primitivos viajan juntos (→ [[4. Codigo sucio por grupos de datos|Data Clumps]]) |
| **Replace Array with Object** | Un array posicional `[cantidad, moneda]` en realidad es un concepto |

## 🔧 Ejemplo (después): objetos de valor (Value Objects)

```java
// Value Object: encapsula el formato y la validación del email
public final class Email {
    private final String valor;

    public Email(String valor) {
        if (valor == null || !valor.matches("^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$")) {
            throw new IllegalArgumentException("Email inválido: " + valor);
        }
        this.valor = valor;
    }

    public String valor() { return valor; }

    @Override
    public String toString() { return valor; }
}
```

```java
// Value Object: encapsula el formato del teléfono
public final class Telefono {
    private final String valor;

    public Telefono(String valor) {
        if (valor == null || !valor.matches("\\d{9}")) {
            throw new IllegalArgumentException("Teléfono inválido (9 dígitos)");
        }
        this.valor = valor;
    }

    public String valor() { return valor; }
}
```

```java
// Cliente usa tipos ricos: el compilador impide intercambiarlos
public class Cliente {
    private final String nombre;
    private final Email email;
    private final Telefono telefono;

    public Cliente(String nombre, Email email, Telefono telefono) {
        this.nombre = nombre;
        this.email = email;
        this.telefono = telefono;
    }

    public void mostrarInfo() {
        System.out.println("Cliente: " + nombre + ", Email: " + email + ", Teléfono: " + telefono);
    }
}
```

> [!note] Resultado
> La validación está **centralizada** en cada Value Object. Si cambia el formato del email, se toca **una sola clase**. Y ahora `new Cliente("Ana", telefono, email)` **no compila**: el error se detecta en tiempo de compilación, no en producción.

## 💰 Ejemplo clásico: el dinero

```java
// ❌ Antes: dos primitivos que siempre van juntos y sin reglas
double importe = 99.99;
String moneda = "EUR";
double total = importe * 1.21;          // ¿y si la moneda cambia?
```

```java
// ✅ Después: el concepto "Dinero" con su moneda y sus operaciones
public final class Dinero {
    private final long centimos;   // evitar double para no perder precisión
    private final String moneda;

    public Dinero(long centimos, String moneda) {
        if (moneda == null || moneda.length() != 3) {
            throw new IllegalArgumentException("Moneda ISO de 3 letras");
        }
        this.centimos = centimos;
        this.moneda = moneda;
    }

    public Dinero mas(Dinero otro) {
        if (!this.moneda.equals(otro.moneda)) {
            throw new IllegalArgumentException("No se pueden sumar monedas distintas");
        }
        return new Dinero(this.centimos + otro.centimos, moneda);
    }

    public Dinero conIVA(double porcentaje) {
        return new Dinero(Math.round(centimos * (1 + porcentaje / 100)), moneda);
    }

    @Override
    public String toString() {
        return String.format("%.2f %s", centimos / 100.0, moneda);
    }
}
```

> [!tip] `Dinero` también resuelve un bug clásico
> Usar `double` para dinero provoca **errores de redondeo** (`0.1 + 0.2 != 0.3`). Un `Dinero` con céntimos enteros y moneda **impide sumar euros con dólares** y elimina esos errores.

---

## 🎯 Ventajas

- La **validación está centralizada** en la clase del concepto.
- El código es **más expresivo**: `Email` ≠ `String`, `Dinero` ≠ `double`.
- **Se reducen errores**: el compilador impide mezclar conceptos distintos.
- Cumple **Tell, don't ask**: los objetos saben validarse y operar sobre sí mismos.
- Facilita **combinar con otros smells**: un Value Object bien hecho **no es una clase perezosa**.

> [!warning] No convertir todo en objeto
> Un `id`, un contador o un índice de bucle **no necesitan** clase propia. Convierte en objeto los valores que tienen **reglas, formato o semántica de dominio**. Y si el conjunto de valores es **cerrado**, usa un **`enum`** en lugar de una clase.

> [!example] Cuándo usar `enum`
> ```java
> public enum EstadoPedido { PENDIENTE, ENVIADO, ENTREGADO, CANCELADO }
> ```
> Mejor que `int estado = 2;` o `String estado = "ENVIADO";` (que acepta erratas como `"ENVIADO "`).

## ✅ Conclusión para examen

1. **Primitive Obsession** = usar `int`, `double`, `String`, `boolean` para conceptos del dominio que merecen su propia clase.
2. Es un problema de **expresividad, validación y seguridad de tipos**: la lógica se duplica y el compilador no ayuda.
3. **Detección:** muchos Strings desnudos, validaciones repetidas, booleanos bandera, comentarios que explican formatos.
4. **Solución:** **Value Objects** (`Email`, `Telefono`, `Dinero`, `Intervalo`) que encapsulen reglas; **enumerados** si el conjunto es cerrado; **Introduce Parameter Object** si van agrupados.
5. **Cuidado:** no envolver todo (ids, contadores) y no crear envoltorios vacíos (→ [[2. Codigo sucio por clases perezosas|Lazy Class]]).

> [!question] Pregunta típica
> *"¿Qué es Primitive Obsession y cómo se corrige?"*
> **Respuesta:** es el abuso de tipos primitivos para representar conceptos del dominio. Se detecta por Strings/números desnudos con validaciones repetidas y comentarios de formato. Se corrige **reemplazando el primitivo por una clase con su responsabilidad** (Value Object: `Email`, `Telefono`, `Dinero`) o por un **enum** si los valores son cerrados. Ej.: `String email` → `Email`, que valida el formato en su constructor.
