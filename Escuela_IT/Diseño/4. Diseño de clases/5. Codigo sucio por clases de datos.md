# 5. Código sucio por clases de datos

> [!info] Code smell · Clase de datos (Data Class)
> Relacionado con [[2. Codigo sucio por clases perezosas|Lazy Class]] · [[3. Codigo sucio por obsecion de tipos primitivos|Primitive Obsession]] · [[10. Principio de unica responsabilidad|SRP]]

---

## 📖 ¿Qué es?

Una **clase de datos** es una clase que **solo tiene atributos, getters y setters, y nada más**. Es un "soporte de datos tonto": no valida, no calcula, no protege sus invariantes. Toda la lógica que debería estar dentro **vive fuera**, en otras clases que la manipulan con demasiado detalle.

> [!warning] Señal de alarma
> Si para hacer cualquier operación con la clase necesitas **leer sus campos con getters, calcular fuera y volver a escribir con setters**, entonces la clase solo está **transportando datos** y su comportamiento está **en otro sitio**.

---

## ❓ Por qué es un problema (justificación)

- **Rompe la encapsulación:** cualquiera puede dejar el objeto en un estado inválido (`cuenta.setSaldo(-500)`).
- **Lógica dispersa:** las reglas del concepto se repiten en cada clase que lo usa.
- **Acoplamiento excesivo:** los clientes conocen **los detalles internos** de la clase ("a qué sabe" en vez de "qué sabe hacer").
- **Viola [[10. Principio de unica responsabilidad|SRP]]:** los datos están en un sitio y las reglas en otro; el cambio de una regla toca varios sitios.
- **Favorece [[7. Codigo sucio por cirugia a escopetazos|Shotgun Surgery]]:** cambiar una regla obliga a editar todos los que manipulan la clase.
- **Anemia del dominio:** el modelo es un saco de datos y toda la "inteligencia" se concentra en servicios gigantes.

> [!tip] Idea clave
> Una clase de datos **no es mala por tener datos**, sino por **no tener responsabilidad**. Los datos y las reglas que los protegen deben vivir **juntos** (encapsulación).

---

## 🔍 Cómo detectarla

Señales típicas:

- La clase tiene **solo campos, getters y setters** (quizá `toString`).
- **Ningún método** contiene lógica de negocio; todo es acceso directo.
- Otras clases hacen **`objeto.getX()` → calcular → `objeto.setX()`**.
- Hay **setters públicos** para todo, incluso para campos que no deberían cambiar.
- Las validaciones del objeto **no están en el objeto** (o no existen).
- Aparece en el code review la frase: *"esto lo calcula el servicio"*.

> [!note] No confundir con un DTO
> Un **DTO** (*Data Transfer Object*) es una clase de datos **legítima**: su única misión es **transportar datos entre capas** (API, red, formulario) y no debe tener lógica. El smell aparece cuando usas una Data Class como **modelo de dominio** y le pones la lógica fuera.

## 💥 Ejemplo (antes): `Cuenta` sin comportamiento

```java
public class Cuenta {
    private String titular;
    private double saldo;

    public Cuenta(String titular, double saldo) {
        this.titular = titular;
        this.saldo = saldo;
    }

    public String getTitular() { return titular; }
    public double getSaldo() { return saldo; }
    public void setSaldo(double saldo) { this.saldo = saldo; }
}
```

```java
public class CajeroService {

    public void retirar(Cuenta cuenta, double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("Monto inválido");
        }
        if (cuenta.getSaldo() < monto) {
            throw new IllegalStateException("Saldo insuficiente");
        }
        cuenta.setSaldo(cuenta.getSaldo() - monto);
    }

    public void depositar(Cuenta cuenta, double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("Monto inválido");
        }
        cuenta.setSaldo(cuenta.getSaldo() + monto);
    }
}
```

> [!danger] Problemas
> `Cuenta` es un **saco de datos**: `CajeroService` **pregunta** por el saldo, **calcula fuera** y **modifica con un setter**. Cualquier otra clase puede hacer `cuenta.setSaldo(-1000)` y dejar la cuenta en un estado imposible. Las reglas (no retirar de más, monto positivo) están **fuera** de la clase que debería protegerlas.

---

## ✅ Solución

> [!success] Regla general
> **Mover el comportamiento dentro de la clase de datos** y **eliminar los getters/setters innecesarios**. Que la clase **sepa hacer** sus operaciones en vez de exponer sus campos.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Move Method** (Mover método) | La lógica que manipula los datos vive en otra clase → moverla a la Data Class |
| **Encapsulate Field** (Encapsular campo) | El campo es público o tiene setter libre |
| **Remove Setting Method** (Eliminar setter) | El campo no debería cambiar desde fuera |
| **Replace Data Value with Object** | El campo es un primitivo con reglas → Value Object |
| **Extract Class** (la solución *contraria*) | Es un DTO legítimo al que se le quiere añadir lógica → separar DTO y modelo |

> [!tip] Heurística práctica
> Busca los **`get`/`set` que se llaman desde otras clases** y pregúntate: *¿qué está intentando hacer el cliente con esos datos?* Ese "qué" es un **método que falta** en la clase de datos. Muévelo dentro y ponle un nombre de negocio.

## 🔧 Ejemplo (después): `Cuenta` con comportamiento

```java
public class Cuenta {
    private final String titular;
    private double saldo;

    public Cuenta(String titular, double saldoInicial) {
        if (saldoInicial < 0) {
            throw new IllegalArgumentException("El saldo inicial no puede ser negativo");
        }
        this.titular = titular;
        this.saldo = saldoInicial;
    }

    public void retirar(double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("El monto debe ser positivo");
        }
        if (monto > saldo) {
            throw new IllegalStateException("Saldo insuficiente");
        }
        this.saldo -= monto;
    }

    public void depositar(double monto) {
        if (monto <= 0) {
            throw new IllegalArgumentException("El monto debe ser positivo");
        }
        this.saldo += monto;
    }

    public double saldo() { return saldo; }   // consulta, no modificación
    public String titular() { return titular; }
}
```

```java
// El servicio ya no manipula datos: solo coordina
public class CajeroService {
    public void retirar(Cuenta cuenta, double monto) {
        cuenta.retirar(monto);
    }
}
```

> [!note] Resultado
> La cuenta ya **no puede quedar en estado inválido**: el saldo solo cambia por operaciones válidas. Las reglas viven en **un único sitio** (`Cuenta`), el `setSaldo` desaparece y el servicio deja de "saber de más". Se cumple **Tell, don't ask**: le **decimos** a la cuenta qué hacer en vez de **preguntarle** por sus datos.

## 🔁 Otro ejemplo: `Pedido` con total calculado fuera

```java
// ❌ Antes
class Pedido {
    private List<Linea> lineas;
    public List<Linea> getLineas() { return lineas; }
}
// El total se calcula en 3 sitios distintos:
double total = pedido.getLineas().stream().mapToDouble(l -> l.getPrecio() * l.getCantidad()).sum();
```

```java
// ✅ Después
class Pedido {
    private final List<Linea> lineas = new ArrayList<>();

    public void agregar(Linea linea) {
        if (linea == null || linea.cantidad() <= 0) {
            throw new IllegalArgumentException("Línea inválida");
        }
        lineas.add(linea);
    }

    public double total() {
        return lineas.stream().mapToDouble(Linea::subtotal).sum();
    }
}
```

> [!tip] `tell, don't ask` en una frase
> **No le pidas los datos a un objeto para hacer su trabajo: dile que lo haga él.** Si escribes `objeto.getAlgo()` seguido de un cálculo, probablemente ese cálculo pertenece al objeto.

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| **Encapsulación real**: no hay estados inválidos | No todas las clases con datos son un smell: los **DTO sí** deben ser "tontos" |
| Reglas en **un único punto** | En **entidades JPA/Hibernate** a veces se necesitan getters/setters |
| Menos **acoplamiento** entre capas | Mover lógica puede **romper serialización** o frameworks |
| Código más **expresivo** (`cuenta.retirar(x)`) | Si el objeto es **solo un registro de BD**, quizá la lógica pertenezca a un servicio de dominio |
| Reduce [[7. Codigo sucio por cirugia a escopetazos\|Shotgun Surgery]] | Añadir comportamiento **sin criterio** puede crear [[1. Codigo sucio por clases grandes\|clases grandes]] |

> [!warning] Data Class vs DTO vs Value Object
> - **DTO:** solo transporta datos entre capas → **está bien** que sea "tonto".
> - **Value Object:** representa un valor inmutable con reglas (`Dinero`, `Email`) → **no** es un smell.
> - **Data Class (smell):** modelo de dominio que **debería** tener lógica pero no la tiene → **hay que corregirla**.

## ✅ Conclusión para examen

1. **Data Class** = clase con **atributos, getters y setters y nada más**; su comportamiento vive fuera.
2. Es un problema de **encapsulación y dispersión de la lógica**: se pueden crear estados inválidos y las reglas se duplican.
3. **Detección:** solo getters/setters, otras clases hacen `get → calcular → set`, setters públicos para todo.
4. **Solución:** **Move Method** (traer el comportamiento dentro), **Encapsulate Field**, **Remove Setting Method**, **Replace Data Value with Object**; aplicar **Tell, don't ask**.
5. **Cuidado:** los **DTO** son clases de datos legítimas; el smell es usar una Data Class como **modelo de dominio**.

> [!question] Pregunta típica
> *"¿Qué es una Data Class y cómo se refactoriza?"*
> **Respuesta:** es una clase que solo tiene atributos y getters/setters, sin comportamiento, por lo que otras clases la manipulan con demasiado detalle y pueden dejarla en estado inválido. Se detecta porque los clientes hacen `get → calcular → set`. Se corrige **moviendo los métodos que usan sus datos dentro de la clase** (Move Method), encapsulando campos y eliminando setters innecesarios. Ej.: `CajeroService.retirar(cuenta, m)` → `Cuenta.retirar(m)`.
