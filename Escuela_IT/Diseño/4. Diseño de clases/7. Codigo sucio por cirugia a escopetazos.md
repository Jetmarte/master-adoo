# 7. Código sucio por cirugía a escopetazos

> [!info] Code smell · Cirugía a escopetazos (Shotgun Surgery)
> Relacionado con [[8. Codigo sucio por Cambios Divergentes|Divergent Change]] · [[1. Codigo sucio por clases grandes|Clase grande]] · [[10. Principio de unica responsabilidad|SRP]]

---

## 🏷️ Sinónimos

| Término | Fuente |
|---------|--------|
| **Shotgun Surgery** | *Refactoring* (Code Smells) — Martin Fowler |
| **Cirugía a escopetazos** | Traducción habitual al español |
| **Cambio disperso** | Nombre coloquial: un cambio → muchos archivos |

---

## 📖 ¿Qué es?

Ocurre cuando **cada vez que se hace un cambio, hay que hacer un montón de pequeños cambios en un montón de clases diferentes**. El cambio conceptual es **uno**, pero está **esparcido** por el sistema.

> [!warning] Señal de alarma
> Para cambiar una sola regla (p. ej. el IVA) tienes que abrir **5 archivos distintos** y modificar cada uno. Y si olvidas uno, el sistema **falla en silencio** en algún caso concreto.

> [!tip] La relación ideal
> Idealmente existe una relación **uno a uno** entre los **cambios comunes** y las **clases**: un cambio conceptual → una clase que tocar.

---

## ❓ Por qué es un problema (justificación)

- **Cambios difíciles de localizar:** la lógica está repartida y no hay un punto único.
- **Fácil olvidar un sitio:** el bug aparece en producción solo en el caso que no actualizaste.
- **Alto acoplamiento:** muchas clases dependen del mismo detalle.
- **Riesgo en cada cambio:** cuanto más código tocas, más probabilidad de romper algo.
- **Baja cohesión:** cada clase mezcla trozos de la misma responsabilidad.
- **Contradice la idea de software blando:** deberíamos poder "saltar a un solo punto y hacer el cambio".

> [!warning] Shotgun Surgery ≠ Divergent Change
> Son **inversos**:
> - **Divergent Change:** **una clase** cambia por **muchos motivos** (1 → N).
> - **Shotgun Surgery:** **un cambio** obliga a tocar **muchas clases** (N → 1).
> A menudo aparecen **juntos**: una clase grande con varias responsabilidades se parte mal y reparte una misma lógica entre muchas clases.

---

## 🔍 Cómo detectarla

Señales típicas:

- Una regla de negocio está **copiada** en varias clases.
- **Constantes mágicas repetidas** (`0.19`, `"EUR"`, `"ACTIVO"`) en distintos archivos.
- Un cambio de requisito (nuevo impuesto, nuevo estado, nueva moneda) obliga a editar **muchos métodos** que no están juntos.
- En el control de versiones, un mismo concepto aparece en **commits que tocan 10 archivos**.
- Cada clase tiene un **trocito** del mismo cálculo o de la misma validación.

---

## 💥 Ejemplo (antes): cambiar el IVA toca media aplicación

```java
public class CalculadoraImpuesto {
    public double calcular(double base) {
        return base * 0.19;                       // ← IVA hardcodeado
    }
}
```

```java
public class Factura {
    private double base;

    public double total() {
        return base + base * 0.19;                // ← otra vez el IVA
    }
}
```

```java
public class GeneradorReporte {
    public String generar(double base) {
        double iva = base * 0.19;                 // ← otra vez
        return "Base: " + base + ", IVA: " + iva + ", Total: " + (base + iva);
    }
}
```

```java
public class ReporteAnual {
    public double ivaRecaudado(double[] bases) {
        double total = 0;
        for (double base : bases) {
            total += base * 0.19;                 // ← y otra vez
        }
        return total;
    }
}
```

> [!danger] Problemas
> El IVA (`0.19`) está **repetido en cuatro clases**. Cuando el IVA cambie a `0.21`, hay que tocar **las cuatro**. Si se olvida una, `Factura` y `GeneradorReporte` darán **totales distintos** para la misma operación. Es un cambio conceptual **uno** repartido en **N clases**.

---

## ✅ Solución

> [!success] Regla general
> **Mover las responsabilidades entre las clases para evitarlo.** Si no hay una clase que sea buena candidata, **crearla**: normalmente una clase que represente **la regla** (impuesto, tarifa, parámetros fiscales).

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Move Method / Move Field** | El método/campo usa más datos de otra clase que de la suya |
| **Inline Class** | Una clase solo existe para trocear una responsabilidad → integrarla |
| **Extract Class** | Crear una clase que concentre la regla dispersa |
| **Replace Magic Number with Symbolic Constant** | Constantes mágicas repetidas |
| **Introduce Parameter Object** | El grupo de datos de la regla viaja por todas partes |

## 🔧 Ejemplo (después): una única fuente de verdad

```java
// La regla vive en un solo sitio
public final class ParametrosFiscales {
    public static final double IVA_GENERAL = 0.19;

    private ParametrosFiscales() { }
}
```

```java
public class CalculadoraImpuesto {
    public double calcular(double base) {
        return base * ParametrosFiscales.IVA_GENERAL;
    }
}
```

```java
public class Factura {
    private double base;

    public double total() {
        return base + base * ParametrosFiscales.IVA_GENERAL;
    }
}
```

```java
public class GeneradorReporte {
    public String generar(double base) {
        double iva = base * ParametrosFiscales.IVA_GENERAL;
        return "Base: " + base + ", IVA: " + iva + ", Total: " + (base + iva);
    }
}
```

```java
public class ReporteAnual {
    public double ivaRecaudado(double[] bases) {
        double total = 0;
        for (double base : bases) {
            total += base * ParametrosFiscales.IVA_GENERAL;
        }
        return total;
    }
}
```

> [!note] Resultado
> Ahora el IVA cambia **en un único sitio**. Las cuatro clases leen la **misma fuente de verdad** y no pueden desincronizarse.

### Mejor aún: mover el cálculo completo

```java
// La lógica del impuesto, no solo la constante, está centralizada
public class Impuesto {
    private final double tasa;

    public Impuesto(double tasa) {
        if (tasa < 0 || tasa > 1) {
            throw new IllegalArgumentException("Tasa inválida");
        }
        this.tasa = tasa;
    }

    public double sobre(double base) {
        return base * tasa;
    }

    public double totalConImpuesto(double base) {
        return base + sobre(base);
    }
}
```

```java
public class Factura {
    private final double base;
    private final Impuesto impuesto;

    public Factura(double base, Impuesto impuesto) {
        this.base = base;
        this.impuesto = impuesto;
    }

    public double total() {
        return impuesto.totalConImpuesto(base);
    }
}
```

> [!tip] Regla de oro
> Si al cambiar una regla tienes que abrir **más de un archivo** y los cambios son "el mismo cambio", **falta una clase** que represente esa regla.

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios de corregirlo | ⚠️ Contraindicaciones / cuidado |
|------------------------------|----------------------------------|
| Cambios **localizados** en un punto | Centralizar **demasiado** puede crear una [[1. Codigo sucio por clases grandes\|clase grande]] |
| Menos riesgo de **olvidar un sitio** | No todas las duplicaciones son iguales: a veces son **coincidencias** |
| Menos **acoplamiento** entre clases | Si la regla cambia **con frecuencia e independencia**, quizá conviene estrategia/inyección |
| Código más **cohesionado** | Mover lógica puede afectar a **tests** y otras capas |

> [!warning] No centralizar por reflejo
> Antes de unificar, comprueba que los trozos cambian **por la misma razón**. Si dos cálculos parecidos pueden evolucionar por separado, unificarlos crea un acoplamiento **artificial**.

## ✅ Conclusión para examen

1. **Shotgun Surgery** = **un cambio conceptual** obliga a hacer **muchos cambios pequeños en muchas clases**.
2. Es un problema de **dispersión y acoplamiento**: es fácil olvidar un sitio y romper la consistencia.
3. **Detección:** reglas/constantes repetidas, un cambio de requisito toca muchos archivos, commits que modifican 10 clases por el mismo motivo.
4. **Solución:** **Move Method/Field**, **Extract Class** para crear la clase que represente la regla, **Inline Class**, **constantes simbólicas**; centralizar en una **única fuente de verdad**.
5. **Distinción clave:** **Divergent Change** = una clase cambia por muchos motivos; **Shotgun Surgery** = un motivo cambia muchas clases.

> [!question] Pregunta típica
> *"¿Qué es Shotgun Surgery y en qué se diferencia de Divergent Change?"*
> **Respuesta:** es un smell en el que un solo cambio de requisito obliga a modificar muchas clases porque la lógica está dispersa (p. ej. el IVA repetido en 4 clases). Se detecta porque el mismo concepto aparece en varios archivos y es fácil olvidar uno. Se corrige **moviendo la responsabilidad a una única clase** (Move Method/Field, Extract Class) que sea la fuente de verdad. **Diferencia:** Divergent Change es **una clase con muchos motivos de cambio** (1→N); Shotgun Surgery es **un motivo de cambio repartido en muchas clases** (N→1).
