# 6. Código sucio por librería incompleta

> [!info] Code smell · Librería incompleta (Incomplete Library Class)
> Relacionado con [[7. Codigo sucio por cirugia a escopetazos|Shotgun Surgery]] · [[2. Codigo sucio por clases perezosas|Lazy Class]] · [[3. Codigo sucio por obsecion de tipos primitivos|Primitive Obsession]]

---

| Término | Fuente |
|---------|--------|

| **Clase de librería incompleta** | Traducción habitual al español |
| **Wrapper / Utilidades** | Nombres habituales de la solución |

---

## 📖 ¿Qué es?

Ocurre cuando una **clase de una librería externa no tiene las funciones que necesitas** y, además, **no puedes modificarla** porque no es tuya. Entonces terminas escribiendo **código repetido, improvisado o parcheado** por todo el proyecto para suplir lo que falta.

> [!warning] Señal de alarma
> El mismo bloque de código ("contar líneas de un archivo", "formatear una fecha", "validar un IBAN") **copiado y pegado** en muchos sitios, porque la librería no lo ofrece.

> [!tip] No es culpa de la librería
> Los desarrolladores de librerías **no son omniscientes**: es imposible prever todos los usos. El problema no es que falte el método, sino **cómo lo suplimos**: si lo repetimos por todo el código, el diseño se ensucia.

---

## ❓ Por qué es un problema (justificación)

- **Código duplicado:** la misma lógica de relleno aparece en N sitios.
- **Mantenimiento costoso:** si hay que optimizar o corregir esa lógica, se toca en **todos** lados (→ [[7. Codigo sucio por cirugia a escopetazos|Shotgun Surgery]]).
- **Fragilidad:** cada copia puede evolucionar de forma distinta y aparecer **inconsistencias**.
- **Acoplamiento a la librería:** el código de negocio queda lleno de detalles de una API que no controlas.
- **Difícil de testear:** la lógica improvisada está mezclada con el uso de la librería.
- **Riesgo al actualizar:** si la librería cambia o añade la función, hay que limpiar todas las copias.

---

## 🔍 Cómo detectarla

Señales típicas:

- **El mismo bloque** que usa una API externa se repite en varios sitios.
- Comentarios del tipo *"la librería no tiene esto, lo hago a mano"*.
- Métodos estáticos sueltos en clases de negocio para "adaptar" la librería.
- Código que **envuelve** una clase externa solo en algunos lugares y en otros se usa directamente.
- Actualizaciones de la librería que **rompen** decenas de sitios.

---

## 💥 Ejemplo (antes): lógica repetida porque `File` no lo trae

La clase `File` de Java **no tiene** un método para contar líneas. Entonces muchos desarrolladores escriben este bloque **cada vez que lo necesitan**:

```java
import java.io.*;

public class ContadorLineas {
    public static void main(String[] args) throws IOException {
        File archivo = new File("datos.txt");

        int lineas = 0;
        BufferedReader br = new BufferedReader(new FileReader(archivo));
        while (br.readLine() != null) {
            lineas++;
        }
        br.close();

        System.out.println("Total de líneas: " + lineas);
    }
}
```

> [!danger] Problemas
> La lógica de conteo está **mezclada** con el programa que la usa. Si se repite en 10 informes, optimizar la lectura obliga a cambiarla en **10 sitios**. Además, el `br.close()` **no está en un `finally`**: si salta una excepción, el fichero queda abierto.

---

## ✅ Solución

> [!success] Regla general
> **Crear una clase con los métodos extra que necesitas** (utilidad, wrapper o *adapter*) y **centralizar** ahí la funcionalidad que falta. El resto del código usa **tu clase**, no la librería directamente.

### Técnicas de refactorización

| Técnica | Cuándo usarla |
|---------|---------------|
| **Introduce Foreign Method** | Necesitas **un solo método** sobre una clase externa → método estático en una utilidad |
| **Introduce Local Extension** | Necesitas **varios métodos** → crear una clase propia (wrapper o subclase) |
| **Wrapper / Adapter (composición)** | La clase externa es compleja o puede cambiar → **envolverla**, no heredar |
| **Extract Class** | La lógica de relleno está mezclada en una clase de negocio → sacarla a una utilidad |
| **Actualizar la librería** | La versión nueva ya incorpora la función (ej. `java.time`) |

## 🔧 Ejemplo (después): `FileUtils` centraliza lo que falta

```java
import java.io.*;
import java.nio.file.Files;

public final class FileUtils {

    private FileUtils() { }   // clase de utilidades: no se instancia

    // Introduce Foreign Method: amplía File sin modificarla
    public static int contarLineas(File archivo) throws IOException {
        try (BufferedReader br = new BufferedReader(new FileReader(archivo))) {
            int lineas = 0;
            while (br.readLine() != null) {
                lineas++;
            }
            return lineas;
        }
    }
}
```

```java
import java.io.File;
import java.io.IOException;

public class Demo {
    public static void main(String[] args) throws IOException {
        File archivo = new File("datos.txt");
        int total = FileUtils.contarLineas(archivo);
        System.out.println("Total de líneas: " + total);
    }
}
```

> [!note] Resultado
> El `try-with-resources` **cierra siempre** el fichero (incluso con excepción). La lógica está **en un único sitio**: si se optimiza, todo el proyecto se beneficia. El código de negocio ya no conoce los detalles de `FileReader`/`BufferedReader`.

## 🔁 Variante con composición: un wrapper

Cuando necesitas **varios métodos** o quieres **aislar** el código de la librería (por si cambia), envuelve la clase externa:

```java
public class Archivo {
    private final File file;

    public Archivo(String ruta) {
        this.file = new File(ruta);
    }

    public int contarLineas() throws IOException {
        try (var br = new java.io.BufferedReader(new java.io.FileReader(file))) {
            return (int) br.lines().count();
        }
    }

    public String nombre() { return file.getName(); }
    public long tamano()   { return file.length(); }
}
```

> [!warning] Herencia vs composición
> **Evita heredar** de una clase de librería (`class MiFile extends File`) para añadir métodos: te acoplas a su implementación interna y puedes romper su contrato. **Envuelve** (composición) y expón solo lo que necesitas.

---

## 📅 El caso clásico: `Date` y `Calendar`

`java.util.Date` y `Calendar` son **notoriamente limitados e incómodos** (meses desde 0, mutabilidad, zonas horarias). La solución moderna **no es copiar lógica** en cada clase, sino:

- usar **`java.time`** (`LocalDate`, `LocalDateTime`, `Duration`, `Period`), que ya trae lo que falta;
- o crear utilidades propias (`Fechas.hoy()`, `Fechas.formatear(...)`) si necesitas un formato corporativo.

```java
// ✅ Con java.time (Java 8+)
LocalDate hoy = LocalDate.now();
LocalDate vencimiento = hoy.plusDays(30);
boolean vencida = LocalDate.now().isAfter(vencimiento);
```

> [!tip] Antes de envolver, actualiza
> Comprueba si la **versión nueva** de la librería ya ofrece lo que buscas. Envolver algo que ya existe es **deuda técnica innecesaria**.

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones / cuidado |
|---------------|----------------------------------|
| **Elimina duplicación** de código de relleno | No envolver **todo**: crea indirección y clases de relleno |
| Un **único punto** para corregir y optimizar | Un wrapper **sin valor añadido** es una [[2. Codigo sucio por clases perezosas\|Lazy Class]] |
| Aísla el código de negocio de la librería | Si la librería **ya lo resuelve**, no la envuelvas |
| Facilita **tests** (puedes simular el wrapper) | Demasiados wrappers propios pueden **reinventar la librería** |
| Permite **cambiar de librería** sin tocar el dominio | En **código de un solo uso**, una utilidad puede ser excesiva |

> [!warning] No reinventar la rueda
> Una clase `StringUtils` propia con 40 métodos que ya existen en Apache Commons o en el JDK es **otro smell**. Envuelve **solo lo que falta** o lo que necesitas **estabilizar**.

## ✅ Conclusión para examen

1. **Incomplete Library Class** = una clase de librería **no cubre una necesidad** y **no se puede modificar**.
2. El problema no es la librería, sino **cómo lo suplimos**: código repetido y parcheado por todo el proyecto.
3. **Detección:** el mismo bloque de adaptación repetido, comentarios "la librería no lo trae", métodos estáticos sueltos en clases de negocio.
4. **Solución:** **Introduce Foreign Method** (un método) o **Local Extension** (wrapper/composición); centralizar en una clase de utilidades; **actualizar** la librería si ya lo ofrece.
5. **Cuidado:** no envolver lo que ya existe ni crear wrappers vacíos (→ [[2. Codigo sucio por clases perezosas|Lazy Class]]); preferir **composición** sobre herencia.

> [!question] Pregunta típica
> *"¿Qué es Incomplete Library Class y cómo se resuelve?"*
> **Respuesta:** es el smell que aparece cuando una clase de una librería externa no tiene la funcionalidad que necesitas y no puedes modificarla, por lo que acabas duplicando código de relleno. Se detecta por bloques idénticos que usan la API externa repetidos por el proyecto. Se resuelve creando una **clase propia con los métodos extra** (Foreign Method o Local Extension: utilidad o wrapper por composición) que centralice esa lógica. Ej.: `FileUtils.contarLineas(File)` en lugar de copiar el bucle de lectura.
