# 3. Nombrado del código limpio

> [!info] Nombres que revelan la intención
> **Sinónimos:** *Choose Descriptive Names*, *Choose Names at the Appropriate Level of Abstraction*, *Use Standard Nomenclature Where Possible*, *Unambiguous Names*, *Use Long Names for Long Scopes*, *Avoid Encodings*, *Names Should Describe Side-Effects* — todos de *Clean Code* (Robert C. Martin).
> Relacionado con [[1. Formato de codigo limpio|Formato]] y [[2. Comentarios de codigo limpio|Comentarios]].

---

## 📖 ¿Qué es un buen nombre?

Un nombre debe **revelar su intención**: por qué existe, qué hace y cómo se usa. El nombre es la primera documentación del código y la única que se lee **siempre**, incluso en un `git diff`.

> [!tip] Idea clave
> «Una línea de código se escribe una vez y se lee cientos de veces.» — Cox
> Elegir buenos nombres lleva tiempo, pero **ahorra más del que cuesta**.

---

## ❓ Por qué es importante (justificación)

Los nombres deben revelar su intención para facilitar la legibilidad y el **mantenimiento correctivo, perfectivo y adaptativo**.

- Un nombre malo obliga a **leer la implementación** para entender qué hace.
- Un nombre malo obliga a **escribir comentarios** que se quedarán obsoletos.
- Un nombre ambiguo provoca **errores** al usar la cosa equivocada.
- Un buen nombre permite **hablar del código** en reuniones, revisiones y pair programming.

```java
// ❌ Obliga a leer el cuerpo para saber qué es
int d;
int mpd;
List<String> lista1;

// ✅ El nombre basta para entenderlo
int elapsedTimeInDays;
int daysSinceModification;
List<String> clientesActivos;
```

---

## 🔍 Implicaciones: cómo nombrar bien

### 1️⃣ Nombres descriptivos

Elige nombres que digan **qué representa** la variable o **qué hace** la función.

```java
// ❌ Descriptivo solo para el autor original
int x = 0;
String s = "Omar";

// ✅ Cualquiera lo entiende
int intentosFallidos = 0;
String nombreUsuario = "Omar";
```

---

### 2️⃣ Nombres al nivel de abstracción apropiado

El nombre debe hablar del **concepto del dominio**, no del detalle de implementación.

```java
// ❌ Detalle de implementación en el nombre
String[] arrayDeCadenasDeCorreos = obtenerCorreos();

// ✅ Nivel de abstracción correcto
String[] correos = obtenerCorreos();
```

Otro ejemplo: si un método devuelve un `Map<String, Empleado>`, no lo llames `listaEmpleados` — direcciona lo que **es**, no cómo está guardado.

---

### 3️⃣ Nomenclatura estándar donde sea posible

Usa las **convenciones conocidas** de la comunidad y del lenguaje: no inventes.

```java
// ✅ Convenciones Java
public class Factura {                 // clase: sustantivo, PascalCase
    private static final double IVA = 0.19; // constante: MAYÚSCULAS_CON_GUIONES

    public double calcularTotal() {    // método: verbo, camelCase
        return 0;
    }
}
```

---

### 4️⃣ Nombres no ambiguos

Un nombre debe tener **una única interpretación** en su contexto.

```java
// ❌ ¿'fecha' es del pedido, de la entrega o de la factura?
void actualizar(Date fecha) { /* … */ }

// ✅ Sin ambigüedad
void actualizarFechaEntrega(Date fechaEntrega) { /* … */ }
```

---

### 5️⃣ Nombres largos para ámbitos largos

Cuanto **mayor** sea el alcance, más **descriptivo** debe ser el nombre.

| Ámbito | Longitud del nombre | Ejemplo |
|--------|---------------------|---------|
| **Variable de bucle** | Muy corto | `i` |
| **Variable local de un método** | Corto | `total` |
| **Atributo de clase** | Medio | `saldoPendiente` |
| **Método público / constante** | Largo y descriptivo | `calcularTotalConImpuestos()` |

```java
// ✅ 'i' es aceptable: alcance mínimo y uso tradicional
for (int i = 0; i < clientes.size(); i++) {
    procesar(clientes.get(i));
}

// ✅ Nombre largo para un alcance amplio
public double calcularTotalConImpuestosYDescuentos(Pedido pedido) { /* … */ }
```

> [!note] Excepción razonable
> En contadores de bucles muy cortos se aceptan `i`, `j`, `k` (nunca `l`, que se confunde con `1`). Es una tradición estándar: «allá donde fueres, haz lo que vieres».

---

### 6️⃣ Evita codificaciones

No metas el **tipo** ni el **ámbito** en el nombre (notación húngara y similares).

```java
// ❌ Notación húngara / códigos de tipo
int iAge;
int m_iAge;
String strNombre;
class CStudent { }

// ✅ El tipo ya lo dice la declaración
int age;
String nombre;
class Student { }
```

---

### 7️⃣ El nombre debe describir los efectos laterales

Si una función **hace algo más** de lo que su nombre sugiere, el nombre miente.

```java
// ❌ Parece una comprobación, pero además guarda
boolean comprobarPassword(String usuario, String password);

// ✅ El nombre revela el efecto secundario
boolean comprobarYGuardarPassword(String usuario, String password);
// ✅ Mejor todavía: separar responsabilidades
boolean comprobarPassword(String usuario, String password);
void guardarPassword(String usuario, String password);
```

> [!warning] Efectos laterales ocultos
> Un `get` que modifica estado, un `validar` que envía un correo o un `calcular` que escribe en la BD son **trampas** que cuestan horas de depuración. Si hay un efecto secundario, que el nombre lo diga (o mejor: sepáralo).

## 📐 Implicaciones por tipo de elemento

| Elemento | Regla | Ejemplo |
|----------|-------|---------|
| **Paquete** | **Sustantivo** en minúsculas | `models.customers` |
| **Clase** | **Sustantivo** y empieza en mayúsculas | `Controller`, no `Control` |
| **Método** | **Verbo** o frase con verbo, minúscula | `calcularTotal()` |
| **Getter / setter** | `get` / `set`; `is` para booleanos | `getNombre()`, `isActivo()`, `setEdad()` |
| **Constante** | MAYÚSCULAS con guiones bajos | `IVA_POR_DEFECTO` |
| **Interfaz** | Sustantivo o adjetivo de capacidad | `RepositorioUsuarios`, `Comparable` |

## ⚠️ Violaciones típicas

| Violación | ❌ Mal | ✅ Bien |
|-----------|--------|---------|
| **Nombre que exige comentario** | `d`, `mpd`, `lista1` | `elapsedTimeInDays`, `daysSinceModification` |
| **Separadores de palabras** | `nombre_usuario`, `nombre-usuario` | `nombreUsuario` (salvo constantes) |
| **Una sola letra** | `O`, `l` (se confunden con `0` y `1`) | Nombres descriptivos; `i`, `j`, `k` solo en bucles |
| **Acrónimos no internacionales** | `BHPS` | `BehaviourHumanPredictionSystem` |
| **Códigos de tipo / ámbito** | `iAge`, `m_iAge`, `CStudent` | `age`, `Student` |
| **Palabras vacías o redundantes** | `StudentData`, `boardObject`, `theMessage` | `Student`, `board`, `message` |
| **Nombres en serie** | `player1`, `player2` | `players`, `winnerPlayer`, `loserPlayer` |
| **Nombres desinformativos** | `customerList` cuando es un `Set` | `customerSet` o `customers` |
| **Nombres indistinguibles** | `XYZControllerForEfficientHandlingOfStrings` vs `…StorageOfStrings` | Nombres que destaquen la diferencia real |
| **Nombres polisémicos** | `book` como registro de hotel y como libro | `reservaHabitacion`, `libro` |
| **Nombres graciosos / juegos de palabras** | `cagadaTotal` | `totalConErrores` |

### 🧩 Ejemplo integrador

```java
// ❌ Todo mal: códigos de tipo, serie, palabras vacías y polisemia
public class CStudentData {
    private int iAge;
    private String strName1;

    public void getData() { /* … */ }
}

// ✅ Todo bien
public class Student {
    private int age;
    private String name;

    public int getAge() { return age; }
    public String getName() { return name; }
}
```

## ⚖️ Una palabra para un concepto

Elige **una sola palabra** para cada concepto abstracto y **aférrate a ella**.

```java
// ❌ Tres verbos para lo mismo: ¿son sinónimos o hacen cosas distintas?
empleado.getNombre();
empleado.retrieveApellido();
empleado.fetchEdad();

// ✅ Un único verbo para el mismo concepto
empleado.getNombre();
empleado.getApellido();
empleado.getEdad();
```

> [!tip] Vocabulario del dominio
> Usa palabras del **dominio del problema** (`Student`, `TicketVisitor`, `ReaderFactory`, `discard`…) y conocidas por la comunidad de programadores. Así el código habla el idioma del negocio. Véase [[3.  Analisis del dominio|Análisis del dominio]].

## 🎯 Conclusión para examen

1. Un nombre debe **revelar su intención**: por qué existe, qué hace y cómo se usa.
2. **Nombres pronunciables**, sin códigos de tipo/ámbito, sin palabras vacías y sin series (`player1`, `player2`).
3. **Paquete** = sustantivo minúscula; **clase** = sustantivo mayúscula; **método** = verbo minúscula; **constante** = MAYÚSCULAS_CON_GUIONES.
4. **Nombres largos para ámbitos largos**; `i`, `j`, `k` solo en bucles cortos (nunca `l`).
5. **Una palabra por concepto**: si usas `get`, no uses también `retrieve` y `fetch` para lo mismo.
6. Si un nombre **necesita un comentario**, el nombre está mal: cámbialo.
7. **Renombrar sin miedo**: las herramientas modernas (IDE, refactorización) hacen el cambio seguro.

> [!question] Pregunta típica
> *"¿Qué características debe tener un buen nombre de variable y de método?"*
> **Respuesta:** debe **revelar la intención** (por qué existe, qué hace y cómo se usa), ser **pronunciable**, estar al **nivel de abstracción** adecuado, usar la **nomenclatura estándar** y el **vocabulario del dominio**, no ser ambiguo y, si tiene efectos secundarios, indicarlos en el nombre. Los métodos deben empezar por **verbo** (`calcularTotal`), los getters usar `get`/`is`, las clases ser **sustantivos** en mayúscula y los paquetes sustantivos en minúscula. Se evitan códigos de tipo (`iAge`, `CStudent`), palabras vacías (`Data`, `Object`), series (`player1`) y nombres de una letra.
