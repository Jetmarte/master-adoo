# 1. Formato de código limpio

> [!info] Formato y legibilidad
> El formato no es estética: es una **herramienta de comunicación**. Un código bien formateado se lee, se mantiene y se comparte mejor.
> Relacionado con [[3. Nombrado del codigo limpio|Nombrado]] y [[2. Comentarios de codigo limpio|Comentarios]].

---

## 📖 ¿Qué es el formato del código?

Es el conjunto de **reglas visuales** que organizan el código fuente:

- dónde van las **líneas en blanco**,
- cuánto **sangra** cada bloque,
- qué **longitud** tienen las líneas,
- en qué **orden** aparecen atributos y métodos,
- cómo se **separan** los elementos de una expresión.

> [!tip] Idea clave
> El formato correcto hace que la **estructura del código sea obvia a simple vista**, sin necesidad de ejecutarlo ni de leerlo entero.

---

## ❓ Por qué es importante (justificación)

- **Más fácil de leer y entender:** otros desarrolladores (y tu yo futuro) captan la lógica y la estructura rápidamente.
- **Más fácil de mantener:** reduce la probabilidad de introducir errores al modificar o extender el código.
- **Facilita la colaboración:** un equipo comparte un **lenguaje visual común**.
- **Reduce el ruido en los diffs:** un formato consistente evita cambios irrelevantes en Git.

> [!quote] Robert C. Martin
> «Los conceptos que están estrechamente relacionados deben mantenerse verticalmente cercanos.»

---

## 🧩 Ejemplo en Java

### ❌ Mal formateado

```java
public class Pedido {
private String cliente; private double total;
    public Pedido(String cliente){this.cliente=cliente;}
  public void agregarProducto(double precio, int cantidad, boolean aplicarDescuento, double porcentajeDescuento){ total += precio * cantidad * (aplicarDescuento ? (1 - porcentajeDescuento / 100) : 1); }
    public String getCliente(){return cliente;}
}
```

Problemas:

- Atributos **mezclados** con métodos.
- **Sangría inconsistente** (0, 4 y 2 espacios en el mismo bloque).
- Una línea de **más de 150 caracteres** con toda la lógica escondida.
- Falta de **líneas en blanco** que separen conceptos.
- Llaves y operadores **pegados** que dificultan la lectura.

---

### ✅ Bien formateado

```java
public class Pedido {
    private String cliente;
    private double total;

    public Pedido(String cliente) {
        this.cliente = cliente;
    }

    public void agregarProducto(double precio, int cantidad,
                                boolean aplicarDescuento,
                                double porcentajeDescuento) {
        double subtotal = precio * cantidad;
        double descuento = aplicarDescuento
                ? subtotal * porcentajeDescuento / 100
                : 0;
        total += subtotal - descuento;
    }

    public String getCliente() {
        return cliente;
    }
}
```

Mejoras:

- Atributos **al principio** de la clase.
- **Línea en blanco** entre atributos, constructor y métodos.
- **Sangría consistente** de 4 espacios.
- Parámetros largos **partidos en varias líneas**.
- Cálculo complejo **dividido en variables con nombre**.
- La función que **llama** (`agregarProducto`) aparece antes que las que **son llamadas**.

## 🔍 Reglas clave

### 1️⃣ Organización lógica: todo en su lugar

| Regla | Qué dice | Ejemplo |
|-------|----------|---------|
| **Separación de bloques** | Una línea en blanco entre grupos lógicos | Entre atributos y métodos, entre métodos |
| **Atributos al principio** | Las variables de instancia van al inicio de la clase | `private String cliente;` arriba |
| **Proximidad de funciones** | La que llama va **antes** que la llamada | `procesar()` antes de `validar()` |
| **Agrupación por funcionalidad** | Juntas las funciones que hacen tareas similares | Todos los `get…` juntos |

```java
// ✅ La función que llama aparece primero
public void registrar(Usuario usuario) {
    validar(usuario);
    guardar(usuario);
}

private void validar(Usuario usuario) { /* … */ }
private void guardar(Usuario usuario) { /* … */ }
```

---

### 2️⃣ Proximidad y alcance de variables: menos es más

Declara cada variable **lo más cerca posible de su primer uso**. Así se entiende su propósito y cuánto tiempo estará activa.

```java
// ❌ Declaración lejos del uso: ¿para qué era 'descuento'?
double descuento;
String nombre = "Ana";
int edad = 30;
// … 20 líneas después …
descuento = 10;
```

```java
// ✅ Declaración justo antes de usarla
String nombre = "Ana";
int edad = 30;
// …
double descuento = 10;
```

---

### 3️⃣ Longitud de línea y espacio en blanco

- **Líneas cortas:** ideal ≈ **40 caracteres**; máximo recomendado **80–120**.
- **Espacio horizontal** con tres usos:

| Uso | Qué hace | Ejemplo |
|-----|----------|---------|
| **Asociar** | Une elementos fuertemente relacionados | `variable = valor` |
| **Separar** | Distancia elementos poco relacionados | `a = b + c;   d = e + f;` |
| **Enfatizar** | Aclara la precedencia de operadores | `(a + b) * c` |

```java
// ❌ Difícil de leer
double total=precio*cantidad+iva*(1-descuento);

// ✅ Con espacios que reflejan la precedencia
double total = (precio * cantidad + iva) * (1 - descuento);
```

---

### 4️⃣ Jerarquía y sangría: la estructura visible

El código tiene **niveles**: archivo → clase → método → bloque → sentencia. Cada nivel es un ámbito donde se definen nombres, y la **sangría** debe reflejarlo.

```java
public class Cuenta {              // nivel 1: clase
    public void retirar(double c) { // nivel 2: método
        if (c > 0) {                // nivel 3: bloque
            saldo -= c;             // nivel 4: sentencia
        }
    }
}
```

> [!warning] Consistencia
> Da igual si usas **4 espacios** o **tabuladores**: lo importante es que **todo el equipo use lo mismo**. Un `.editorconfig` o un formateador automático lo garantiza.

## ⚠️ Errores comunes

| Error | Por qué es malo | Solución |
|-------|-----------------|----------|
| **Tabuladores para alinear columnas** | Se descuadra si los nombres tienen distinta longitud | Un solo espacio antes del valor |
| **Romper la sangría en líneas cortas** | La estructura deja de verse | Sangrar siempre, aunque la línea sea corta |
| **Líneas kilométricas** | Obligan a hacer scroll horizontal | Partir en variables o líneas |
| **Todo pegado sin líneas en blanco** | No se distinguen los bloques lógicos | Separar grupos con una línea vacía |
| **Formato distinto por archivo** | Ruido en los diffs y en las revisiones | Formateador y configuración comunes |

## 🤖 Automatización del formato

| Lenguaje | Herramientas típicas |
|----------|----------------------|
| **Java** | `google-java-format`, Checkstyle, Spotless |
| **JavaScript / TypeScript** | Prettier, ESLint |
| **Python** | Black, Ruff |
| **Cualquiera** | EditorConfig + formateador del IDE al guardar |

> [!tip] Regla de oro
> El formato **no se discute en las revisiones de código**: lo impone la herramienta. Las revisiones se dedican a la lógica y al diseño.

## 🎯 Conclusión para examen

1. **Formato** = organización visual del código para que su **estructura** y su **lógica** se entiendan a simple vista.
2. **Atributos arriba**, líneas en blanco entre bloques, **la función que llama antes** que la llamada.
3. **Variables cerca de su primer uso**; líneas de ≈40 caracteres (máx. 80–120).
4. **Sangría consistente** que refleje la jerarquía archivo → clase → método → bloque.
5. **Consistencia de equipo**: un único estilo, idealmente impuesto por una **herramienta automática**.

> [!question] Pregunta típica
> *"¿Por qué es importante el formato del código y qué reglas básicas seguirías?"*
> **Respuesta:** porque el código se lee muchas más veces de las que se escribe, y un formato consistente reduce errores y facilita el mantenimiento y la colaboración. Reglas: atributos al inicio y separados por líneas en blanco, proximidad de funciones que se llaman, variables declaradas cerca de su uso, líneas cortas, espacios que reflejen la precedencia y sangría consistente que muestre la jerarquía.
