# 4. Descomposición funcional

> [!info] Antipatrón · Desarrollo
> **Sinónimos:** *Functional Decomposition* — Antipatrón de Desarrollo (William H. Brown et al.).
> **Síntomas:** clases con nombres de función, clases con un solo método, ausencia de herencia y polimorfismo.
> Relacionado con [[1. GRASP|GRASP]], [[8. Principio KISS|KISS]] y [[5. Anti patron Codigo Muerto|Código muerto]].

---

## 📖 ¿Qué es la descomposición funcional?

Es un **antipatrón de desarrollo** en el que el sistema se divide siguiendo el **flujo de acciones** (verbos) en lugar de modelar **objetos con estado y comportamiento** (sustantivos).

En otras palabras:

- Se piensa primero en **“qué hace”** el sistema y luego se crea **una clase por cada acción**.
- El resultado son clases que en realidad son **funciones disfrazadas**: tienen un solo método, no guardan estado propio y no colaboran entre sí.
- Es programación **estructurada / procedimental** escrita con la sintaxis de un lenguaje orientado a objetos.

> [!danger] El problema de fondo
> El código **“funciona”**, pero pierde todas las ventajas de la orientación a objetos: **encapsulación, reutilización, polimorfismo y facilidad de prueba**.

---

## ❓ Justificación: por qué es un problema

- Es **imposible de comprender** el software: no hay un modelo de objetos que explique el dominio.
- Es **imposible de reutilizar**: cada “acción” está atada a un caso concreto.
- Es **imposible de probar** de forma aislada: las acciones dependen unas de otras y comparten datos sueltos.
- Los datos **viajan sueltos** por todas las clases.
- Un cambio en los datos obliga a **cambiar la firma de todos los métodos**.
- Se produce **alto acoplamiento** y **baja cohesión**.

---

## 🧩 Síntomas típicos

| Síntoma | Ejemplo |
|---------|---------|
| **Clases con nombres de acciones** | `CalcularNomina`, `ValidarUsuario`, `GenerarReporte`, `ProcesarPago` |
| **Clases con un único método** | Una clase con solo `run()` o `main()` |
| **Uso excesivo de `static`** | Todo es estático: no hay objetos ni estado |
| **Ausencia de herencia, interfaces y polimorfismo** | El comportamiento se resuelve con `if/else` o `switch` |
| **Estructuras de datos compartidas** | Si cambia la estructura, hay que cambiar en todas partes |
| **Dependencias en cascada** | Una acción llama a otra y a otra, formando una cadena difícil de seguir |

> [!tip] Regla mnemotécnica
> Si el nombre de la clase es un **verbo** (`Validar`, `Guardar`, `Enviar`), sospecha. Las clases deben ser **sustantivos** del dominio (`Usuario`, `Factura`, `Pedido`).

---

## 🧩 Ejemplo en Java

### ❌ Mal (descomposición funcional)

```java
// Una clase por cada acción, todo estático y sin estado
public class ValidarUsuario {
    public static boolean validar(String nombre, String correo) {
        return nombre != null && correo.contains("@");
    }
}

public class GuardarUsuario {
    public static void guardar(String nombre, String correo) {
        System.out.println("Guardando " + nombre + " - " + correo);
    }
}

public class EnviarCorreoBienvenida {
    public static void enviar(String correo) {
        System.out.println("Correo enviado a " + correo);
    }
}

public class RegistrarUsuario {
    public static void registrar(String nombre, String correo) {
        if (ValidarUsuario.validar(nombre, correo)) {
            GuardarUsuario.guardar(nombre, correo);
            EnviarCorreoBienvenida.enviar(correo);
        }
    }
}
```

Problemas:

- Los datos (`nombre`, `correo`) **viajan sueltos** por todas las clases.
- Si mañana el usuario necesita más campos (teléfono, dirección), hay que **cambiar la firma de todos los métodos**.
- No se puede cambiar el envío del correo sin tocar `RegistrarUsuario`.
- Nada es **reutilizable** ni fácil de **probar de forma aislada**.
- No hay **estado**: el “usuario” no existe como objeto, solo como dos `String` que van de aquí para allá.

---

### ✅ Bien (orientado a objetos + GRASP)

```java
public class Usuario {
    private final String nombre;
    private final String correo;

    public Usuario(String nombre, String correo) {
        if (nombre == null || !correo.contains("@")) {
            throw new IllegalArgumentException("Datos inválidos");
        }
        this.nombre = nombre;
        this.correo = correo;
    }

    public String getNombre() { return nombre; }
    public String getCorreo() { return correo; }
}

public interface RepositorioUsuarios {
    void guardar(Usuario usuario);
}

public interface ServicioCorreo {
    void enviarBienvenida(Usuario usuario);
}

public class RegistroUsuarioService {
    private final RepositorioUsuarios repositorio;
    private final ServicioCorreo correo;

    public RegistroUsuarioService(RepositorioUsuarios repositorio,
                                  ServicioCorreo correo) {
        this.repositorio = repositorio;
        this.correo = correo;
    }

    public void registrar(Usuario usuario) {
        repositorio.guardar(usuario);
        correo.enviarBienvenida(usuario);
    }
}
```

Ahora:

- El **estado** (nombre, correo) vive en `Usuario` y viaja como **un solo objeto**.
- Las responsabilidades están bien asignadas ([[1. GRASP|GRASP]]): `Usuario` conoce sus datos, `RepositorioUsuarios` persiste, `ServicioCorreo` notifica.
- Se pueden intercambiar implementaciones (**polimorfismo**) sin tocar `RegistroUsuarioService`.
- Cada clase se puede **probar por separado** (con un repositorio y un correo falsos).

---

## 🔍 Cómo detectarlo

- Hay clases cuyo nombre es un **verbo** o una acción.
- Hay **muchas clases con un solo método** público.
- Abundan los métodos **`static`** y las clases de utilidades.
- No aparecen **interfaces** ni **jerarquías** de herencia.
- El comportamiento se decide con **`if/else` o `switch`** sobre un “tipo”.
- Los **datos del dominio** son parámetros sueltos que se repiten en muchas firmas.
- La clase `Main` o un `RegistrarX` **orquesta todo** y conoce a todas las demás.

---

## ✅ Cómo corregirlo

1. **Pensar en sustantivos, no en verbos.**
   → Identifica las entidades del dominio (`Usuario`, `Pedido`, `Factura`) **antes** que las acciones.

2. **Asignar responsabilidades con GRASP.**
   → Ver [[1. GRASP|GRASP]]: Experto en Información, Alta Cohesión, Bajo Acoplamiento, Creador, Controlador, etc.

3. **Eliminar el abuso de `static`.**
   → Si todo es estático no hay objetos, no hay estado y no hay polimorfismo.

4. **Agrupar datos y comportamiento.**
   → Una clase debe tener sus datos **y** las operaciones que los usan (**encapsulación**).

5. **Usar interfaces y polimorfismo** para variar comportamientos sin `if/else` gigantes.

6. **Aplicar refactorización**: *Move Method*, *Extract Class*, *Replace Conditional with Polymorphism*.

## 🎯 Resumen / Conclusión para examen

1. La **descomposición funcional** modela el software como una colección de **acciones**, no de **objetos**.
2. Sus señales: **clases con nombres de verbos**, **un solo método**, todo **`static`** y **sin herencia ni polimorfismo**.
3. Provoca **alto acoplamiento**, **baja cohesión** y un mantenimiento costoso: un cambio en los datos afecta a muchas clases.
4. La solución es **asignar responsabilidades con GRASP** y diseñar objetos con **estado, comportamiento y colaboración**.
5. Los datos del dominio deben **viajar juntos** dentro de un objeto, no como parámetros sueltos.

> [!question] Pregunta típica
> *"¿Qué es la descomposición funcional y cómo se corrige?"*
> **Respuesta:** es un antipatrón en el que se crea **una clase por cada acción** (validar, guardar, enviar…), con un solo método y frecuentemente `static`, de modo que el sistema es programación procedimental disfrazada de OO. Se detecta por clases con nombres de verbos, ausencia de estado, herencia y polimorfismo, y datos que viajan sueltos. Se corrige **modelando primero las entidades del dominio** (`Usuario`, `Pedido`), agrupando datos y comportamiento, y **asignando responsabilidades con GRASP**, usando interfaces y polimorfismo.
