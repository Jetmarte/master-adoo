# 6. Principio YAGNI (no lo vas a necesitar)

> [!info] Principio de diseño · Desarrollo ágil
> **YAGNI** = *You Aren’t Gonna Need It* (“No lo vas a necesitar”).
> **Violación relacionada:** *Generalidad Especulativa* (*Speculative Generality*, code smell — Refactoring).
> Relacionado con [[8. Principio KISS|KISS]], [[7. Principio No te repitas DRY|DRY]] y [[5. Anti patron Codigo Muerto|Código muerto]].

---

## 📖 ¿Qué significa YAGNI?

Es un **principio de desarrollo ágil** que dice:

> [!quote] Regla
> «No implementes funcionalidad hasta que **realmente sea necesaria**.»

Siempre se implementan las cosas **cuando se necesitan**, no cuando se **prevé** que se necesitarán. No se debe añadir funcionalidad hasta que se considere **estrictamente necesaria**.

> [!tip] Idea clave
> YAGNI está en **contraposición** a la “interfaz suficiente, completa y primitiva”: no diseñes una interfaz para todos los usos futuros imaginables. Diseña la que necesitas **hoy**.

---

## ❓ Por qué es importante (justificación)

Las características innecesarias son un inconveniente porque:

- **Tiempo perdido:** se gasta tiempo en añadir, probar y mejorar funcionalidad que nadie usa; y luego hay que **depurarla, documentarla y mantenerla**.
- **Hinchazón del código:** el software se hace **más grande y más complicado**.
- **Efecto bola de nieve:** añadir una característica sugiere otras, que a su vez sugieren más, y el alcance crece sin control.
- **Riesgo de errores:** código extra es código extra que puede fallar.

---

## ⚠️ Violaciones y sus consecuencias

- **Difícil de definir y probar:** hasta que la característica es realmente necesaria, es difícil definir **qué debe hacer** y probarla. Si no está bien definida, puede **no funcionar** incluso si algún día se necesita.
- **Nadie la conoce:** a menos que existan especificaciones y control de revisión, los programadores que **sí podrían usarla** no sabrán que existe.
- **Restringe el futuro:** toda característica nueva impone **restricciones** a lo que se puede hacer después; una característica innecesaria puede **estorbar** a las necesarias del futuro.
- **Requiere disciplina:** debe usarse junto con **refactorización continua**, **pruebas unitarias automatizadas** e **integración continua**.

> [!warning] El mito del “por si acaso”
> «Seguro lo piden después» es la frase que más deuda técnica genera. Si de verdad se pide después, **se añade después**, con un requisito real.

---

## 🧩 Ejemplo en Java

### ❌ Mal (violando YAGNI)

```java
public class Calculadora {
    public int sumar(int a, int b) {
        return a + b;
    }

    public int restar(int a, int b) {
        return a - b;
    }

    // "Por si acaso" algún día se necesita
    public int multiplicar(int a, int b) {
        return a * b;
    }

    public int dividir(int a, int b) {
        return a / b;
    }

    // "Por si acaso" algún día hay potencias
    public double potencia(double base, double exponente) {
        return Math.pow(base, exponente);
    }

    // "Por si acaso" algún día hay raíces
    public double raizCuadrada(double valor) {
        return Math.sqrt(valor);
    }
}
```

El cliente solo pidió **sumar y restar**, pero el programador añadió el resto “porque seguro lo van a usar después”. Ese código extra:

- Hay que **mantenerlo**.
- Puede tener **bugs innecesarios**.
- **Complica** sin aportar valor hoy.
- Obliga a **probarlo** y documentarlo.

---

### ✅ Bien (aplicando YAGNI)

```java
public class Calculadora {
    public int sumar(int a, int b) {
        return a + b;
    }

    public int restar(int a, int b) {
        return a - b;
    }
}
```

Solo lo que se necesita **ahora**. Si mañana el cliente pide multiplicar, se implementa **en ese momento**, con un requisito real y sus pruebas.

### 🧩 Ejemplo de generalidad especulativa

```java
// ❌ Interfaz y jerarquía "por si acaso" para algo que solo tiene un uso
public interface Operacion {
    int ejecutar(int a, int b);
}

public abstract class OperacionBinaria implements Operacion {
    protected abstract int operar(int a, int b);

    @Override
    public int ejecutar(int a, int b) {
        return operar(a, b);
    }
}

public class Suma extends OperacionBinaria {
    @Override
    protected int operar(int a, int b) {
        return a + b;
    }
}
```

```java
// ✅ Lo simple que se necesita hoy
public class Calculadora {
    public int sumar(int a, int b) {
        return a + b;
    }
}
```

> [!tip] Refactoriza cuando llegue el tercer caso
> La abstracción tiene sentido cuando hay **varios usos reales**. Si aparece el segundo o tercer caso, entonces se extrae la interfaz. Antes, es **generalidad especulativa**.

---

## 🔍 Cómo detectar una violación de YAGNI

- Métodos o clases **públicos que nadie llama**.
- **Parámetros “de configuración”** que siempre llevan el mismo valor.
- **Interfaces con una sola implementación** creadas “para el futuro”.
- **Flags y opciones** que nadie activa.
- Código **“preparado para cuando…”** con comentarios del tipo “en el futuro”.
- Jerarquías de herencia **profundas** para variaciones que no existen.
- Métodos **genéricos** que resuelven un caso concreto.

## ⚖️ YAGNI frente a otros principios

| Principio | Pregunta que responde | En una frase |
|-----------|----------------------|--------------|
| **YAGNI** | ¿Lo necesito **ahora**? | No implementes lo que no necesitas todavía |
| **KISS** | ¿Puede ser **más simple**? | La solución más simple que funcione es la mejor |
| **DRY** | ¿Estoy **repitiendo** conocimiento? | Cada pieza de conocimiento, una sola representación |
| **SRP** | ¿Tiene **una sola razón** de cambio? | Cada clase, una responsabilidad |

> [!note] Se complementan
> **YAGNI** evita construir de más; **KISS** evita complicar lo que ya hay; **DRY** evita duplicar; **SRP** reparte bien las responsabilidades. Juntos producen código **pequeño, simple, sin duplicación y bien organizado**.

## 🎯 Resumen / Conclusión para examen

1. **YAGNI** = «No lo vas a necesitar»: implementa **solo** lo que se necesita ahora.
2. Evita programar funcionalidades **no pedidas**; reduce complejidad, tiempo de desarrollo y coste de mantenimiento.
3. Características innecesarias: **hinchan** el código, generan **efecto bola de nieve**, son **difíciles de definir y probar** y **restringen** el futuro.
4. **Síntomas:** interfaces con una sola implementación, parámetros que siempre valen lo mismo, flags que nadie activa, métodos públicos sin uso.
5. Se combina con **refactorización continua**, **pruebas unitarias** e **integración continua**.
6. Muy relacionado con **KISS** (*Keep It Simple*) y **Lean Software Development**.

> [!question] Pregunta típica
> *"Explica el principio YAGNI con un ejemplo."*
> **Respuesta:** YAGNI (*You Aren’t Gonna Need It*) dice que no debe implementarse funcionalidad hasta que sea **estrictamente necesaria**. Ejemplo: si el cliente pide una calculadora que solo **sume y reste**, no se añaden multiplicar, dividir o potencias “por si acaso”; ese código habría que mantenerlo, probarlo y documentarlo sin aportar valor, y podría incluso estorbar a requisitos futuros. Cuando el requisito aparezca de verdad, se implementa con pruebas. Se apoya en refactorización continua y pruebas automatizadas, y se relaciona con **KISS** y con el antipatrón de **generalidad especulativa**.
