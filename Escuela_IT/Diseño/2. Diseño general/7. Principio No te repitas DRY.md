# 7. Principio DRY (no te repitas)

> [!info] Principio de diseño · Fuente única de la verdad
> **DRY** = *Don’t Repeat Yourself* (“No te repitas”). Definido por **Andrew Hunt y David Thomas** en *The Pragmatic Programmer*.
> **Sinónimo:** Fuente Única de la Verdad (*Single Source of Truth*).
> **Antónimos:** *Duplicate Code* (code smell — Refactoring, Martin Fowler), *Copy+Paste* (antipatrón — William H. Brown et al.), *Duplication* (code smell — Clean Code, Robert Martin), **WET** (*Write Everything Twice*).
> Relacionado con [[8. Principio KISS|KISS]], [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]] y [[10. Principio de unica responsabilidad|SRP]].

---

## 📖 ¿Qué significa DRY?

> [!quote] Definición
> «Cada pieza de **conocimiento** debe tener una única, inequívoca y autoritativa representación en un sistema.»

En la práctica:

- Evitar **duplicar lógica, reglas de negocio o estructuras de datos**.
- En lugar de repetir código, **encapsularlo en un solo lugar**.
- Si mañana cambia la lógica, se cambia en **un único sitio**, no en varios.

> [!tip] Idea clave
> DRY habla de **conocimiento**, no de texto. Dos bloques pueden parecerse y representar **reglas distintas**; entonces **no** son duplicación.

---

## ❓ Justificación

- Evita **re-analizar, re-diseñar y re-codificar** soluciones, lo que complica enormemente el mantenimiento **correctivo, perfectivo y adaptativo**.
- Un cambio en una regla duplicada obliga a recordar **todos** los sitios donde está repetida: tarde o temprano se olvida uno.
- La duplicación es una de las principales fuentes de **errores en producción**.
- Ejemplo histórico: el **efecto 2000** paralizó la producción de software; los gobiernos subvencionaron con dinero de los impuestos a empresas privadas para reaccionar al problema. Con una única fuente para el tratamiento de fechas, el impacto habría sido mucho menor.

---

## ✅ Solución

- Cada pieza de conocimiento debe tener una **única, inequívoca y autoritativa** representación en el sistema.
- El objetivo es **reducir la repetición de información** de todo tipo, lo que hace los sistemas **más fáciles de mantener**.
- Consecuencia: una modificación de un elemento **no requiere cambiar** otros elementos lógicamente no relacionados (similar a la **1ª Forma Normal** en bases de datos).
- Es aplicable a:
  - **programación** (lógica, constantes, validaciones),
  - **esquemas de bases de datos**,
  - **planes de prueba**,
  - **sistema de construcción**,
  - incluso la **documentación**.

## 🧩 Ejemplo en Java

### ❌ Mal (violando DRY)

```java
public class FacturaService {

    public double calcularImpuestoProducto(double precio) {
        return precio * 0.19; // IVA 19%
    }

    public double calcularImpuestoServicio(double precio) {
        return precio * 0.19; // ❌ Lógica duplicada
    }
}
```

La lógica del impuesto está **repetida**. Si el IVA cambia de 19 % a 21 %, hay que modificarlo en **varios lugares** (y seguro se olvidará alguno).

---

### ✅ Bien (aplicando DRY)

```java
public class FacturaService {
    private static final double IVA = 0.19;

    private double calcularImpuesto(double precio) {
        return precio * IVA;
    }

    public double calcularImpuestoProducto(double precio) {
        return calcularImpuesto(precio);
    }

    public double calcularImpuestoServicio(double precio) {
        return calcularImpuesto(precio);
    }
}
```

La lógica del impuesto vive en **un único lugar** (`calcularImpuesto`). Si cambia el IVA → solo se actualiza la constante.

### 🧩 Ejemplo 2: validación duplicada

```java
// ❌ La misma regla en dos sitios: si cambia, hay que tocar ambos
public void registrarUsuario(Usuario u) {
    if (u.getCorreo() == null || !u.getCorreo().contains("@")) {
        throw new IllegalArgumentException("Correo inválido");
    }
    // …
}

public void actualizarUsuario(Usuario u) {
    if (u.getCorreo() == null || !u.getCorreo().contains("@")) {
        throw new IllegalArgumentException("Correo inválido");
    }
    // …
}
```

```java
// ✅ Una única fuente para la regla
public final class ValidadorCorreo {
    private ValidadorCorreo() { }

    public static void validar(String correo) {
        if (correo == null || !correo.contains("@")) {
            throw new IllegalArgumentException("Correo inválido");
        }
    }
}

public void registrarUsuario(Usuario u) {
    ValidadorCorreo.validar(u.getCorreo());
    // …
}

public void actualizarUsuario(Usuario u) {
    ValidadorCorreo.validar(u.getCorreo());
    // …
}
```

### 🧩 Ejemplo 3: duplicación de datos (no solo de código)

```java
// ❌ El total se guarda y además se puede recalcular: dos fuentes de verdad
public class Pedido {
    private List<Producto> productos;
    private double total; // ¿y si un producto cambia de precio?

    public double getTotal() {
        return total;
    }
}
```

```java
// ✅ Una única fuente: el total se deriva de los productos
public class Pedido {
    private final List<Producto> productos = new ArrayList<>();

    public double getTotal() {
        return productos.stream()
                .mapToDouble(Producto::getPrecio)
                .sum();
    }
}
```

> [!note] DRY también aplica a datos
> Guardar un valor **derivable** crea dos fuentes de verdad que pueden **desincronizarse**. Es la misma idea que la **normalización** en bases de datos.

## ⚠️ Violaciones típicas

| Violación | Ejemplo |
|-----------|---------|
| **Código repetido carácter por carácter** | La misma línea copiada en dos clases |
| **Código semánticamente repetido** | Nombres de variables cambiados, distinto orden de sentencias |
| **Bloques que deberían ser métodos** | Un bloque que ya existe como método en otro sitio |
| **Constantes mágicas repetidas** | `precio * 0.19` en diez lugares |
| **Reglas de negocio duplicadas** | Validaciones, cálculos, formatos |
| **Duplicación en pruebas** | El mismo *setup* copiado en cada test |
| **Duplicación en configuración** | La misma URL o puerto en varios ficheros |
| **Duplicación en documentación** | El mismo dato explicado en varios documentos |

> [!warning] Cuidado con la misma línea en ámbitos distintos
> `this.add(element);` puede ser **completamente diferente** en dos clases, porque depende de las declaraciones en las que se apoya. La duplicación es de **conocimiento**, no de **texto**.

---

## ⚖️ DRY ≠ “todo el código parecido se unifica”

- **DRY no significa que nunca pueda haber código parecido.**
- Si la duplicación responde a **cosas diferentes** (por ejemplo, dos validaciones con **reglas distintas** que hoy coinciden), **está bien** que no se fuercen a unificar.
- Unificar dos cosas que **solo se parecen hoy** crea un **acoplamiento artificial**: el día que una cambie, la abstracción se rompe.

> [!tip] Regla de tres
> La primera vez, escribe el código. La segunda, **duplícalo** si hace falta. A la **tercera**, refactoriza y extrae la abstracción. Abstraer a la primera suele ser **premature abstraction** (una violación de [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]]).

### 🧩 Ejemplo: parecido que NO es duplicación

```java
// ❌ Unificar por parecido aparente
public double calcularDescuentoCliente(double total) {
    return total * 0.10;
}

public double calcularDescuentoEmpleado(double total) {
    return total * 0.10;
}

// ⚠️ Hoy coinciden, pero son reglas de negocio distintas:
// mañana el empleado puede tener un 20 % y el cliente un 5 %.
// Unificarlas crearía un acoplamiento falso.
```

| | **Duplicación real** | **Parecido casual** |
|---|---|---|
| **Representa** | El mismo conocimiento | Conocimientos distintos |
| **Si cambia uno…** | Debe cambiar el otro | El otro **no** debe cambiar |
| **Acción** | **Unificar** | **Dejar separado** |

---

## 🚫 WET: el antónimo

**WET** = *Write Everything Twice* (“escribe todo dos veces”, o *We Enjoy Typing*).

- Es la **violación consciente o inconsciente** de DRY.
- Copiar y pegar es su forma más común.
- Consecuencia: **mantenimiento duplicado**, errores por olvido y código que evoluciona de forma desigual.

## 🎯 Resumen / Conclusión para examen

1. **DRY** = cada pieza de **conocimiento** debe tener **una única representación** autoritativa en el sistema.
2. Evita **re-analizar, re-diseñar y re-codificar**; reduce el mantenimiento correctivo, perfectivo y adaptativo.
3. Se aplica a **código, datos, pruebas, configuración, sistema de construcción y documentación**.
4. **Violaciones típicas:** código copiado, constantes mágicas repetidas, reglas de negocio y validaciones duplicadas.
5. **DRY ≠ unificar todo lo parecido:** si son **reglas distintas**, deben permanecer separadas (**parecido casual**).
6. **Regla de tres:** a la tercera repetición, refactoriza. Abstraer antes es **premature abstraction**, contraria a **YAGNI**.
7. Su antónimo es **WET** (*Write Everything Twice*); su pariente en BBDD es la **normalización**.

> [!question] Pregunta típica
> *"¿Qué es DRY y cómo se aplica? Pon un ejemplo."*
> **Respuesta:** DRY (*Don’t Repeat Yourself*) establece que cada pieza de conocimiento debe tener **una única representación** inequívoca y autoritativa. Ejemplo: si dos métodos de facturación calculan el IVA con `precio * 0.19`, la lógica está duplicada; si el IVA cambia, hay que modificarlo en varios sitios y es fácil olvidar uno. La solución es extraer `calcularImpuesto` y una constante `IVA`, de modo que el cambio se haga en **un solo lugar**. Se aplica también a datos (no guardar valores derivables), pruebas, configuración y documentación. Eso sí: DRY **no** obliga a unificar código que solo se parece, porque representaría reglas distintas; la **regla de tres** y **YAGNI** evitan la abstracción prematura.
