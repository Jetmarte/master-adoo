# 8. Principio KISS (mantenlo simple)

> [!info] Principio de diseño
> **KISS** = *Keep It Simple, Stupid* / *Keep It Short and Simple* / *Keep It Small and Simple* (Kelly Johnson).
> **Sinónimo:** *Understand the Algorithm* (code smell — Clean Code, Robert Martin).
> **Antónimos:** *Spaghetti Code* (antipatrón — William H. Brown et al.), *Speculative Generality* (code smell — Refactoring, Martin Fowler), *Obscured Intent* (code smell — Clean Code, Robert Martin).
> Relacionado con [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]], [[7. Principio No te repitas DRY|DRY]] y [[1. Formato de codigo limpio|Formato]].

---

## 📖 ¿Qué significa KISS?

> [!quote] Regla
> «La solución **más simple que funcione** suele ser la mejor.»

Es un principio de diseño de software (y de ingeniería en general):

- Evitar soluciones demasiado **complejas** o **sofisticadas** cuando una más simple es suficiente.
- No añadir **capas, patrones o abstracciones innecesarias**.
- Facilitar que el código sea **legible, entendible y mantenible**.

> [!tip] Idea clave
> La simplicidad debe ser un **objetivo clave del diseño**; cualquier complejidad **innecesaria** debe evitarse.

---

## ❓ Justificación

- La mayoría de sistemas funcionan mejor si se mantienen **simples** que si se hacen complejos.
- En igualdad de condiciones, la explicación más sencilla suele ser la correcta (**Navaja de Occam**).
- «Cualquier tonto inteligente puede hacer cosas más grandes y más complejas… se necesita un toque de genialidad y mucho coraje para moverse en la dirección opuesta.» — Einstein
- «No es suficiente dejar las comillas alrededor de la palabra “funciona”. Debes saber que la solución es **correcta**. A menudo, la mejor manera de obtener ese conocimiento es **refactorizar** la función en algo tan limpio y expresivo que sea **obvio** cómo funciona.» — Martin
- «La diferencia entre un programador inteligente y un programador profesional es que el profesional entiende que **la claridad es el rey**. Los profesionales usan su potencia para escribir código que **otros puedan entender**.» — Martin

## 🧩 Ejemplo en Java

### ❌ Mal (violando KISS: demasiado complejo)

Un programador implementa la suma de dos números con un patrón innecesario:

```java
public interface Operacion {
    int ejecutar(int a, int b);
}

public class Suma implements Operacion {
    @Override
    public int ejecutar(int a, int b) {
        return a + b;
    }
}

public class Calculadora {
    public int calcular(Operacion op, int a, int b) {
        return op.ejecutar(a, b);
    }
}

public class Main {
    public static void main(String[] args) {
        Calculadora calc = new Calculadora();
        System.out.println(calc.calcular(new Suma(), 3, 5));
    }
}
```

Aquí se usó una **interfaz**, una **clase extra** y una **calculadora**… solo para sumar dos números. Eso es **overengineering** (sobreingeniería).

---

### ✅ Bien (aplicando KISS: simple y claro)

```java
public class Calculadora {
    public int sumar(int a, int b) {
        return a + b;
    }
}

public class Main {
    public static void main(String[] args) {
        Calculadora calc = new Calculadora();
        System.out.println(calc.sumar(3, 5));
    }
}
```

Mucho más **simple, claro y suficiente**. Si mañana el cliente pide operaciones complejas, se refactoriza en ese momento (**YAGNI**).

### 🧩 Ejemplo 2: algoritmo generalista para un caso concreto

```java
// ❌ Resolver una ecuación genérica de segundo grado para un caso fijo
public double calcularDistancia(double x1, double y1, double x2, double y2) {
    double dx = x2 - x1;
    double dy = y2 - y1;
    // … 40 líneas de álgebra general, validaciones y casos especiales
    return Math.sqrt(dx * dx + dy * dy);
}

// ✅ La solución directa y comprensible
public double calcularDistancia(double x1, double y1, double x2, double y2) {
    double dx = x2 - x1;
    double dy = y2 - y1;
    return Math.sqrt(dx * dx + dy * dy);
}
```

Un algoritmo **complejo y general** para una situación **muy concreta** es una violación de KISS.

### 🧩 Ejemplo 3: eficiencia innecesaria

```java
// ❌ Complejo y "muy eficiente" cuando el rendimiento no es un problema
public int sumarLista(List<Integer> numeros) {
    return numeros.parallelStream()
            .mapToInt(Integer::intValue)
            .reduce(0, Integer::sum);
}

// ✅ Simple y suficientemente rápido para listas normales
public int sumarLista(List<Integer> numeros) {
    int suma = 0;
    for (int numero : numeros) {
        suma += numero;
    }
    return suma;
}
```

> [!warning] Optimización prematura
> «La optimización prematura es la raíz de todos los males.» Si no hay un problema de rendimiento **medido**, la solución simple es la correcta. Optimiza cuando tengas **datos** que lo justifiquen.

## ⚠️ Violaciones típicas

| Violación | Qué hacer |
|-----------|-----------|
| **Clases abstractas que no aportan** | Si no hacen mucho, **colapsa la jerarquía** |
| **Delegación innecesaria** | Eliminar la clase intermedia y usar la clase “en línea” |
| **Métodos que no usan sus parámetros** | **Eliminar el parámetro** (o el método) |
| **Nombres abstractos y extraños** | Renombrarlos para “traerlos a la tierra” |
| **Algoritmos generalistas para casos concretos** | Resolver el caso concreto de forma directa |
| **Algoritmos muy eficientes sin necesidad** | Usar la versión simple y legible |
| **Patrones de diseño sin motivo** | Aplicar un patrón solo cuando el problema lo pida |
| **Capas y capas de indirección** | Reducir hasta que el flujo sea evidente |

---

## ✅ Cómo aplicar KISS

1. **Pregúntate:** «¿Cuál es la forma más simple que cumple el requisito **hoy**?».
2. **Evita abstracciones prematuras:** la interfaz o el patrón se añaden cuando aparecen **varios usos reales** (véase [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]]).
3. **Escribe código que se lea como prosa:** nombres claros, métodos cortos, flujo evidente.
4. **Refactoriza para aclarar**, no para impresionar.
5. **Mide antes de optimizar:** sin datos de rendimiento, prioriza la claridad.
6. **Desconfía de la complejidad accidental:** herencia profunda, genéricos innecesarios, configuración para todo.

> [!tip] Prueba de simplicidad
> Si un compañero nuevo no entiende el código en **cinco minutos**, probablemente no es KISS. La complejidad debe estar en el **problema**, no en la **solución**.

---

## ⚖️ KISS frente a otros principios

| Principio | Pregunta | Se viola cuando… |
|-----------|----------|------------------|
| **KISS** | ¿Puede ser más simple? | Añades patrones, capas o algoritmos innecesarios |
| **YAGNI** | ¿Lo necesito ahora? | Implementas para un futuro imaginado |
| **DRY** | ¿Estoy repitiendo conocimiento? | Copias y pegas lógica |
| **SRP** | ¿Tiene una sola razón de cambio? | Una clase mezcla responsabilidades |

> [!note] Cuidado con los extremos
> KISS **no** significa escribir código pobre o no pensar en el diseño. Significa que la solución debe ser **tan simple como sea posible, pero no más**. Una abstracción **necesaria** no viola KISS; una abstracción **decorativa**, sí.

## 🎯 Resumen / Conclusión para examen

1. **KISS** = «Mantenlo simple»: la solución **más simple que funcione** suele ser la mejor.
2. Evita **sobreingeniería**: patrones, capas, interfaces y algoritmos que no aportan valor.
3. **Justificación:** los sistemas simples funcionan mejor; la claridad es lo que distingue al profesional.
4. **Violaciones típicas:** clases abstractas vacías, delegación innecesaria, parámetros sin usar, nombres extraños, algoritmos generalistas o ultraeficientes sin necesidad.
5. **Optimiza solo con datos:** la optimización prematura añade complejidad sin garantía de mejora.
6. Se relaciona con **YAGNI** (no añadas lo que no necesitas) y **DRY** (no repitas lógica).
7. KISS **no** es escribir código pobre: es evitar la **complejidad accidental**, manteniendo la **necesaria**.

> [!question] Pregunta típica
> *"¿Qué es el principio KISS y cómo se detecta su violación?"*
> **Respuesta:** KISS (*Keep It Simple, Stupid*) establece que la solución **más simple que cumpla el requisito** es preferible a una más compleja. Se viola cuando se añaden **patrones, interfaces, capas o algoritmos innecesarios** para un problema sencillo (por ejemplo, una interfaz, una clase `Suma` y una calculadora solo para sumar dos números), cuando se usan **clases abstractas que no aportan**, **delegaciones innecesarias**, **parámetros sin usar** o **algoritmos generalistas/ultraeficientes** sin necesidad. Se corrige eliminando lo superfluo, usando la solución directa y **refactorizando** para que el código sea obvio; la optimización se hace solo cuando hay **datos** que la justifican. Se complementa con **YAGNI** y **DRY**.
