# Comentarios de código limpio

## Propósito

Un comentario bien colocado puede ser muy útil. Sin embargo, el código claro y expresivo, acompañado de pocos comentarios, es preferible al código confuso que depende de muchos de ellos.

Antes de añadir un comentario, conviene preguntarse si se puede expresar la misma idea mejorando el código, por ejemplo, mediante una función con un nombre descriptivo.

## Cuándo comentar

- **Requisitos legales:** avisos de copyright, licencias y otras obligaciones.
- **Aclaraciones necesarias:** explican información que no resulta evidente al leer el código, como el formato que debe reconocer una expresión regular:

  ```java
  // Formato: hh:mm:ss EEE, MMM dd, yyyy
  String format = "\\d*:\\d*:\\d* \\w*, \\w* \\d*, \\d*";
  ```

## Comentarios que conviene evitar

- **Redundantes:** repiten lo que ya expresa el código.

  ```java
  int dayOfMonth; // El día del mes
  ```

- **De atribución:** indican quién añadió una línea. Para eso está el control de versiones.
- **Confusos o inexactos:** no explican con claridad lo que ocurre o describen el código de forma imprecisa.
- **De sección:** separadores decorativos que añaden ruido, por ejemplo `// Acciones //////////////////`.
- **Código comentado:** el control de versiones permite recuperar código eliminado; mantenerlo comentado dificulta la lectura.
- **Desactualizados:** contienen datos que ya no son ciertos, como `// El puerto es 7077` después de cambiar la configuración.
- **Excesivos:** incluyen largas discusiones o detalles que no ayudan a entender el código.
- **Dogmáticos:** imponen comentarios para cada variable o función sin considerar si realmente aportan información.

Un comentario desactualizado puede ser especialmente perjudicial: propaga información falsa y hace que el código resulte más difícil de entender.

## Máxima

> «No comentes código malo; reescríbelo». — Kernighan y Plauger
