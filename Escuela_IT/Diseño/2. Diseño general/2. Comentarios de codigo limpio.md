# 2. Comentarios de código limpio

> [!info] Comentarios: lo mínimo imprescindible
> Un comentario bien colocado puede ser muy útil, pero **el código claro y expresivo, con pocos comentarios, es mejor que el código confuso que depende de muchos**.
> Relacionado con [[3. Nombrado del codigo limpio|Nombrado]] y [[8. Principio KISS|KISS]].

---

## 📖 ¿Qué es un buen comentario?

Un comentario es una **explicación escrita por un humano** que el compilador ignora. Su valor depende de que aporte información que **el código por sí solo no puede expresar**.

> [!tip] Idea clave
> Antes de escribir un comentario, pregúntate: **¿puedo expresar esta misma idea mejorando el código?** Muchas veces la respuesta es un **nombre más descriptivo** o una **función extraída**.

```java
// ❌ Comentario que compensa un mal nombre
int d; // días transcurridos desde la modificación

// ✅ El nombre ya lo dice todo: el comentario sobra
int daysSinceModification;
```

---

## ❓ Por qué importa (justificación)

- El código se **escribe una vez y se lee cientos de veces**.
- Un comentario **obsoleto propaga información falsa** y hace el código más difícil de entender que si no existiera.
- Los comentarios **se desactualizan**: si cambias el código y no el comentario, este miente.
- Un exceso de comentarios **distrae** de la lógica y suele indicar que el código no es autoexplicativo.

> [!quote] Kernighan y Plauger
> «No comentes código malo; reescríbelo.»

---

## ✅ Cuándo sí comentar

| Tipo | Para qué sirve | Ejemplo |
|------|----------------|---------|
| **Requisitos legales** | Copyright, licencias, obligaciones | Cabecera de licencia |
| **Aclaraciones necesarias** | Explican información no evidente en el código | El formato que reconoce una regex |
| **Advertencias de consecuencias** | Evitan que alguien “mejore” algo peligroso | `// No usar en producción: borra la BD` |
| **Intención / el porqué** | Explica una decisión de diseño no obvia | `// O(n²) aceptable: la lista siempre es pequeña` |
| **Amplificación** | Resalta algo que puede pasar desapercibido | `// Este método es thread-safe` |
| **Documentación pública** | Javadoc de una API para sus clientes | `@param`, `@return`, `@throws` |

### 🧩 Ejemplo de aclaración necesaria

```java
// Formato esperado: hh:mm:ss EEE, MMM dd, yyyy
String format = "\\d*:\\d*:\\d* \\w*, \\w* \\d*, \\d*";
```

Sin el comentario sería imposible saber **qué** debe reconocer esa expresión regular.

### 🧩 Ejemplo de intención (el porqué)

```java
// Se usa una lista en vez de un Set porque el orden de llegada importa
private final List<Evento> eventos = new ArrayList<>();
```

El código dice **qué** hace; el comentario aclara **por qué** se eligió así.

---

## ❌ Comentarios que conviene evitar

### 1. Redundantes

Repiten lo que el código ya expresa.

```java
// ❌ Ruido: no aporta nada
int dayOfMonth; // El día del mes
i++;            // Incrementa i

// ✅ Sin comentario: el código es evidente
int dayOfMonth;
i++;
```

---

### 2. De atribución

Indican **quién** añadió una línea. Para eso está el control de versiones.

```java
// ❌ "Añadido por Ana el 12/03"
public void pagar() { /* … */ }

// ✅ El historial de Git ya lo registra
public void pagar() { /* … */ }
```

---

### 3. Confusos o inexactos

No explican con claridad lo que ocurre o describen el código de forma imprecisa.

```java
// ❌ ¿Qué significa "lo de siempre"?
// Hace lo de siempre con el pedido
procesar(pedido);
```

---

### 4. De sección (decorativos)

Separadores que solo añaden ruido visual.

```java
// ❌ Ruido decorativo
// ===== ACCIONES =====================
// ***********************************
private void ejecutar() { /* … */ }
```

Si necesitas separadores tan llamativos, probablemente la **clase es demasiado grande**.

---

### 5. Código comentado

El control de versiones permite recuperar código eliminado; mantenerlo comentado **dificulta la lectura**.

```java
// ❌ Código muerto comentado
// public void calcularTotal() {
//     total = precio * cantidad;
// }
public void calcularTotal() {
    total = precio * cantidad * (1 - descuento);
}
```

> [!warning] Regla
> Si no se usa, **bórralo**. Git guarda el historial: no necesitas conservarlo “por si acaso”.

---

### 6. Desactualizados

Contienen datos que **ya no son ciertos**.

```java
// ❌ El puerto cambió hace meses
// El puerto es 7077
config.setPort(8080);
```

> [!danger] El peor comentario
> Un comentario desactualizado es **peor que ninguno**: propaga información falsa y hace que el código resulte más difícil de entender. Si el comentario y el código se contradicen, ¿a quién crees?

---

### 7. Excesivos

Largas discusiones o detalles que no ayudan a entender el código.

```java
// ❌ Novela en lugar de comentario
// Primero pensé en usar un Map, luego probé con una lista,
// después consulté con el equipo y decidimos que…
```

Si la explicación es tan larga, va en la **documentación del proyecto**, no en el código.

---

### 8. Dogmáticos

Imponen un comentario para **cada** variable o función sin valorar si aporta información.

```java
/**
 * Clase Usuario.
 * Tiene un nombre.
 * Tiene un correo.
 */
public class Usuario {
    /** El nombre. */
    private String nombre;
    /** El correo. */
    private String correo;
}
```

Añadir Javadoc a todo por obligación genera **ruido** sin valor.

---

## ⚖️ Decisión rápida

| Situación | ¿Comentar? | Mejor alternativa |
|-----------|-----------|-------------------|
| Puedo renombrar para que se entienda | ❌ No | Mejor nombre |
| El bloque hace varias cosas | ❌ No | Extraer un método con nombre |
| Explico una decisión no obvia | ✅ Sí | Comentario de **por qué** |
| Formato de una regex o protocolo | ✅ Sí | Comentario de **aclaración** |
| Licencia o copyright | ✅ Sí | Cabecera legal |
| Quiero guardar una versión anterior | ❌ No | Git |
| El comentario ya no es cierto | ❌ No | **Borrarlo o corregirlo** |

## 🎯 Conclusión para examen

1. **El código expresivo y con pocos comentarios es preferible** al código confuso lleno de ellos.
2. **Comenta el porqué**, no el qué: el código ya dice qué hace.
3. **Comentarios útiles:** legales, aclaraciones necesarias, advertencias, intención y documentación pública.
4. **Comentarios a evitar:** redundantes, de atribución, confusos, de sección, código comentado, desactualizados, excesivos y dogmáticos.
5. **El comentario desactualizado es el más peligroso**: propaga información falsa.
6. Antes de comentar, intenta **renombrar** o **extraer un método**.

> [!question] Pregunta típica
> *"¿Cuándo es útil un comentario y cuándo perjudica?"*
> **Respuesta:** es útil cuando aporta información que el código no puede expresar: requisitos legales, aclaraciones necesarias (el formato de una regex), advertencias de consecuencias, la **intención** de una decisión o la documentación de una API pública. Perjudica cuando es redundante, explica lo obvio, indica autoría, decora secciones, conserva código comentado, está desactualizado o impone un comentario a cada línea. La regla es: **si el código puede expresarlo, mejora el código en lugar de comentarlo**.
