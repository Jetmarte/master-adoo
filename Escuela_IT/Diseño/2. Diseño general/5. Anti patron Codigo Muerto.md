# 5. Antipatrón código muerto

> [!info] Antipatrón · Desarrollo
> **Sinónimos:** *Dead Code*, *Lava Flow* (flujo de lava).
> **Síntomas:** fragmentos injustificables, bloques de código comentado, interfaces sin usar y comentarios del tipo “para ser reemplazado”.
> Relacionado con [[2. Comentarios de codigo limpio|Comentarios]], [[6. Principio no vas ha necesitarlo YAGNI|YAGNI]] y [[8. Principio KISS|KISS]].

---

## 📖 ¿Qué es el código muerto?

Se llama **código muerto** a cualquier fragmento de programa que:

- **Nunca se ejecuta**, porque no hay forma de alcanzarlo.
- **Ya no se usa**, porque nadie lo llama.
- **Sobró de una versión anterior**, pero quedó olvidado en el código.

> [!danger] Por qué es peligroso
> Aunque no afecte directamente a la ejecución, **aumenta la complejidad innecesaria** y confunde a otros desarrolladores. Parece importante, pero no participa en el sistema: es una **trampa de lectura**.

---

## ❓ Justificación: el efecto “lava”

- El código muerto se **anquilosa y se endurece**: rápidamente se hace imposible documentar el código o entender su arquitectura para hacer mejoras.
- Si no se elimina, puede **seguir proliferando**: los desarrolladores lo **reutilizan** en otras áreas sin saber que ya no sirve.
- Puede haber **crecimiento exponencial**: los sucesivos desarrolladores, apremiados o intimidados por analizar el código original, producen **nuevos flujos secundarios** para evitar los originales.
- Al final, el sistema queda cubierto de **“lava”** solidificada (código viejo) sobre la que se construye código nuevo, cada vez más difícil de entender.

> [!example] La metáfora del flujo de lava
> Imagina código antiguo que se enfría y se convierte en roca. El siguiente desarrollador no se atreve a tocarlo y construye **alrededor**. Diez versiones después, nadie sabe qué es roca y qué es código vivo.

---

## 🧩 Síntomas típicos

| Síntoma | Descripción |
|---------|-------------|
| **Fragmentos injustificables** | Clases, funciones o segmentos complejos, no documentados, con aspecto importante pero **sin relación con el sistema** |
| **Bloques comentados** | Enteros de código comentado **sin explicación ni documentación** |
| **Interfaces no usadas** | Interfaces inexplicables u **obsoletas** |
| **Comentarios de transición** | Zonas con “proceso de cambio”, “para ser reemplazado”, “TODO antiguo” |
| **Métodos sin llamadas** | Métodos que ninguna otra parte del sistema invoca |
| **Ramas inalcanzables** | Código después de un `return`, un `throw` o un `break` |
| **Parámetros muertos** | Parámetros que nunca se usan en el cuerpo |
| **Variables muertas** | Variables declaradas que nunca se leen |

---

## 🧩 Ejemplos en Java

### Ejemplo 1: método nunca usado

```java
public class Cliente {
    private String nombre;

    public Cliente(String nombre) {
        this.nombre = nombre;
    }

    public String getNombre() {
        return nombre;
    }

    // ❌ Método muerto: nadie lo llama en el sistema
    public String getNombreEnMayusculas() {
        return nombre.toUpperCase();
    }
}
```

`getNombreEnMayusculas()` nunca es invocado → **código muerto**.

---

### Ejemplo 2: bloque inalcanzable

```java
public int dividir(int a, int b) {
    if (b == 0) {
        return 0;
    } else {
        return a / b;
    }
    // ❌ Código muerto: nunca se ejecutará
    System.out.println("Esta línea es inalcanzable");
}
```

La última línea después del `return` es **código muerto**, jamás se ejecuta.

---

### Ejemplo 3: variable sin uso

```java
public void procesar() {
    int x = 10; // ❌ Variable muerta: nunca se usa
    System.out.println("Procesando...");
}
```

---

### Ejemplo 4: parámetro muerto

```java
// ❌ 'descuento' nunca se usa dentro del método
public double calcularTotal(double precio, double descuento) {
    return precio * 1.19;
}

// ✅ Se elimina el parámetro o se usa de verdad
public double calcularTotal(double precio) {
    return precio * 1.19;
}
```

> [!warning] Cuidado con las interfaces
> Un parámetro puede parecer muerto en una implementación pero ser necesario por el **contrato** de la interfaz. Antes de borrarlo, revisa si la firma la impone un `interface` o una clase base.

---

### Ejemplo 5: código comentado

```java
// ❌ Código muerto comentado, sin explicación
// public double calcularDescuento(double total) {
//     return total * 0.10;
// }

public double calcularTotal(double total) {
    return total * 1.19;
}
```

El control de versiones (Git) ya guarda el historial: **no necesitas conservarlo “por si acaso”**.

---

### Ejemplo 6: funcionalidad tras un flag que ya no se usa

```java
// ❌ Rama muerta: la versión antigua ya no existe
if (usarNuevaFacturacion) {
    facturarV2(pedido);
} else {
    facturarV1(pedido); // nadie activa esta rama desde 2021
}
```

Si el flag siempre es `true`, la rama `else` es **código muerto**.

## 🔍 Cómo detectarlo

| Técnica | Qué encuentra |
|---------|---------------|
| **Avisos del IDE / compilador** | Variables y parámetros sin usar, código inalcanzable |
| **Búsqueda de referencias** | Métodos, clases y campos que nadie llama |
| **Cobertura de pruebas** | Zonas del código que ninguna prueba ejecuta (ojo: no todo lo no cubierto es muerto) |
| **Análisis estático** | Herramientas como SonarQube, PMD, SpotBugs, ESLint |
| **Revisión de `git blame`** | Código que lleva años sin tocarse y sin uso |
| **Búsqueda de `//` y `/*`** | Bloques de código comentado |

> [!tip] Cuidado con los falsos positivos
> El código invocado por **reflexión**, **frameworks**, **serialización** o **pruebas** puede parecer muerto. Verifica antes de eliminarlo.

---

## ✅ Cómo eliminar el código muerto

1. **Borrar métodos, clases y variables no usadas.**
   → El compilador moderno (Java, C#…) avisa de muchos casos.

2. **Refactorizar condiciones.**
   → Si un `if` siempre es verdadero o falso, elimina la **rama muerta**.

3. **Eliminar código comentado.**
   → Git ya guarda el historial; no lo mantengas en comentarios.

4. **Eliminar flags de funcionalidad ya consolidados.**
   → Si una rama lleva tiempo sin usarse, bórrala y quédate con la viva.

5. **Hacerlo de forma segura.**
   → Apóyate en **pruebas automatizadas** y en el control de versiones: si algo se rompe, se recupera.

---

## 📋 Código muerto vs. código malo

| | **Código muerto** | **Código malo (pero vivo)** |
|---|---|---|
| **Se ejecuta** | ❌ No | ✅ Sí |
| **Aporta valor** | ❌ No | ✅ (aunque mal) |
| **Solución** | **Eliminarlo** | **Refactorizarlo** |
| **Riesgo de mantenerlo** | Confusión, complejidad | Errores, deuda técnica |

## 🎯 Resumen / Conclusión para examen

1. El **código muerto** no se ejecuta, no se usa o sobró de una versión anterior: **no aporta valor**.
2. Aumenta la **complejidad**, confunde y hace más difícil mantener el sistema.
3. El **flujo de lava** describe cómo el código viejo se solidifica y el nuevo se construye alrededor, generando capas imposibles de entender.
4. **Síntomas:** código comentado, métodos sin llamadas, código inalcanzable, variables/parámetros sin usar, interfaces obsoletas.
5. La mejor práctica es **eliminarlo sin miedo**: el **control de versiones** conserva el historial y las pruebas automatizadas dan seguridad.
6. **YAGNI** es su principal prevención: si no lo necesitas hoy, no lo escribas.

> [!question] Pregunta típica
> *"¿Qué es el código muerto y por qué debe eliminarse?"*
> **Respuesta:** es cualquier fragmento que nunca se ejecuta o ya no se usa (métodos sin llamadas, ramas inalcanzables, variables o parámetros sin uso, código comentado). Debe eliminarse porque aumenta la complejidad y el tiempo de lectura, propaga confusión y puede “contagiar” a nuevo código (efecto **lava flow**). Se elimina borrándolo, apoyándose en el IDE, las pruebas automatizadas y el control de versiones, que permite recuperarlo si fuera necesario.
