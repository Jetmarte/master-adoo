## 📖 La agregación es un punto intermedio

Las relaciones por colaboración forman un **continuo** de fuerza/acoplamiento:

```text
 MÁS FUERTE / RÍGIDO                              MÁS DÉBIL / FLEXIBLE
◄──────────────────────────────────────────────────────────────────────►
   Composición        Agregación        Asociación        Dependencia
       ◆                  ◇                 ───               ┄┄►
   (todo–parte)      (todo–parte)      (cliente–servidor)  (uso puntual)
```

![[relaciones.png]]

> [!tip] Idea clave
> La **agregación** es un **área difusa** entre la **composición** (a su izquierda) y la **asociación** (a su derecha).

---

## 📊 Tabla comparativa completa

| Relación | UML | Visibilidad | Temporalidad | Versatilidad | Idea central |
|----------|-----|-------------|--------------|--------------|--------------|
| **Composición** | ◆ rombo relleno | Privada | No momentánea | Reducida | La parte vive y muere con el todo |
| **Agregación** | ◇ rombo vacío | Pública | No momentánea | Reducida | La parte forma parte, pero sobrevive |
| **Asociación** | Línea continua | Pública | No momentánea | Reducida | Cliente usa un servidor **concreto** de forma estable |
| **Dependencia** | Flecha discontinua | Pública o privada | **Momentánea** | **Alta** | Cliente usa **cualquier** servidor de forma puntual |

---

## 🧭 El contexto lo decide casi todo

> [!quote] Factor determinante
> El **contexto** en el que se desenvuelven los objetos determina de forma "categórica" qué grados de **visibilidad**, **temporalidad** y **versatilidad** se producen en su colaboración.

### Ejemplo 1: paciente y médico

| Contexto | Relación que se inclina |
|----------|-------------------------|
| Hospital de **urgencias** | **Dependencia (uso)**: atención puntual |
| **Médico de cabecera** que conoce el historial y tiene pendiente un tratamiento | **Asociación**: relación estable con un servidor concreto |

### Ejemplo 2: motor y coche

| Contexto | Relación que se inclina |
|----------|-------------------------|
| **Taller mecánico** (se accede al motor, se cambian motores) | **Asociación**: el motor se usa como servidor intercambiable |
| **Gestión municipal del parque automovilístico** (altas, bajas, denuncias; el motor responde por características del vehículo) | **Composición**: el motor forma parte indisociable del coche |

### Ejemplo 3: tienda POS

| Contexto | Relación que se inclina |
|----------|-------------------------|
| `Venta` y `LineaVenta` | **Composición**: la línea solo existe dentro de la venta |
| `Venta` y `Producto` del catálogo | **Asociación** o **agregación**: el producto existe fuera de la venta |

## ⚠️ No hay una relación ideal

> [!quote] [Rumbaugh, 91]
> "La decisión de utilizar una agregación es discutible y suele ser arbitraria. Con frecuencia, no resulta evidente que una asociación deba ser modelada en forma de agregación. En gran parte, este tipo de incertidumbre es típico del modelado; este requiere un juicio bien formado y hay pocas reglas inamovibles. La experiencia demuestra que si uno piensa cuidadosamente e intenta ser congruente, la distinción imprecisa entre asociación ordinaria y agregación no da lugar a problemas en la práctica."

Consecuencias:

- Para una misma colaboración suele haber **varias relaciones candidatas**, cada una con ventajas y desventajas.
- Elegir es una **decisión de ingeniería**: un compromiso entre **costes, modularidad, legibilidad, eficiencia**, etc.
- El objetivo principal **no** es acertar la etiqueta, sino:
  1. Analizar/diseñar **cómo colaboran** los objetos para cumplir los requisitos.
  2. Analizar/diseñar **entre qué clases no existe relación**.

## 💻 Pautas de traducción a código

No hay fórmulas exactas, solo **pautas de actuación** que dan un esqueleto del programa. La responsabilidad final es del programador.

| Relación | Pauta de implementación |
|----------|-------------------------|
| **Composición** | La clase "todo" **crea** un objeto de la clase "parte" y lo mantiene como **referencia atributo**. |
| **Agregación** | La clase "todo" mantiene una referencia atributo a la parte, que se **suministra** desde un constructor o un método para añadir el agregado. |
| **Asociación** | La clase "cliente" mantiene una referencia atributo al servidor, que se **suministra** desde un constructor o un método para establecer la asociación. |
| **Dependencia (uso)** | El servidor aparece como **parámetro o valor devuelto** de un método si el uso es **público**; como **objeto local** de un método si es **privado**. |

```java
// Composición: el todo crea la parte
class Venta {
    private final List<LineaVenta> lineas = new ArrayList<>();
    void agregar(Producto p, int c) { lineas.add(new LineaVenta(p, c)); }
}

// Agregación: la parte se inyecta y sobrevive
class Biblioteca {
    private final List<Libro> catalogo;
    Biblioteca(List<Libro> catalogo) { this.catalogo = catalogo; }
}

// Asociación: referencia estable a un servidor concreto
class Socio {
    private final Biblioteca biblioteca;
    Socio(Biblioteca b) { this.biblioteca = b; }
}

// Dependencia: uso puntual como parámetro o variable local
class ServicioPrestamo {
    void registrar(Prestamo p, CalculadoraMulta c) { p.setMulta(c.calcular(p)); }
    void imprimir(Prestamo p) { new Impresora().imprimir(p); }
}
```

## 🧭 Guía rápida de decisión

1. ¿Es una relación **"es un"**? → **Herencia**.
2. ¿Es una relación **todo–parte**?
   - La parte **no vive sin** el todo y **no se comparte** → **Composición**.
   - La parte **sobrevive** o **se comparte** → **Agregación**.
3. ¿No es todo–parte, pero el cliente usa un servidor **concreto** de forma **estable**? → **Asociación**.
4. ¿El uso es **puntual**, con **cualquier** servidor y **sin dependencia futura**? → **Dependencia (uso)**.
5. ¿No colaboran ni hay jerarquía? → **No hay relación**.

> [!warning] La última palabra la tiene el contexto
> La misma pareja de clases puede cambiar de relación según el sistema. Lo importante es **ser congruente** y poder **justificar** la elección.

---

## ✅ Conclusión para examen

1. El continuo va de **composición** (más fuerte) a **dependencia** (más débil); la **agregación** queda en medio.
2. **Visibilidad, temporalidad y versatilidad** describen la relación, pero el **contexto** decide.
3. No existe **relación ideal** ni **fórmula** de traducción a código: hay **pautas** y decisiones de ingeniería.
4. El objetivo es modelar **cómo colaboran** los objetos, no solo poner la etiqueta correcta.
5. Las pautas de implementación se resumen en: **crear** (composición), **inyectar** (agregación/asociación) y **usar como parámetro/local** (dependencia).
