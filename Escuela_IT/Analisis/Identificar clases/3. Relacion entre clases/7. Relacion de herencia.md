# 7. Relación de herencia

> [!info] Relación **"es un"** · Sección 4.4.7
> Anterior: [[6. Comparativa entre clases por colaboracion|Comparativa]] · [[1. Tipos de relacion entre clases|Volver a tipos de relación]]

---

## 📖 Definición

La **herencia** es la **transmisión de la vista pública y de la vista privada** de una clase a otra.

| Vista | Qué se transmite |
|-------|------------------|
| **Pública** | Métodos públicos |
| **Privada** | Atributos, métodos privados y **definición de los métodos** |

> [!tip] Idea clave
> La clase **hija** (subclase) recibe los miembros de la clase **padre** (superclase) y puede **añadir** o **redefinir** comportamiento. No es una relación de uso: **no exige** que los objetos colaboren, aunque **no lo impide**.

---

## 🧭 Reglas de construcción

### ✅ Regla ISA

**ISA** = *is a* = **"¿... es un ...?"**

> [!success] Pregunta de validación
> ¿**Un elemento del dominio del nodo hijo** es **un elemento del dominio del nodo padre**?
>
> - `Libro` **es un** `MaterialBiblioteca` → ✅ correcto
> - `Coche` **es un** `Vehiculo` → ✅ correcto
> - `Motor` **es un** `Coche` → ❌ incorrecto (es una **parte**, no un tipo)

Si la respuesta es afirmativa, la herencia es candidata.

### 🔍 Generalización / especialización

La herencia organiza el conocimiento en dos direcciones:

| Dirección | Qué hace | Ejemplo |
|-----------|----------|---------|
| **Generalización** | Sube los rasgos **comunes** al padre | `Libro` y `Revista` → `MaterialBiblioteca` |
| **Especialización** | Baja los rasgos **distintivos** al hijo | `MaterialBiblioteca` → `LibroDidactico` |

> [!note] En qué consiste
> Un subconjunto de elementos mantiene las características **esenciales e identificativas** del conjunto, pero posee rasgos **suficientemente relevantes** como para ser **distintivos** de ese subconjunto.

## 📐 Notación UML

```text
        MaterialBiblioteca
                △
                │
        ┌───────┴───────┐
      Libro          Revista
```

- Línea **continua** con **triángulo hueco** apuntando al **padre**.
- El triángulo siempre está del lado de la **superclase**.

## 💻 Implementación en Java

```java
abstract class MaterialBiblioteca {
    protected String titulo;

    public abstract int diasPrestamo();

    public String getTitulo() {
        return titulo;
    }
}

class Libro extends MaterialBiblioteca {
    @Override
    public int diasPrestamo() {
        return 21;
    }
}

class Revista extends MaterialBiblioteca {
    @Override
    public int diasPrestamo() {
        return 7;
    }
}
```

- `extends` implementa la herencia de **clase**.
- `implements` implementa el **contrato** de una interfaz (herencia de tipo).
- La subclase **hereda** `titulo` y `getTitulo()` y **especializa** `diasPrestamo()`.

## 🆚 Herencia vs. composición

| Criterio | Herencia | Composición/Agregación |
|----------|----------|------------------------|
| **Relación** | **"es un"** (ISA) | **"tiene un"** (todo–parte) |
| **Qué se comparte** | Miembros (atributos y métodos) | Objetos |
| **Acoplamiento** | **Fuerte**: el hijo depende del padre | Variable (fuerte en composición, débil en agregación) |
| **Flexibilidad** | Baja: se fija en compilación | Alta: se puede cambiar el objeto |
| **Uso típico** | Jerarquías de tipos | Reutilizar comportamiento sin ISA |

> [!warning] No heredes solo para reutilizar código
> Si no se cumple **ISA**, usa **composición**: evitas acoplar la hija al padre y puedes cambiar el comportamiento en tiempo de ejecución.

---

## ⚖️ Cuándo usarla

> [!success] Úsala cuando
> - Se cumple **ISA** de forma clara.
> - El hijo **puede sustituir** al padre sin romper el contrato (principio de sustitución de Liskov).
> - Hay comportamiento **común** que conviene centralizar.
> - La jerarquía es **estable**.

> [!warning] Evítala cuando
> - Solo quieres **reutilizar código** y no hay ISA.
> - La relación es **todo–parte** (usa composición/agregación).
> - La jerarquía va a cambiar mucho (prefiere composición + interfaces).
> - El hijo **no respeta** el contrato del padre.

---

## 🔗 Relación con las demás relaciones

- La clase **hija depende** de la clase **padre** (dependencia en sentido amplio).
- La herencia **no exige colaboración** entre objetos, pero **no la prohíbe**.
- Se combina con **polimorfismo**: el cliente trata a los hijos como si fueran el padre.
- Se relaciona con **variaciones protegidas**: la interfaz del padre es el punto estable; los hijos encapsulan lo que varía.

---

## ✅ Conclusión para examen

1. Herencia = transmisión de la **vista pública** (métodos públicos) y **privada** (atributos, métodos privados y definiciones) de una clase a otra.
2. Se valida con **ISA**: ¿el hijo **es un** padre?
3. **Generalización** sube lo común; **especialización** baja lo distintivo.
4. UML: línea continua con **triángulo hueco** hacia el padre.
5. Es un acoplamiento **fuerte**: úsala solo cuando haya **ISA** real, no para reutilizar código.
