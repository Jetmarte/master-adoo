# 3. Relación de composición y agregación

> [!info] Relación **todo–parte** · Sección 4.4.3
> Anterior: [[2. Caracteristicas de la relacion entre clases|Características]] · Siguiente: [[4. Relacion de asociacion|Asociación]]

---

## 📖 Definición

La **composición/agregación** es la relación que se establece entre el **todo** y la **parte**.

> [!tip] Regla de detección
> Existe una relación todo–parte entre la clase **A** (el todo) y la clase **B** (la parte) si un objeto de A **"tiene un"** objeto de B.

No se limita a cuestiones **físicas**; también cubre relaciones **lógicas**:

| Expresión | Ejemplo (todo – parte) |
|-----------|------------------------|
| "tiene un" | `Libro` – `Página` |
| "contiene un" | `AparatoDigestivo` – `BoloAlimenticio` |
| "posee un" | `Propietario` – `Propiedades` |
| "está formado por" | `Venta` – `LineaVenta` |

---

## 🧩 Composición vs. agregación

La diferencia está en la **fuerza** del vínculo todo–parte.

### 🔒 Composición (fuerte)

- La **vida de la parte coincide** con la vida del todo.
- Los componentes **no pueden compartirse** entre varios objetos compuestos.
- La **supresión del todo** conlleva la **supresión de las partes**.
- La parte **no tiene sentido** sin el todo.

> [!example] Ejemplos de composición
> - `Persona` ◆— `Cabeza`: una cabeza solo puede pertenecer a una persona y no puede existir sin ella.
> - `Libro` ◆— `Página`: al destruir el libro desaparecen sus páginas.
> - `Venta` ◆— `LineaVenta`: las líneas no existen fuera de la venta.
> - `Pedido` ◆— `LineaPedido`.

### 🔓 Agregación (débil)

- Es un tipo de **asociación** que indica que una clase **forma parte** de otra.
- Los componentes **pueden compartirse** entre varios compuestos.
- La **destrucción del compuesto no destruye** los componentes.
- La parte **tiene vida propia**.

> [!example] Ejemplos de agregación
> - `Persona` ◇— `Familia`: una persona puede pertenecer a la familia en que nació y a la que formó después, y seguir viva aunque esas familias ya no existan.
> - `Biblioteca` ◇— `Libro`: los libros existen aunque se cierre la biblioteca.
> - `Equipo` ◇— `Jugador`: el jugador sigue existiendo al disolverse el equipo.
> - `Curso` ◇— `Estudiante`.

## 📊 Tabla comparativa

| Criterio | Composición | Agregación |
|----------|-------------|------------|
| **Fuerza** | Fuerte | Débil |
| **¿Relación todo–parte?** | Sí | Sí |
| **Ciclo de vida** | La parte **muere con** el todo | La parte **sobrevive** al todo |
| **¿Se comparte la parte?** | No | Sí |
| **Supresión del todo** | Elimina las partes | No elimina las partes |
| **Notación UML** | Rombo **relleno** ◆ | Rombo **vacío** ◇ |
| **Visibilidad** | Privada | Pública |

> [!tip] Mnemotecnia UML
> El **rombo** siempre está del lado del **TODO**.
> Relleno ◆ → composición (**fuerte**). Vacío ◇ → agregación (**débil**).

```text
Venta        ◆──────── LineaVenta      (composición)
Biblioteca   ◇──────── Libro           (agregación)
```

## 💻 Implementación en Java

### Composición: el todo **crea** la parte

```java
class Venta {
    private final List<LineaVenta> lineas = new ArrayList<>();

    void agregar(Producto producto, int cantidad) {
        // La Venta crea la LineaVenta: nadie más la comparte
        lineas.add(new LineaVenta(producto, cantidad));
    }
}
```

La parte se crea **dentro** del todo y no se inyecta desde fuera.

### Agregación: el todo **recibe** la parte

```java
class Biblioteca {
    private final List<Libro> catalogo;

    // Los libros vienen de fuera y pueden compartirse
    Biblioteca(List<Libro> catalogo) {
        this.catalogo = catalogo;
    }

    void anadir(Libro libro) {
        catalogo.add(libro);
    }
}
```

La parte se **suministra** desde un constructor o un método para añadir el agregado.

## ⚖️ ¿Composición o agregación?

> [!warning] La frontera es difusa
> La decisión entre agregación y composición (o incluso entre agregación y asociación) es en gran parte **arbitraria** y depende del **contexto** y del **ciclo de vida** que se quiera modelar. No existe una relación ideal categórica.
>
> La experiencia demuestra que, si se piensa con cuidado y se es **congruente**, la distinción imprecisa entre asociación ordinaria y agregación **no da problemas en la práctica** — [Rumbaugh, 91].

Preguntas útiles:

1. ¿La parte **puede existir** sin el todo? → Si sí, **agregación**.
2. ¿La parte **puede compartirse** con otro todo? → Si sí, **agregación**.
3. ¿Al borrar el todo deben **desaparecer** las partes? → Si sí, **composición**.
4. ¿La parte **solo tiene sentido** dentro del todo? → Si sí, **composición**.

---

## ✅ Conclusión para examen

1. Composición/agregación = relación **todo–parte** ("tiene un").
2. **Composición** = vínculo **fuerte**: la parte vive y muere con el todo y no se comparte.
3. **Agregación** = vínculo **débil**: la parte se comparte y sobrevive al todo.
4. UML: rombo **relleno** ◆ para composición, **vacío** ◇ para agregación; el rombo va en el **todo**.
5. En código: el todo **crea** la parte (composición) o la **recibe** (agregación).
