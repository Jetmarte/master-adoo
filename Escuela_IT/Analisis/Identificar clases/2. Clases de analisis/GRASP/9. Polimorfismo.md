# 9. Polimorfismo

> [!info] Principio **8 de 9** · [[1. GRASP|GRASP]]
> Anterior: [[8. Indireccion|Indirección]] · Siguiente: [[10. Variaciones Protegidas|Variaciones protegidas]]

---

## ❓ Problema

*¿Cómo manejar **alternativas basadas en un tipo**?*

*¿Cómo crear **componentes software conectables** (plug-in)?*

- **Alternativas basadas en tipos:** si el programa usa `if-then-else` o `switch` sobre el tipo, **cada nueva alternativa obliga a modificar la lógica** en varios lugares. Extender el programa se vuelve difícil.
- **Componentes conectables:** en una relación cliente/servidor, ¿cómo **reemplazar el servidor** sin afectar al cliente?

---

## ✅ Solución

> [!success] Polimorfismo
> Cuando alternativas o comportamientos relacionados **varían por tipo (clase)**, asignar la responsabilidad del comportamiento a **los tipos en los que varía**, usando **operaciones polimórficas**.

> [!important] Corolario
> **No preguntes por el tipo de un objeto** ni uses lógica condicional para realizar variaciones basadas en tipo.

---

## 💡 Ejemplo (tienda POS)

### ❌ Sin polimorfismo (condicional por tipo)

```java
class Venta {
  void pagar(String tipo, double monto) {
    if (tipo.equals("TARJETA"))       { /* ... */ }
    else if (tipo.equals("EFECTIVO")) { /* ... */ }
    else if (tipo.equals("TRANSFERENCIA")) { /* ... */ }
    // añadir "BITCOIN" ⇒ editar Venta (viola Abierto/Cerrado)
  }
}
```

### ✅ Con polimorfismo

```java
interface MetodoPago {
  void pagar(double monto);
}

class PagoTarjeta       implements MetodoPago { public void pagar(double m) { ... } }
class PagoEfectivo      implements MetodoPago { public void pagar(double m) { ... } }
class PagoTransferencia implements MetodoPago { public void pagar(double m) { ... } }

class Venta {
  void pagar(MetodoPago pago, double monto) {
    pago.pagar(monto);        // sin conocer el tipo concreto
  }
}
```

Añadir `PagoBitcoin` **no toca** `Venta` → el comportamiento varía **en el tipo** donde corresponde.

> [!tip] Otro ejemplo: descuentos
> `interface Descuento { double aplicar(double total); }` con `SinDescuento`, `DescuentoPorcentaje`, `DescuentoFijo`. La `Venta` no pregunta qué descuento es: solo lo aplica.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| Las **extensiones** con nuevas variaciones son fáciles de añadir | Polimorfismo **especulativo** "a prueba de futuro" que nunca se usa |
| Nuevas implementaciones **sin afectar a los clientes** | El esfuerzo extra solo se justifica si la variabilidad es **real o muy probable** |
| Elimina condicionales dispersos → **claridad y flexibilidad** | |

> [!warning] Sé realista
> Antes de invertir en flexibilidad, evalúa la **verdadera probabilidad** de que aparezca la variación. No es raro ver esfuerzo innecesario en variaciones que **nunca surgen**.

---

## 🧠 Cuándo aplicarlo

Aplícalo si:

- Hay un **`if`/`switch` sobre el tipo** que crece con nuevas alternativas.
- Se prevé **agregar tipos** de forma realista (métodos de pago, exportadores, descuentos, impuestos).
- Quieres un diseño **plug-in**: el cliente depende de una interfaz, no de implementaciones.

Si la variación es **improbable**, un condicional simple puede ser suficiente.

---

## 🔗 Relación con otros patrones

- **Variaciones protegidas**: el polimorfismo es su **mecanismo nuclear**.
- **Indirección**: la interfaz actúa como intermediario abstracto.
- **Invención pura**: las jerarquías de estrategias suelen introducir clases artificiales.
- **Bajo acoplamiento**: el cliente solo conoce la **abstracción**.

---

## ✅ Conclusión para examen

1. **Polimorfismo** = asignar el comportamiento **a los tipos donde varía**, usando operaciones polimórficas.
2. Evita `if`/`switch` sobre el tipo → **fácil de extender**.
3. Permite **componentes conectables**: cambiar el servidor sin tocar al cliente.
4. **Contraindicación**: no añadir polimorfismo **especulativo** sin variabilidad realista.

> [!question] Pregunta típica
> *"¿Cómo aplica polimorfismo GRASP en un sistema de pagos?"*
> **Respuesta:** `interface MetodoPago` con `pagar()` e implementaciones `PagoTarjeta`, `PagoEfectivo`, `PagoTransferencia`; `Venta` depende de la interfaz y añadir un método nuevo no requiere modificarla.
