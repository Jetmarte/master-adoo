# 7. Creador

> [!info] Principio **6 de 9** · [[1. GRASP|GRASP]]

---

## ❓ Problema

*¿Quién debería ser el responsable de **crear una nueva instancia** de una clase?*

La creación de objetos es una de las actividades más comunes en un sistema OO, así que conviene un principio general para asignarla. Un buen reparto apoya **bajo acoplamiento**, **claridad**, **encapsulación** y **reutilización**.

---

## ✅ Solución

> [!success] Creador
> Asignar a la clase **B** la responsabilidad de crear instancias de **A** si se cumple **una o más** de estas condiciones:
> - B **contiene o agrega** objetos de A.
> - B **registra** instancias de A.
> - B **usa estrechamente** objetos de A.
> - B tiene los **datos de inicialización** que se pasan al crear A → B es *experto en la creación de A*.

---

## 💡 Ejemplo (tienda POS)

`Venta` **contiene/agrega** sus `LineaVenta` → `Venta` las crea:

```java
class Venta {
  private List<LineaVenta> lineas = new ArrayList<>();

  void agregar(Producto p, int cantidad) {
    lineas.add(new LineaVenta(p, cantidad));   // Venta es Creadora de LineaVenta
  }
}
```

`ControladorVenta` **tiene los datos** y **usa** la `Venta` → puede crearla:

```java
class ControladorVenta {
  Venta iniciarVenta() {
    return new Venta();                        // Creador de Venta
  }
}
```

> [!note] ¿Y quién crea `Producto`?
> `LineaVenta` **usa** un `Producto`, pero **no lo crea**: el `Producto` viene del catálogo (`RepositorioProductos`). Crearlo en la línea sería incorrecto porque no lo contiene ni tiene sus datos de alta.

---

## 🧠 Intención del patrón

Elegir como Creador a una clase que **ya está conectada** al objeto creado (por una asociación existente) **no aumenta el acoplamiento**: la clase creada ya era visible para el Creador.

> [!tip] Creador ⊆ Experto
> Es un caso particular de **Experto en información**: el "experto en la creación" tiene los datos para construir el objeto.

---

## 🏭 Cuando la creación es compleja

A veces crear requiere complejidad: reciclar instancias por rendimiento, creación condicional según una propiedad externa, o elegir entre una **familia** de clases similares. Ahí conviene delegar en una **fábrica** (Factory) —una invención pura— en vez de sobrecargar al Creador.

```java
class FabricaPagos {                    // invención pura
  static MetodoPago crear(String tipo) {
    return switch (tipo) {
      case "TARJETA"      -> new PagoTarjeta();
      case "EFECTIVO"     -> new PagoEfectivo();
      case "TRANSFERENCIA"-> new PagoTransferencia();
      default -> throw new IllegalArgumentException(tipo);
    };
  }
}
```

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| **Bajo acoplamiento**: no añade dependencias nuevas | Si la creación es **compleja**, el Creador se sobrecarga → usar Factory |
| Mayor **claridad** y **encapsulación** | Crear desde una clase **no relacionada** aumenta el acoplamiento |
| Favorece la **reutilización** | |

---

## 🔗 Relación con otros patrones

- **Experto**: Creador es su especialización para la creación.
- **Bajo acoplamiento**: criterio que guía la elección del Creador.
- **Invención pura**: una fábrica/repositorio es una clase artificial que también crea o recupera objetos.

---

## ✅ Conclusión para examen

1. **Creador** = clase que crea otra si la **contiene/agrega**, la **registra**, la **usa mucho** o tiene sus **datos de inicialización**.
2. Se elige un creador **ya conectado** al objeto → apoya **bajo acoplamiento**.
3. Es una especialización del **Experto**.
4. Si la creación es compleja → **fábrica** (invención pura).

> [!question] Pregunta típica
> *"¿Quién debe crear `LineaVenta` según GRASP y por qué?"*
> **Respuesta:** `Venta`, porque **agrega/contiene** sus `LineaVenta`; así se mantiene el bajo acoplamiento y la encapsulación.
