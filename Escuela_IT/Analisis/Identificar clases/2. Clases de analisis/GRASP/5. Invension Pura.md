# 5. Invención pura (Fabricación pura)

> [!info] Principio **4 de 9** · [[1. GRASP|GRASP]]
> Anterior: [[4. Bajo Acoplamiento|Bajo acoplamiento]] · Siguiente: [[6. Controlador|Controlador]]

---

## ❓ Problema

*Asignar responsabilidades solo a clases del dominio suele producir **baja cohesión**, **alto acoplamiento** o **poco potencial de reutilización**.*

Algunas tareas (persistencia, cálculo de impuestos, formateo, notificaciones) **no encajan** en ninguna entidad del mundo real. Si las metemos en `Venta`, esta deja de ser cohesiva y se acopla a la base de datos, al email, etc.

---

## ✅ Solución

> [!success] Invención / Fabricación pura
> Asignar un conjunto **altamente cohesivo** de responsabilidades a una **clase artificial o de conveniencia** que **no representa un concepto del dominio**, para apoyar **alta cohesión**, **bajo acoplamiento** y **reutilización**.

---

## 💡 Ejemplo (tienda POS)

```java
// Clase del DOMINIO: solo sabe de la venta
class Venta {
  private List<LineaVenta> lineas = new ArrayList<>();
  double total() { return lineas.stream().mapToDouble(LineaVenta::subtotal).sum(); }
}
```

```java
// INVENCIONES PURAS: no existen en el negocio, mejoran el diseño
class RepositorioVentas {          // persistencia
  void guardar(Venta v) { /* SQL / ORM */ }
  Venta buscarPorId(int id) { ... }
}

class ServicioCalculoImpuestos {   // reglas de impuestos
  double calcular(Venta v) { ... }
}

class FormateadorMoneda {          // presentación
  String formatear(double monto) { ... }
}
```

> [!note] Ejemplos clásicos de Larman
> - **"Cadena de caracteres poética"**: responsabilidades sobre rimas que no quieres meter en la `String` general.
> - **"Formateador de intervalos"**: distintas presentaciones de un rango de fechas.

---

## 🧠 Criterio para decidir

Pregúntate:

1. ¿La tarea pertenece **conceptualmente** a una entidad del dominio? → Experto.
2. ¿Meterla ahí **baja la cohesión** o **sube el acoplamiento** (BD, red, UI)? → **Invención pura**.
3. ¿La clase nueva agrupa responsabilidades **afines**? → sí, debe ser cohesiva.

> [!tip] Nombres típicos
> `Repositorio...`, `Servicio...`, `Gestor...`, `Formateador...`, `Calculadora...`, `Notificador...`.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| **Alta cohesión**: cada clase hace una cosa | Puede **diluir el modelo de dominio** si se abusa |
| **Bajo acoplamiento**: el dominio no conoce BD/UI/red | Riesgo de **sobre-ingeniería** con clases auxiliares innecesarias |
| **Reutilización**: el servicio sirve en varios contextos | Nombres vagos (`Utilidades`, `Manager`) pueden volverse cajón de sastre |

> [!warning] No confundir
> Invención pura **no** es "una clase para todo". Debe ser **cohesiva**. Una clase `Utilidades` que hace de todo es el **anti-ejemplo**.

---

## 🔗 Relación con otros patrones

- **Experto**: se usa primero; si el experto rompe cohesión/acoplamiento → invención pura.
- **Bajo acoplamiento / Alta cohesión**: son los **objetivos** que justifican la invención pura.
- **Indirección**: muchas invenciones puras (repositorios, servicios) actúan como **intermediarios**.
- **Variaciones protegidas**: los servicios suelen detrás de una **interfaz** (p. ej. `RepositorioVentas`).

---

## ✅ Conclusión para examen

1. **Invención pura** = clase **fuera del dominio** que agrupa responsabilidades afines para mejorar el diseño.
2. Se crea cuando asignar la tarea a una entidad del dominio causaría **baja cohesión** o **alto acoplamiento**.
3. Favorece **cohesión, acoplamiento y reutilización**.
4. Ejemplos: `RepositorioVentas`, `ServicioCalculoImpuestos`, `FormateadorMoneda`.

> [!question] Pregunta típica
> *"¿Qué es la invención pura y cuándo la usaría?"*
> **Respuesta:** crear una clase que no representa el dominio (p. ej. `RepositorioVentas`) para sacar de `Venta` la persistencia y mantener cohesión y bajo acoplamiento.
