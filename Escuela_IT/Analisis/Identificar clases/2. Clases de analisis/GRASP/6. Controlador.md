# 6. Controlador

> [!info] Principio **5 de 9** · [[1. GRASP|GRASP]]
> Anterior: [[5. Invension Pura|Invención pura]] · Siguiente: [[7. Creador|Creador]]

---

## ❓ Problema

*¿Quién debe ser responsable de manejar un **evento de sistema** de entrada generado por un agente externo?*

Un **evento de sistema** lo genera un actor externo: una persona (teclado/ratón) o una máquina (sensor, trama de red).

---

## ✅ Solución

> [!success] Controlador
> Asignar la responsabilidad de **recibir o manejar** los eventos del sistema a una clase que represente **una de estas opciones**:
> 1. El **sistema, dispositivo o subsistema en general** (controlador *fachada*).
> 2. Un **caso de uso** dentro del cual ocurre el evento → `<NombreCasoDeUso>Controller` (controlador *de caso de uso*).
>
> El controlador **define los métodos** de las operaciones del sistema y **delega** el trabajo real.

---

## 💡 Ejemplo (tienda POS)

```java
class ControladorVenta {                 // controlador de caso de uso "Registrar venta"
  private Venta venta;
  private RepositorioVentas repo;
  private ServicioNotificaciones notificador;

  void iniciarVenta() { venta = new Venta(); }

  void agregarProducto(Producto p, int cantidad) {
    venta.agregar(new LineaVenta(p, cantidad));   // delega en el dominio
  }

  void finalizarVenta(MetodoPago pago) {
    venta.pagar(pago);                            // delega
    repo.guardar(venta);                          // delega
    notificador.enviarConfirmacion(venta);        // delega
  }
}
```

> [!important] El controlador **coordina**, no hace el trabajo
> Recibe el evento, ordena la secuencia y **delega** en `Venta`, `RepositorioVentas`, `ServicioNotificaciones`.

---

## 🚫 Qué NO es un controlador

- **No** es un objeto de **interfaz de usuario**.
- Clases `Window`, `Widget`, `View`, `Dialog`, `Document` **no** deben contener la lógica del evento: lo **reciben y lo delegan** a un controlador.

```java
// ✅ La vista recibe y delega
class PantallaVenta {
  private ControladorVenta controlador;

  void onBotonFinalizarClick() {
    controlador.finalizarVenta(pagoSeleccionado);
  }
}
```

| ❌ Mal | ✅ Bien |
|--------|---------|
| `PantallaVenta` calcula totales, guarda en BD y envía emails | `PantallaVenta` llama a `ControladorVenta` |
| Un `Sistema` gigante con todos los casos de uso | Un controlador **por caso de uso** |

---

## ⚖️ Tipos de controlador

| Tipo | Descripción | Cuándo usar |
|------|-------------|-------------|
| **Fachada (Facade controller)** | Una clase representa todo el sistema/subsistema | Sistemas pequeños o pocos casos de uso |
| **De caso de uso** | Una clase por caso de uso (`ControladorVenta`, `ControladorPago`) | Lo habitual; evita controladores "hinchados" |

> [!warning] Anti-patrón: controlador hinchado
> Un único controlador con decenas de métodos mezcla casos de uso → **baja cohesión** y **alto acoplamiento**. Divide por caso de uso.

---

## 💡 Implicaciones

- Informalmente, una **sesión** es una instancia de conversación con un actor; suele organizarse por casos de uso.
- El controlador **no ejecuta** el trabajo: **coordina o controla** la actividad.
- Colabora con el **Experto en información** para repartir el trabajo entre las clases del dominio.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| Separa la **interfaz** de la **lógica** | Un solo controlador para todo → clase **hinchada** |
| Punto único de entrada por caso de uso | Puede convertirse en un **cuello de botella** si absorbe lógica |
| Facilita **reutilizar** la lógica con otras UIs (web, móvil, escritorio) | |

---

## 🔗 Relación con otros patrones

- **Experto**: el controlador no calcula; delega en los expertos.
- **Bajo acoplamiento / Alta cohesión**: un controlador por caso de uso mantiene ambos.
- **Indirección**: el controlador es el intermediario entre la UI y el dominio.
- **Creador**: puede crear el objeto del caso de uso (p. ej. `new Venta()`).

---

## ✅ Conclusión para examen

1. **Controlador** = objeto que **recibe eventos del sistema** y **delega**.
2. Dos variantes: **fachada** (todo el sistema) o **de caso de uso** (`<CasoUso>Controller`).
3. **No es** la clase de interfaz: `Window`/`View`/`Widget` **delegan** en él.
4. **Coordina**, no ejecuta el trabajo → evita el controlador hinchado.

> [!question] Pregunta típica
> *"¿Qué es un controlador GRASP y qué diferencia tiene con una clase de interfaz?"*
> **Respuesta:** el controlador maneja los eventos del sistema y delega la lógica; la clase de interfaz solo **captura** el evento y se lo pasa al controlador. Ej.: `PantallaVenta` → `ControladorVenta`.
