# 2. Experto en la información

> [!info] Principio **1 de 9** · [[1. GRASP|GRASP]]
> Anterior: [[1. GRASP|GRASP]] · Siguiente: [[3. Alta cohesion|Alta cohesión]]

---

## ❓ Problema

*¿Cuál es un principio general para asignar responsabilidades a los objetos?*

Un modelo de diseño puede tener cientos o miles de clases, y una aplicación cientos o miles de responsabilidades que cumplir. Al definir las interacciones tomamos decisiones sobre **a quién** asignar cada responsabilidad. Un buen reparto hace los sistemas **más fáciles de entender, mantener y ampliar**, y da **más oportunidades de reutilización**.

---

## ✅ Solución

> [!success] Experto en la información
> Asignar la responsabilidad **a la clase que tiene la información necesaria** para cumplirla.

Es la "intuición" de que los objetos hacen cosas relacionadas con la información que tienen. En el mundo real también damos la tarea a quien **tiene los datos** para hacerla.

---

## 💡 Ejemplo (tienda POS)

`LineaVenta` conoce el `Producto` y la `cantidad` → **calcula su subtotal**.
`Venta` conoce sus `LineaVenta` → **calcula su total**.

```java
class LineaVenta {
  private Producto producto;
  private int cantidad;

  double subtotal() {                       // experta: tiene producto y cantidad
    return producto.precio() * cantidad;
  }
}

class Venta {
  private List<LineaVenta> lineas = new ArrayList<>();

  double total() {                          // experta: tiene las líneas
    return lineas.stream().mapToDouble(LineaVenta::subtotal).sum();
  }
}
```

> [!note] Expertos "parciales"
> Una responsabilidad suele necesitar información de **varias clases**. `Venta.total()` **colabora** con `LineaVenta.subtotal()`, que a su vez colabora con `Producto.precio()`. Cada objeto aporta su parte.

### ❌ Contraejemplo

```java
class GestorReportes {                      // NO tiene los datos de la venta
  double totalDe(Venta v) {
    double suma = 0;
    for (LineaVenta l : v.getLineas())      // rompe la encapsulación
      suma += l.getProducto().getPrecio() * l.getCantidad();
    return suma;
  }
}
```
Aquí `GestorReportes` accede a datos internos de `Venta`: **viola encapsulación** y crea acoplamiento.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| Mantiene la **encapsulación**: cada objeto usa su propia información | A veces el "experto" produce **bajo acoplamiento/cohesión** y hay que desviarse |
| Distribuye el comportamiento → clases más **cohesionadas** | Puede violar la **separación de intereses** (p. ej. experto de persistencia + negocio) |
| Sistemas más **robustos y fáciles de mantener** | Mal ejemplo: una clase que concentra **todo** el código en un archivo |

> [!warning] Cuando el experto es mala idea
> Si seguir al experto aumenta el **acoplamiento** o baja la **cohesión**, el diseño pierde. Ahí se usan otros principios (Indirección, Invención pura) aunque el experto "tenga" los datos.

---

## 🔗 Relación con otros patrones

- **Creador** es un caso particular del Experto: *experto en la creación* (tiene los datos de inicialización).
- **Alta cohesión** y **Bajo acoplamiento** son los criterios que **limitan** al Experto.
- **Invención pura** aparece cuando ninguna clase del dominio es buena experta para cierta tarea.

---

## ✅ Conclusión para examen

1. Asignar la responsabilidad a la clase que **tiene la información** [Larman].
2. Mantiene la **encapsulación** y distribuye el comportamiento → alta cohesión.
3. Hay **expertos parciales** que colaboran.
4. Si el experto rompe cohesión/acoplamiento, **no se aplica ciegamente**.

> [!question] Pregunta típica
> *"¿Qué dice el patrón Experto en información? Dé un ejemplo."*
> **Respuesta:** asignar la responsabilidad a la clase que posee los datos necesarios. Ej.: `Venta.total()` porque conoce sus líneas; `LineaVenta.subtotal()` porque conoce producto y cantidad.
