# 10. Variaciones protegidas

> [!info] Principio **9 de 9** · [[1. GRASP|GRASP]]
> Anterior: [[9. Polimorfismo|Polimorfismo]] · [[1. GRASP|Volver al índice]]

---

## ❓ Problema

*¿Cómo diseñar objetos, subsistemas o sistemas de modo que **variaciones o inestabilidades** no tengan un **impacto indeseable** en otros elementos?*

---

## ✅ Solución

> [!success] Variaciones protegidas
> **Identificar los puntos de variación o inestabilidad previstos** y asignar responsabilidades para crear **interfaces estables** alrededor de ellos.

```
   Cliente ───► [ Interfaz estable ] ◄─── Implementación A / B / C
                      (punto fijo)              (lo que cambia)
```

---

## 💡 Ejemplo (tienda POS)

`MetodoPago` es una **interfaz estable**; lo que varía queda detrás:

```java
interface MetodoPago { void pagar(double monto); }   // estable

class PagoTarjeta       implements MetodoPago { ... }
class PagoEfectivo      implements MetodoPago { ... }
class PagoTransferencia implements MetodoPago { ... }
// mañana: PagoBitcoin, PagoBizum... sin tocar Venta ni ControladorVenta
```

Otros ejemplos:

- `CalculadoraImpuestos` (interfaz) → `IVAEspana`, `IVAMexico`…: cambia la ley, no el sistema.
- **Diseños dirigidos por datos**: leer valores, nombres de clase, ficheros de propiedades, hojas de estilo… para **parametrizar el comportamiento en tiempo de ejecución** sin recompilar.

---

## 🧩 Fundamentos teóricos

> [!quote] Mismo principio, distintos nombres
> - **Principio Abierto/Cerrado de Meyer (SOLID)**: abierto a extensión, cerrado a modificación. Es la misma idea con otro énfasis.
> - **Ocultación de información de Parnas**: ocultar las decisiones que pueden cambiar (no solo encapsulación de datos).
> - **Indirección + Polimorfismo**: mecanismos habituales para implementarlo.

| Mecanismo | Cómo protege |
|-----------|--------------|
| **Encapsulación** | Oculta los detalles internos |
| **Polimorfismo** | Permite sustituir implementaciones |
| **Indirección** | Aísla al cliente del componente que varía |
| **Estándares** | Fijan interfaces comunes (p. ej. protocolos) |
| **Diseño dirigido por datos** | Cambia comportamiento sin modificar código |

---

## ⚠️ Contraindicaciones (¡importante!)

> [!warning] No todo futuro merece protección
> Distingue **dos tipos de puntos de cambio**:
> - **Punto de variación**: la variación **ya debe soportarse** (requisito actual).
> - **Punto de evolución**: variación **posible en el futuro**, pero aún no requerida.

- Proteger un **punto de evolución** especulativo puede costar más que **rehacer** un diseño simple cuando el cambio llegue de verdad.
- El **coste de la protección** (complejidad, pruebas, capas) puede superar el coste del **retrabajo**.
- **Equilibrio:** no abogues por diseños frágiles; si la flexibilidad es **realista**, aplícala. Si es especulativa con probabilidad incierta → **moderación y pensamiento crítico**.

---

## ⚖️ Beneficios y contraindicaciones

| ✅ Beneficios | ⚠️ Contraindicaciones |
|---------------|------------------------|
| El sistema **resiste cambios** en puntos inestables | Proteger **futuros especulativos** innecesarios |
| Añadir variantes **sin tocar** a los clientes | Sobrecoste de **complejidad** y pruebas |
| Base de la mayoría de **patrones de diseño** | Puede rigidizar el diseño si se abusa |

---

## 🔗 Relación con otros patrones

- Es la **raíz** que motiva **Polimorfismo**, **Indirección**, **Invención pura** y **Bajo acoplamiento**.
- El **Polimorfismo** es su mecanismo principal cuando la variación es por **tipo**.
- La **Indirección** lo implementa cuando se necesita **mediar** entre cliente y variación.
- **Invención pura**: interfaces/estrategias suelen ser clases artificiales que protegen variaciones.

---

## ✅ Conclusión para examen

1. **Variaciones protegidas** = identificar puntos de cambio y **encapsularlos** tras **interfaces estables**.
2. Se relaciona con **Abierto/Cerrado** (Meyer) y **ocultación de información** (Parnas).
3. Mecanismos: **encapsulación, polimorfismo, indirección, estándares, diseño dirigido por datos**.
4. **Distinguir** punto de variación (actual) vs. punto de evolución (futuro).
5. Proteger **solo** lo que tiene variabilidad **realista**; evitar sobre-ingeniería.

> [!question] Pregunta típica
> *"¿Qué son las variaciones protegidas y cómo se relacionan con Abierto/Cerrado?"*
> **Respuesta:** identificar lo que puede cambiar y aislarlo tras una interfaz estable. Es el mismo principio que Abierto/Cerrado: el sistema queda **abierto a extensión** (nuevas implementaciones) y **cerrado a modificación** (el cliente no cambia).
