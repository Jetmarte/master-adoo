# 5. Análisis de casos de uso

> [!info] Estrategia 5 de 5 para **identificar clases**
> [[1. Descripcion Informal|Descripción informal]] → [[2. Analisis clasico|Análisis clásico]] → [[3.  Analisis del dominio|Análisis del dominio]] → [[4. Analisis del comportamiento|Análisis del comportamiento]] → **Análisis de casos de uso**

---

## 📖 Definición

> [!quote] Estrategia
> A medida que el equipo se guía a través de **cada escenario de cada caso de uso**, se deben identificar los **objetos** que participan, las **responsabilidades** de cada objeto y las formas en que esos objetos **colaboran** con otros, en términos de las **operaciones** que cada uno invoca en el otro.

El análisis de casos de uso obliga a **repartir claramente las responsabilidades** entre todas las abstracciones: cada escenario es una "prueba de esfuerzo" que revela qué objetos hacen falta y qué debe hacer cada uno.

> [!tip] Idea clave
> El caso de uso describe **qué hace el sistema desde fuera**; el análisis del escenario revela **qué objetos lo hacen por dentro** y **cómo se pasan el trabajo** entre ellos.

---

## 🧩 Conceptos básicos

| Concepto | Significado | Ejemplo (biblioteca) |
|----------|-------------|----------------------|
| **Actor** | Rol externo que interactúa con el sistema | Bibliotecario, Socio |
| **Caso de uso** | Servicio completo y observable que el sistema ofrece a un actor | *Realizar préstamo* |
| **Escenario** | Una **instancia concreta** de un caso de uso | "El socio 123 pide el ejemplar A-45" |
| **Curso normal** | Secuencia de pasos que termina en éxito | Préstamo registrado |
| **Curso alternativo** | Variante válida que toma otro camino | El ejemplar no está disponible → reserva |
| **Excepción** | Falla o condición anómala | El catálogo no responde |

> [!important] Un caso de uso tiene **muchos escenarios**
> El **curso normal** es solo uno. Los **alternativos** y las **excepciones** son los que suelen descubrir **nuevas abstracciones** y **nuevas responsabilidades**.

---

## 🔧 Cómo aplicarla

1. **Identificar actores** y **casos de uso** a partir de los requisitos.
2. **Enumerar los escenarios** de cada caso de uso: normal, alternativos y excepciones. Al principio basta con listarlos; no hace falta profundizar.
3. **Recorrer cada escenario paso a paso** e identificar:
   - los **objetos** que participan,
   - la **responsabilidad** de cada uno en ese paso,
   - las **colaboraciones**: qué operación invoca un objeto sobre otro.
4. **Actualizar el modelo**: añadir abstracciones nuevas, **modificar** responsabilidades o **reasignarlas** cuando un objeto queda sobrecargado.
5. **Repetir** con los escenarios secundarios: introducen nuevas abstracciones que ajustan el modelo.
6. **Validar** el modelo con usuarios y expertos del dominio.
7. **Usar los escenarios como base de las pruebas** del sistema.

> [!note] Se puede empezar temprano
> El análisis de casos de uso puede aplicarse ya en el **análisis de requisitos**, cuando usuarios finales, otros expertos y el equipo enumeran los escenarios **fundamentales** para el funcionamiento del sistema.

---

## 🎬 Técnica de *storyboard*

Para estudiar cada escenario se pueden usar técnicas similares a las prácticas de la industria de la televisión y el cine: el **storyboard (guión gráfico)**.

- Se dibujan o describen **viñetas** de cada paso del escenario.
- Cada viñeta muestra **quién actúa**, **qué objeto responde** y **qué mensaje/operación** se intercambia.
- Ayuda a detectar pasos faltantes, objetos redundantes y responsabilidades mal asignadas.

```text
[1] Socio pide préstamo ──▶ [2] Sistema valida socio ──▶ [3] Sistema valida ejemplar
                                                                      │
[6] Confirma al socio ◀── [5] Marca ejemplar prestado ◀── [4] Registra préstamo
```

## 📚 Ejemplo completo: *Realizar préstamo*

**Caso de uso:** Realizar préstamo
**Actor primario:** Bibliotecario
**Actores secundarios:** Socio
**Precondición:** el socio está registrado y el ejemplar existe en el catálogo.

### Curso normal

1. El bibliotecario identifica al socio.
2. El sistema verifica que el socio esté **habilitado**.
3. El bibliotecario ingresa el código del **ejemplar**.
4. El sistema verifica que el ejemplar esté **disponible**.
5. El sistema **registra el préstamo** y calcula la fecha de vencimiento.
6. El sistema **marca el ejemplar como prestado**.
7. El sistema muestra la confirmación al bibliotecario.

### Cursos alternativos y excepciones

| Flujo | Condición | Respuesta del sistema | Abstracción que aparece |
|-------|-----------|-----------------------|-------------------------|
| 2a | Socio no habilitado | Muestra el motivo y cancela | — |
| 4a | Ejemplar no disponible | Ofrece **reservar** el ejemplar | `Reserva` |
| 4b | El ejemplar no existe | Informa el error | — |
| * | Falla la conexión con el catálogo | Registra una **incidencia** | `Incidencia` |

> [!tip] Lo que descubre el análisis
> El flujo alternativo **4a** hace nacer la clase `Reserva`, que no aparecía en el curso normal. La excepción hace nacer `Incidencia`. Esa es la esencia de la estrategia: **los escenarios secundarios amplían el modelo**.

---

## 🔗 Objetos, responsabilidades y colaboraciones

### Paso a paso

| Paso | Objeto responsable | Responsabilidad | Colabora con (operación invocada) |
|------|--------------------|-----------------|-----------------------------------|
| 1 | `Bibliotecario` | Identificar al socio | `ControladorPrestamo.buscarSocio(id)` |
| 2 | `Socio` | Saber si está habilitado | `Socio.estaHabilitado()` |
| 3 | `Bibliotecario` | Ingresar el ejemplar | `ControladorPrestamo.buscarEjemplar(codigo)` |
| 4 | `Ejemplar` | Saber si está disponible | `Ejemplar.estaDisponible()` |
| 5 | `Préstamo` | Registrar datos y calcular vencimiento | `Préstamo.crear(socio, ejemplar)` |
| 6 | `Ejemplar` | Cambiar su estado | `Ejemplar.marcarPrestado()` |
| 7 | `ControladorPrestamo` | Confirmar la operación | `ControladorPrestamo.confirmar()` |
| 4a | `Reserva` | Registrar la reserva | `Reserva.crear(socio, ejemplar)` |

### Tarjetas CRC derivadas

**`ControladorPrestamo`**

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Coordinar el caso de uso *Realizar préstamo* | `Socio`, `Ejemplar`, `Préstamo`, `Catálogo` |
| Buscar socio y ejemplar | `Catálogo` |
| Confirmar o rechazar la operación | `Préstamo` |

**`Socio`**

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Conocer su estado de habilitación | — |
| Conocer sus préstamos y reservas | `Préstamo`, `Reserva` |

**`Ejemplar`**

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Conocer su disponibilidad y ubicación | `Catálogo` |
| Cambiar a prestado / disponible | `Préstamo` |

**`Préstamo`**

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Conocer socio, ejemplar y fechas | `Socio`, `Ejemplar` |
| Calcular el vencimiento | `Ejemplar` |
| Saber si está vencido | — |

**`Reserva`** *(nueva, del flujo alternativo)*

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Conocer socio, ejemplar y fecha | `Socio`, `Ejemplar` |
| Notificar disponibilidad | `Ejemplar` |
| Expirar si no se retira | — |

**`Incidencia`** *(nueva, de la excepción)*

| Responsabilidades | Colaboradores |
|-------------------|---------------|
| Conocer el hecho, la fecha y el contexto | — |
| Registrar la falla | `Catálogo` |

## 🧪 De los escenarios a las pruebas

Los escenarios son la **base de las pruebas del sistema**: cada flujo se convierte en un caso de prueba.

| Escenario | Entrada | Resultado esperado |
|-----------|---------|--------------------|
| Normal | Socio habilitado + ejemplar disponible | Préstamo registrado, ejemplar prestado |
| Alternativo 2a | Socio no habilitado | Préstamo rechazado con motivo |
| Alternativo 4a | Ejemplar no disponible | Reserva creada |
| Alternativo 4b | Código inexistente | Mensaje de error, sin cambios |
| Excepción | Catálogo caído | Incidencia registrada, operación cancelada |

> [!important] Trazabilidad
> Cada caso de prueba queda **trazado** a un escenario y a las responsabilidades del modelo. Si cambia el escenario, se sabe **qué clases y qué pruebas** revisar.

## 🛒 Segundo ejemplo breve: *Finalizar compra*

**Caso de uso:** Finalizar compra — **Actor:** Comprador.

| Flujo | Objetos que participan | Responsabilidades / colaboraciones | Abstracción nueva |
|-------|------------------------|------------------------------------|-------------------|
| Normal | `Comprador`, `Carrito`, `Pedido`, `Pago` | `Carrito.calcularTotal()`, `Pedido.crear()`, `Pago.procesar()` | — |
| Alternativo: pago rechazado | `Pago`, `Pedido` | `Pago.rechazar()`, `Pedido.marcarPendiente()` | `ReintentoPago` |
| Alternativo: sin stock | `Inventario`, `Pedido` | `Inventario.verificar()`, `Pedido.rechazar()` | `NotificaciónStock` |
| Excepción: pasarela caída | `PasarelaPago`, `Pedido` | Registrar falla y reintentar | `IncidenciaPago` |

> [!tip] Patrón que se repite
> Los **flujos alternativos y las excepciones** son los que más clases nuevas aportan. El curso normal suele confirmar las clases ya conocidas.

## ✅ Ventajas vs ⚠️ Riesgos

| ✅ Ventajas | ⚠️ Riesgos |
|-------------|------------|
| Fuerza una **separación clara** de responsabilidades | Requiere **escenarios bien redactados** |
| Descubre clases en **flujos alternativos y excepciones** | Se puede **sobre-diseñar** si se profundiza demasiado pronto |
| Conecta requisitos, modelo y **pruebas** | Un escenario mal elegido **sesga** el modelo |
| Se aplica desde el **análisis de requisitos** | Difícil de priorizar con **muchos** casos de uso |
| Facilita la **comunicación** con usuarios y expertos | No reemplaza al análisis del dominio ni al clásico |

> [!caution] Error frecuente
> Analizar solo el **curso normal**. Los flujos alternativos y las excepciones son justamente donde aparecen las abstracciones que faltan (`Reserva`, `Incidencia`, `ReintentoPago`).

---

## ✅ Conclusión para examen

1. El análisis de casos de uso recorre **cada escenario** identificando **objetos, responsabilidades y colaboraciones** (operaciones que un objeto invoca en otro).
2. Obliga a una **separación clara de responsabilidades** entre todas las abstracciones.
3. Se empieza **enumerando** escenarios; luego se amplían con **condiciones excepcionales y comportamientos secundarios**.
4. Los escenarios secundarios **introducen nuevas abstracciones** o **reasignan** responsabilidades existentes.
5. Puede aplicarse desde el **análisis de requisitos** y sirve como **base de las pruebas**.
6. Se apoya en técnicas de **storyboard** y se complementa con **GRASP** y las tarjetas **CRC**.

> [!question] Pregunta típica
> *"¿Qué se identifica al recorrer un escenario de un caso de uso?"*
> **Respuesta:** los **objetos** que participan, las **responsabilidades** de cada uno y las **colaboraciones** entre ellos, expresadas como las **operaciones** que cada objeto invoca en otro; además, se añaden o reasignan responsabilidades y se descubren nuevas abstracciones en los flujos alternativos.
